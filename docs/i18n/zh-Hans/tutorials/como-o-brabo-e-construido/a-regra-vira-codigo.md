# 规则变成代码，文档随之而行

**适合谁：** 见过文档在代码旁边变旧、并想阻止这种事的人。

**读完之后你可以：** 判断某件事是业务规则还是架构决定，把它记录在正确的位置，并知道哪些内容要与变更进入同一个 PR。

## 两类决定，两种记录

| 它是…… | 就成为…… | 会变吗？ |
|---|---|---|
| 产品所遵守的规则（“邀请 7 天后过期”） | 一条带编号的**业务规则** | 会，当业务变化时 |
| 一个结构性选择（“任务使用队列”） | 一条**决定记录**（ADR） | 从不：由新的一条取代 |

## 业务规则指向代码

没有指针的规则只是意见。Brabo 的每条规则都说明它在**哪里**被落实，以及**哪个测试**证明了它：

```markdown
### Convite expira em 7 dias
O convite deixa de valer 7 dias depois de enviado.
- Código: `src/convites/expira.ts:42`
- Teste: `src/convites/expira.spec.ts`
```

一个检查会确认文件存在，并且该行仍然指向那个符号。如果有人移动了代码却忘了规则，检查就会失败。规则不会悄无声息地变旧。

:::nota[不重复的锚点]
每条规则都有唯一编号。创建之前，要在**所有**打开的分支里找下一个空闲编号，而不只是主分支。两条并行的工作线常常会选到同一个。
:::

## ADR 记录“为什么”

ADR 是一页简短的文字，包含背景、决定和后果。金科玉律：**已接受的 ADR 不再编辑。** 如果决定变了，就写一条新的，并说明它取代哪一条。决定的历史像日记一样阅读，而日记是不会被改写的。[ADR 模板](copie-o-metodo.md)可以直接复制。

并非每次变更都需要 ADR。需要它的是改动边界、数据库、一致性模型或重量级依赖的人。

## 文档进入同一个 PR

Brabo 对“完成”的定义包括：

1. 代码和测试；
2. 更新后的仓库文档（`docs/`）；
3. `CHANGELOG.md` 中“Unreleased”下的一行；
4. 变化时的 README 和贡献指南；
5. 聚合各仓库文档的站点。

不存在“文档以后再说”。一个 PR 如果改变了可观察的行为却没有触及相应文档，就没有完成。

## 告诉你该更新什么的地图

为了不依赖记忆，一个文件（`docs/.docmap.yml`）把**代码路径**与**文档**关联起来。修改 `src/convites/` 的人会看到 `docs/convites.md` 依赖它。这张地图是**下限**：它提醒你最低限度，但写作者仍然要在目录里查找其他受影响的页面。

标记为生成的文件绝不手动编辑；由生成器重写。

## 信息不足时

如果写作者没有办法知道某件事，就留下一个醒目的标记：

```markdown
> **TODO(humano):** o prazo de 7 dias vale para convites reenviados?
```

编造的文档比缺失的文档更糟。这个标记会变成看板上的一个问题，而[任务](do-pedido-a-atividade.md)在有人回答之前不会带上 `#explorada`。
