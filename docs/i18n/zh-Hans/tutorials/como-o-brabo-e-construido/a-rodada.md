# 轮次

**适合谁：** 想把一批任务分给多个执行者（人或智能体），又不让他们互相踩脚的人。

**读完之后你可以：** 规划一个带并行通道的轮次，说明哪些必须顺序执行及原因，并描述通向合并的路径。

## 什么是轮次

一个**轮次**是一批已调研的任务，同时执行。每个任务进入一条**通道**（lane），每条通道就是一个执行者（一个人或一个智能体）。当变更被集成并验证之后，轮次结束。

## 两个角色，彼此分开

| 角色 | 能写代码吗？ | 做什么 |
|---|---|---|
| **分析员** | 不能，只读 | 梳理需求，并把结果写进笔记 |
| **执行者** | 能，在自己的通道内 | 实现、测试并写文档 |

这种分离是这套方法中最有价值的规则。梳理需求的人不会“顺手就改了”。执行的人拿到的是现成的规格。两个示例智能体见[复制这套方法](copie-o-metodo.md)。

## 组建轮次

1. **重新阅读看板。** 只有带 `#explorada` 的任务才能进入。
2. **拆成通道。** 每条通道的文件或区域与同一轮次中的其他通道**互不相交**。
3. **标出顺序执行的部分。** 有真实依赖、共享文件、唯一资源（一个数据库、一个环境）或需要人工操作的，排队等候。
4. **一次性启动所有通道。** 协调者不会等一条结束后再放出下一条。
5. **同时更新看板：** 各通道的卡片移到“进行中”。

:::dica[共享文件由协调者掌管]
索引、菜单列表和看板本身都是冲突点。任何通道都不编辑它们。每条通道在报告中写明需要加入的那一行，由协调者合并。
:::

## 每条通道收到什么

一份好的通道简报一屏就能放下，并包含：

- 起点（代码基线，带 SHA）；
- 任务笔记，它就是规格；
- **不要**碰的东西；
- 验证命令，以及每条命令预期的退出码；
- 报告的格式。

通道不会再开其他智能体。并行度的上限属于协调者，而不是每条通道。

## 每个仓库一个 PR

当两条通道改动同一个仓库时，它们把工作**合并**到一个分支，并为这一轮开**一个** PR。证据就是这个 PR 的 CI。这样可以减少评审噪音，让历史保持可读。

从 PR 到发布的路径在[一次变更的一生](../orquestrar-repositorios/vida-de-uma-mudanca.md)中描述。这里不再重复。

## 评审与合并

协调者负责**集成**：检查每条通道的 diff，运行验证，并更新看板。合并进受保护分支是产品**负责人**的事。没有任何通道、任何智能体可以合并进主分支。

:::cuidado[核对通道所说的话]
通道的报告不是证据。运行命令，读退出码。没有退出码的“测试通过”已经不止一次误导了团队。
:::

## 出问题时

一条通道失败不会拖垮其他通道。协调者读出原因，修正简报，只重新启动那一条通道。原因写入任务笔记。
