# Соберите свой

**Для кого:** для тех, кто решил разделить собственный продукт и хочет маршрут.

**После прочтения вы сможете:** перечислить репозитории, которые создадите, по порядку, и сказать для каждого, что скопируете из Brabo, а что измените.

Порядок важен: каждый шаг зависит только от предыдущих. Делайте по одному и **переходите дальше, только когда пример PR этого шага зелёный**.

## 0. Прежде всего: карта

Составьте таблицу ролей со [страницы 2](o-mapa.md) для **вашего** продукта, указав способ потребления ([страница 3](como-cada-repo-e-consumido.md)) на каждом ребре. Если у какого-то репозитория нет ясной роли, пока не создавайте его.

## 1. Родительская папка и «клонировать всё»

- **Скопируйте** подход [`brabo-workspace`](https://github.com/viralabs-dev/brabo-workspace#readme): папка, где клоны лежат рядом, и `clonar-tudo.sh`, который клонирует всё и ничего не удаляет. Список репозиториев - одна переменная.
- **Измените** название организации и список репозиториев.
- **Осторожно:** скрипт совместим с bash 3.2 (macOS); избегайте ассоциативных массивов и `mapfile`.
- **Готово, когда:** `clonar-tudo.sh` на чистой машине раскладывает все клоны по местам.

## 2. Репозиторий CI с политикой

Делайте его **первым из репозиториев с кодом**, потому что его вызывают все остальные.

- **Скопируйте** [`brabo-ci`](https://github.com/viralabs-dev/brabo-ci#readme) или, без форка, просто вызывайте его workflow. [Руководство по внедрению](https://github.com/viralabs-dev/brabo-ci/blob/dev/scripts/ci/docs/tutorials/adotar.md) доводит репозиторий, никогда не видевший Brabo, до зелёных `pr-police` и `escada`, а репозиторий-пример `daneiel/brabo-ci-exemplo` подтверждает шаги.
- **Измените:** `ci_ref` (SHA выбранной версии), переменную `OWNER_HANDLE` и, если нужны одобрения по ролям, режим `community`.
- **Не копируйте вслепую:** ворота QA, `dependencias-de-merge` (предполагает 11 репозиториев) и `contracts-alinhado` (предполагает пакеты `@viralabs-dev/brabo-*`) специфичны для Brabo.
- **Готово, когда:** пример PR показывает зелёные `Política de branches` и `Escada de aprovação`.

## 3. Репозиторий контрактов

- **Скопируйте** подход [`brabo-contracts`](https://github.com/viralabs-dev/brabo-contracts#readme): `publishConfig` с GitHub Packages, `files: ["dist"]` и `publish.yml`, вызывающий `publish-npm.yml` из CI по тегу.
- **Измените:** область (scope) пакетов и содержимое (типы, схемы, файлы данных).
- **Золотое правило:** потребители закрепляют **точную версию**, никогда не ветку.
- **Готово, когда:** тестовый потребитель устанавливает пакет по тегу через `pnpm add`.

## 4. Репозитории с кодом

- **Скопируйте** каркас README из восьми фиксированных разделов ([`README.modelo.md`](https://github.com/viralabs-dev/brabo-ci/blob/dev/README.modelo.md)), вызов `pr-police`/`escada`/`tag-release` и проставление тега.
- **Измените** то, что публикует каждый репозиторий (образ, бинарный файл, пакет), и команды тестов.
- **Готово, когда:** каждый репозиторий публикует тег `-dev.N` при каждом слиянии в `dev`.

## 5. Оркестрирующий репозиторий

- **Скопируйте** идею [`brabo-infra`](https://github.com/viralabs-dev/brabo-infra#readme): compose, скрипты разработки и action, клонирующий соседей.
- **Измените** сервисы compose и список репозиториев в action.
- **Готово, когда:** `docker compose up` поднимает набор из опубликованных образов.

## 6. Репозиторий качества с воротами

- **Скопируйте** подход [`brabo-qa`](https://github.com/viralabs-dev/brabo-qa#readme): E2E, работающий **по digest**, задание, создающее токен App только после чистого checkout, и каталог функциональностей.
- **Измените** каталог и пути каждого репозитория и напишите спецификации **вашего** продукта.
- **Потребуйте** проверку ворот в ruleset ветки `main`, и только в ней.
- **Готово, когда:** PR в `main` краснеет при поломке E2E.

## 7. Входная дверь

- **Скопируйте** структуру [`brabo`](https://github.com/viralabs-dev/brabo#readme): `repos.yml` (единый источник карты), `componentes.json` (пины), `irmaos.lock` и `install.sh`.
- **Измените** список репозиториев и компоненты, образующие **ваш** продукт.
- **Включайте последним** релиз продукта: он зависит от существования релиза каждого компонента.
- **Готово, когда:** установщик проверяет подписанный `checksums.txt` и устанавливает набор на чистой машине.

## Когда всё стоит

Сгенерируйте блок «Onde se encaixa» каждого README из `repos.yml`, включите проверки порядка слияния и пинов и прочтите [ошибки, которые мы уже совершили](erros-que-ja-cometemos.md), прежде чем решать, что всё в порядке.
