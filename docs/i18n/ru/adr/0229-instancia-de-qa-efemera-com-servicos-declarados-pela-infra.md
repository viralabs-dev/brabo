# ADR 0229 — QA тестирует в эфемерном экземпляре, с сервисами, объявленными Infra

## Статус

**Принято.** 2026-10-29 (AT-612, EP-030; решения владельца от 29.10). Тема:
`container`. Расширяет, не редактируя их,
[0130](0130-broker-de-container.md) и
[0228](0228-comando-do-app-e-rede-do-container.md). Эта lane фиксирует
контракт `packages/docker-port` и broker; жизненный цикл (api, engine,
таблица окружений) идёт позже.

## Контекст

QA работает в РАБОЧЕМ контейнере, а RN-817 убивает то, что проект оставил
запущенным, что убило бы объявленное приложение из ADR 0228. Владелец решил: e2e идёт в
отдельном контейнере QA, включаемом только когда он нужен gate, с инфраструктурой приложения
(база, S3...) внутри того же экземпляра, а сервисы определяет Infra,
а не наш каталог.

## Решение

1. **Роль `qa`.** Spec с `qa: { chave, servicos }` — эфемерный экземпляр на задачу:
   имя `brabo-qa-<workspace_dir_name>-<chave>` (`chave` = 8 символов
   `[a-z0-9]`, первые из `taskId`; единственный источник — `nomeDoContainerDeQa`),
   тот же образ, сеть, ресурсы, пользователь и bind `/work`, что у рабочего, БЕЗ
   `--restart`, с `brabo.papel=qa` и `brabo.qa.instancia=<chave>`. Не принимает
   `comandoDoApp` и `portas`. `DockerPort` остаётся с пятью операциями: `stop`,
   `remove`, `inspect` и `exec` получают необязательный параметр
   `alvo: { papel: 'qa', chave }`.
2. **Только помеченное.** С `alvo` QA адаптер фильтрует `brabo.papel=qa`;
   одноимённый контейнер без роли — «неуправляемый» и никогда не затрагивается. Удаление
   QA сначала стирает СОБСТВЕННЫЕ сервисы экземпляра
   (`brabo.qa.dono=<имя QA>`), а затем сам экземпляр; оно вне абсолютного
   потолка `container_remove` (решение владельца), потому что достигает только того,
   что помечено меткой QA.
3. **Сервисы, объявленные Infra.** `{ nome, imagem, env?, dados?,
   compartilhado? }`, до 6. Образ по DIGEST (`@sha256:` + 64 hex)
   ОБЯЗАТЕЛЕН; `env` с ключами `[A-Z_][A-Z0-9_]*` (до 20, значение без перевода
   строки); `dados` — пути в `--tmpfs` (до 3). Каждый сервис поднимается с
   `--network container:<qa>` (один `localhost`), `--cap-drop ALL`, без
   привилегий и `--cap-add`, без опубликованного порта, КОНСТАНТНЫМ потолком 1 cpu,
   512 МБ и 256 pids, `--tmpfs /tmp`, меткой `brabo.papel=qa`. Сбой посередине
   откатывает поднятое.
4. **Общий сервис.** `--network container:` связывает контейнеры только с ОДНИМ
   namespace, поэтому сервис, общий для экземпляров, в него не помещается. Минимальный
   дизайн: он живёт во внутренней сети `--internal` проекта
   (`brabo-qa-<workspace_dir_name>`), имя сервиса как алиас сети,
   контейнер `brabo-qa-<workspace_dir_name>-svc-<nome>` с меткой
   `brabo.qa.compartilhado=1`, переиспользуется, если уже запущен; каждый экземпляр
   подключается к этой сети через `docker network connect`. Требует сети `egress` (контейнер в
   `none` не подключается). Кто и когда удаляет общий — открытый вопрос
   для lane api.
5. **Broker.** Новые маршруты в закрытом маршрутизаторе:
   `/containers/:projectId/qa/:chave/{start,remove,exec}`. Список сервисов
   берётся из `container-spec` api (`?papel=qa&task=<chave>`), никогда из тела; ключ
   маршрута должен быть тем, что вернула api.

## Последствия

- Два тестовых процесса могут работать на проект, не затрагивая рабочее приложение.
- Официальные Postgres/MinIO с `--cap-drop ALL` и tmpfs НЕ измерялись на реальном
  Docker в этой lane; образ, требующий capability, падает при подъёме, с
  именованным `failed`.
- Pull сервисов укладывается в потолок управления 30 с (RN-604) или падает
  именованно: большой образ не поднимается с первой попытки.
