## Локальный runner — выполнение на машине пользователя (RN-418/419/420, ADR 0102/0103) {#runner-local--execução-na-máquina-do-usuário-rn-418419420-adr-01020103}
Запрос владельца продукта: агент, работающий на МАШИНЕ ПОЛЬЗОВАТЕЛЯ, в локальной
папке проекта, через стандартный терминал пользователя, — плюс настоящий
интерактивный терминал во вкладке Code. Два изменения, одно зависит от другого.

**Политика (ADR 0102 — ГЛОБАЛЬНОЕ решение, явно подтверждённое владельцем
продукта после автоматического предупреждения безопасности об изменении)**:
`git push`/PR/deploy (RN-106) и `sudo`/`doas` (новые) выходят из безусловного
`deny` и становятся АБСОЛЮТНЫМ ПРЕДЕЛОМ — безусловным `require_approval`,
в ТОМ ЖЕ блоке и по ТОМУ ЖЕ шаблону, что соседние пределы (`current.policy ===
'auto_approve'`), никогда не автоодобряемым ни через `agent_autonomy` (подстановка `"*"`),
ни через `permissions.json`. Щель, которую исходный `deny` затыкал силой,
закрыта в ИСТОЧНИКЕ: `ApproveAlwaysActionUseCase`/`patternForAction`
отказываются записывать шаблон в `allow` для действия с внешним git-эффектом или
привилегированной командой — «sempre permitir» одобряет только экземпляр, никогда
шаблон, для этих двух случаев. Без этой второй половины предел был бы
декоративным. `sudo`/`doas` совпадают по ГЛАГОЛУ в `comandoPrivilegiadoNoComando`
(`external-effect.ts`), обходя все сегменты команды, — тот же
принцип, что у `efeitoExternoNoComando`.

**Runner (`apps/runner`, новый workspace Node/TS, ADR 0103)**: CLI
(`brabo-runner --project <id> --dir <pasta> --token brb_...`), который
пользователь запускает на своей машине, подключается к ENGINE через НОВЫЙ канал Phoenix
(`/runner`,
топик `terminal:<projectId>`), аутентифицированный ОДНОРАЗОВЫМ тикетом (тот же
шаблон RN-108, но тикет ВЫПУСКАЕТСЯ ENGINE — схема `"engine"`,
собственная миграция — и запрашивается api через внутренний HTTP-маршрут, инвертируя
поток тикета сессии). Выполняет `exec` (УЖЕ ОДОБРЕННУЮ команду агента
— маршрутизация в `TerminalExecutor` происходит только ПОСЛЕ привычного конвейера
`decide()`/`proposed_action`, никогда до) в `$SHELL`
пользователя, и интерактивный режим PTY для вкладки Terminal (`pty_open`/`pty_data`/
`pty_input`/`pty_resize`/`pty_close` — engine делает чистый RELAY, никогда
не интерпретируя байты). Только ОДИН runner на проект (`Engine.Runners.Registry`,
`:global`, исключительность `:global.register_name/3`); режим `runner` БЕЗ
проверенного workspace или БЕЗ подключённого runner-а явно ОТКАЗЫВАЕТ — никогда
не падает в `System.cmd`/bind-mount, которых для проекта `runner` не существует
(пересмотрено ADR 0104/RN-423, см. выше; откат на привычный
путь по-прежнему действует, но только для `container`/`mounted`). PTY — действие
аутентифицированного ПОЛЬЗОВАТЕЛЯ, не проходит через `proposed_action`, но аудируется
(`terminal.session.started`/`ended` в event log, в том числе когда вкладка
падает без явного `pty_close`).

Граница безопасности runner-а — НЕ sandboxing, это аутентификация
(CLI предъявляет Personal Access Token УЧЁТНОЙ ЗАПИСИ пользователя) + привычный
конвейер одобрения + согласие пользователя запускать
CLI на собственной машине, с его привилегиями. `apps/runner/src/guard.ts`
проверяет `cwd` внутри корня лексическим разрешением, но объявлен
BEST-EFFORT, а не настоящей гарантией.

**PAT закрыл пробел токена автоматизации (ADR 0105/RN-424..426).**
Настоящая находка Волны 1 — «у продукта нет механизма ДОЛГОЖИВУЩЕГО токена учётной записи
для автоматизации, поэтому runner повторяет вход браузера
(cookie/CSRF, сохранённые в `~/.brabo/runner-credentials.json`)» — была
закрыта в Волне 2: `personal_access_tokens` (`brb_…`, хеш HMAC-SHA256+
pepper через `hashDeToken()`, никогда argon2 — неверно для секрета ВЫСОКОЙ
энтропии) выпускается в Настройках проекта, с областью ОДНОГО проекта,
отзываемый, с опциональным истечением. `apps/runner/src/auth.ts` полностью потерял
интерактивный вход, cookies и файл учётных данных — он лишь
проверяет формат и передаёт `--token`/`BRABO_ACCOUNT_TOKEN`, НИКОГДА не записываемый
CLI на диск. PAT никогда не аутентифицирует вне
`POST .../runner-ticket`, по ПОСТРОЕНИЮ (`IS_PAT_ROUTE_KEY`/
`@RequirePatAuth()` + `PatAuthGuard`) — никогда ветка в глобальном `JwtAuthGuard`,
которая позволила бы `RolesGuard` авторизовать PAT для любого маршрута
роли пользователя.

**`maintainer` отзывает PAT другого пользователя (RN-427)**, закрывая пункт,
который ADR 0105 пока объявил вне объёма (реагирование на
инцидент — уволенный dev с утекающим токеном). Расширение той же модели,
без нового ADR: ОТДЕЛЬНЫЕ маршруты (`GET .../personal-access-tokens/all`,
`DELETE .../personal-access-tokens/:tokenId/admin`), область по
`projectId` вместо `userId` — самоотзыв каждого пользователя
(RN-426) не меняется.

`@xterm/xterm`/`@xterm/addon-fit` (web) и `phoenix`/`node-pty` (runner) —
четыре новые зависимости — та же линейка исключения, что у `mermaid`
(ADR 0068): динамический `import()`, отсутствие `eval`/`new Function` подтверждено
grep-ом по установленному пакету (это не формальная гарантия против обфускации, только
сильная улика — объявлено как неопределённость, а не утверждено как уверенность).

**ADR 0104 — Волна 1 ЗАВЕРШЕНА (RN-421/422/423):** ADR 0072 и 0103
никогда не разговаривали друг с другом — RN-170 требовал bind-mount при создании, а маршрутизация в
runner (RN-420) переиспользовала тот же флаг `workspace_mode == 'local'` без
какого-либо bind-mount, поэтому настоящее использование runner-а по-прежнему было обязано
проходить проверку смонтированной папки. `workspace_mode` (2 значения) стал
`execution_mode` (`container`/`mounted`/`runner`, миграция `0048`) —
RN-170 (теперь RN-422) начинает действовать только для `mounted`; `runner` рождается с
путём, проверенным только ЛЕКСИЧЕСКИ (без I/O), и `workspaceVerifiedAt: null`,
продвигаемым в проверенный, когда runner подключается и подтверждает путь на
ХОСТЕ (`POST /internal/projects/:projectId/workspace-verification`, RN-423)
— runner — ИСТОЧНИК ИСТИНЫ пути, перезаписывающий то, что было
набрано в мастере. `Engine.Actions.TerminalExecutor.decisao_de_execucao/1`
получил ЧЕТЫРЕ выхода: маршрутизирует только при проверенном workspace И подключённом
runner-е; без любого из двух явно ОТКАЗЫВАЕТ — никогда не падает в
`System.cmd`/bind-mount от `mounted`, которых для проекта
`runner` не существует.

**Находка реализации, исправляющая ADR (который не редактируется —
исправление живёт здесь и в
[backlog.md](backlog.md#backlog-of-the-runnerexecution_mode-adr-0104)):**
фраза ADR 0104 о том, что конвертация между тремя режимами существующего
проекта «становится разрешённой без пересоздания проекта», НЕВЕРНА.
`UpdateProjectDto` по-прежнему намеренно исключает `executionMode`/`workspacePath`
— это не тривиальный PATCH (worktree, permissions.json и кеш
engine указывают на старую область). Волна 1 сдала лишь поле из трёх
значений при СОЗДАНИИ; конвертация существующего проекта — будущая волна, с
собственным замыслом, ещё не запланированная. Backlog runner-а: Волна 2 (PAT,
ADR 0105) закрыла пункт, блокировавший `npm publish @brabo/runner`, а
Волна 3 (ADR 0106) сдала само распространение — `tsup` упаковывает
`apps/runner` в единый `dist/index.cjs` (`node-pty` как обязательный `external`,
нативный binding), публикуемый на каждом финальном теге собственным
workflow (`publish-runner.yml`), параллельным `release.yml`. Настоящая находка,
проверенная эмпирически: защите автозапуска в `index.ts` понадобился
`realpathSync` на `process.argv[1]` — без этого `main()` никогда не выполнялся,
когда CLI вызывался через `bin`, установленный `npm install -g`
(symlink, который `process.argv[1]` никогда не разрешает через realpath, но
`import.meta.url` всегда разрешает). Объявленный операционный незакрытый пункт:
настоящая публикация требует, чтобы владелец продукта создал Automation Token
npm и настроил секрет `NPM_TOKEN` — без него workflow предупреждает и пропускает,
никогда не падает. Исключительность по `{project_id, machine_id}` по-прежнему отложена
до второго реального одновременного dev; best-effort `guard.ts` — ПОДТВЕРЖДЁННЫЙ
инвариант, а не пробел. См.
[ADR 0104](../adr/0104-execution-mode-tres-valores-e-workspace-verificado-pelo-runner.md)/
[ADR 0105](../adr/0105-personal-access-token-do-runner-escopado-por-construcao.md)/
[ADR 0106](../adr/0106-distribuicao-do-runner-via-tsup-e-npm-publish.md).

## ИНСТРУМЕНТ РАЗРАБОТКИ — `pnpm bootstrap` {#ferramenta-de-desenvolvimento--pnpm-bootstrap}
Терминальное меню в `scripts/dev/bootstrap.sh`, группирующее то, что делается
изо дня в день: Docker, K8s, Database и Test. Существует, потому что эти команды живут
в ТРЁХ местах, которые не разговаривают, — `package.json`, `Makefile` и скрипты в
`deploy/k8s/`/`docker/` — а заученное знание гниёт.

Оно **ничего не переизобретает**: каждый лист вызывает уже существующую команду.
Режим `--print-commands` разрешает всё дерево без TTY и без выполнения, и именно
на нём работает тест (`scripts/dev/bootstrap.spec.ts`) — TUI не тестируется
модульно, но отображение меню→команда — да, и ошибается именно оно.
Ноль новых зависимостей; цвета берутся из `design/tokens.css` в 24-битном ANSI
с деградацией до 256 цветов и до отсутствия цвета.

Вывод выполняющейся команды ПРОКРУЧИВАЕТСЯ (колесо мыши в SGR, `j`/`k`,
PageUp/PageDown, `G` для возврата в конец). Не хватало не чтения колеса: не хватало
СМЕЩЕНИЯ — `tail -n` умеет показывать только конец, — поэтому окно стало срезом
через `sed -n 'a,bp'`, тестируемым без TTY через `--print-window`. Два следствия,
которые объявляет подвал: прокрутка назад ЗАМОРАЖИВАЕТ окно (как `less +F`, иначе
перерисовка с частотой 5 Hz отменяет прокрутку), а отслеживание мыши, включаемое только на экране
выполнения, выключается при ЛЮБОМ выходе — `\e[?1006l\e[?1000l` в
`restaurar_terminal`, который покрывает trap на EXIT. Парсер escape — общий CSI
(читает до финального байта): чтение двух фиксированных байтов оставляло остаток последовательности
в буфере, а поскольку меню трактует `[1-9]` как выбор, поворот колеса запускал
пункты меню.

Три зафиксированных решения: `Create` готовит с нуля, а `Deploy` публикует
в уже существующую среду (поэтому выбор по сервису есть только у `Deploy`);
в K8s работает только `All`, а Api/Engine/Web появляются ВЫКЛЮЧЕННЫМИ, а не
исчезают, потому что меню должно говорить, чего продукт не делает; и
`Database › Delete` пересоздаёт расширение pgvector, поскольку
`docker/postgres/init.sql` выполняется только при первой инициализации тома —
чистый `DROP SCHEMA` заставил бы следующую миграцию упасть, а поскольку engine
делит ту же базу, восстановление требует `db:migrate` И `engine:migrate`.

**`Docker › Reset total`** (`scripts/dev/reset-total.sh`) объединяет всю эту
последовательность в один лист — preflight, `up --build --wait` (
`--wait` из Compose v2.17+ — это «пока всё не станет здоровым», без цикла здоровья,
написанного вручную), тот же `DROP SCHEMA`, что у Delete, `db:migrate` +
`engine:migrate` и seed — с СОБСТВЕННЫМ экраном подтверждения
(`confirmar_reset`, требует набрать `RESET`), отличным от экрана Delete (который
требует ИМЯ базы), и без предусловия Delete «postgres уже запущен»,
потому что именно эта команда поднимает compose с нуля. Seed
(`apps/api/src/db/seed.ts`) получил шаг, активирующий учётные данные
provider-а из `.env`, переиспользуя ТЕ ЖЕ переменные
`<PROVIDER>_TEST_KEY`, которые уже используют smoke-тесты LLM
(`apps/api/test/infrastructure/llm/*.smoke.spec.ts`), — одно соглашение
об именах, два потребителя; provider без заданной переменной не входит, без
ошибки, и учётные данные остаются у OWNER-а (RN-058).

Две находки при первом запуске сброса, а не из-за самого пункта —
ни одна не гипотетична, обе сломали реальное выполнение:

1. `gemma:1b` не существует в registry Ollama (`manifest unknown` — существует только
   `gemma3:1b`), поэтому `ollama-model-loader` всегда падал, и
   `--wait` никогда не закрывался зелёным. Исправлено в шести местах, нёсших
   неверное значение как КОД — `docker-compose.yml`/`.prod.yml`,
   `.env.example`, `docker/ollama/pull-models.sh`,
   `scripts/dev/verificar-modelos-ollama.sh`,
   `deploy/k8s/base/ollama/job-model-loader.yaml` и RN-415 в
   `docs/business-rules.md` — без касания ADR 0099/0100 (принятых) и
   исторического повествования этого же раздела CLAUDE.md, которые описывают то, что
   было запрошено/решено тогда, а не текущее операционное значение.
2. Серьёзнее и старше — `Database › Delete` (пункт 3.4, существующий
   с создания меню) никогда не удалял по-настоящему: `DROP SCHEMA public
   CASCADE` не достаёт до `engine.*` (Ecto/Oban живёт в СОБСТВЕННОЙ схеме,
   `engine`) и до `drizzle.__drizzle_migrations` (управление drizzle-kit
   живёт в СОБСТВЕННОЙ схеме, `drizzle`). Результат: `mix ecto.migrate` упирался
   в `duplicate_table` на выживших таблицах engine, а
   `pnpm db:migrate` — хуже, БЕЗ какой-либо ошибки — видел нетронутое управление
   drizzle-kit, заключал, что уже всё выполнил, и не пересоздавал
   НИ ОДНОЙ таблицы api. `Delete`/`Reset total` теперь удаляют также `engine` и
   `drizzle`, в этом порядке, до `public`.

## Сгруппированные вкладки, PR на уровне проекта, локальная папка через Runner, карусель PO (2026-08-20) {#abas-agrupadas-prs-project-wide-pasta-local-via-runner-carrossel-do-po-2026-08-20}
Пять независимых волн, выполненных параллельно по оспариваемому файлу, пришедших
из реального использования экрана проекта — ни одна не запланирована заранее. Шестая волна
той же программы (полный перевод продукта и документации, i18n)
больше пяти вместе взятых; её ФУНДАМЕНТ (Волна 6a — механизм, пока без
перевода содержимого) уже закрыт: `react-i18next`+`i18next` в web
(`en` стал языком приложения по умолчанию, `pt-BR` сохранён — RN-425), столбец
`locale` в `users`, встроенный в payload входа/refresh, новая `AccountPage`
(`/account`), доказывающая механизм, и Docusaurus с
`i18n.defaultLocale: 'en'`/`locales: ['en', 'pt-BR']` — текущий снимок pt-BR
из `docs/` уже сохранён в
`website/i18n/pt-BR/docusaurus-plugin-content-docs/current/`. Волна 6b
(массовое извлечение интерфейса + перевод `docs/`) сильно продвинулась
2026-08-22, на четырёх параллельных фронтах — подробности каждого см. в CHANGELOG.md (Unreleased/
Документация), — но ЕЩЁ НЕ закрылась: не хватает
`docs/business-rules.md` (переведён только front-matter; тело, с
сотнями RN, по-прежнему на 100% на португальском — это самый большой файл всей
документации, и он растёт быстрее, чем его можно попутно перевести) и
остаточного среза меньших компонентов `.tsx`. Когда она по-настоящему закроется,
этот раздел получит итоговое резюме, а остальной CLAUDE.md (Stack,
«Documentação») будет полностью пересмотрен, чтобы зафиксировать английский как
настоящий основной язык.

- **Сгруппированная линейка вкладок**: 11 отдельных вкладок стали 6 наверху — Visão
  geral, **Agentes ▾** (Executores, Criativo, Chat, Insights), **Dev ▾**
  (Código, PRs, Aprovações), **Documentação ▾** (Backlog, Arquitetura),
  Gastos, Configurações — через новый `GroupedTabs` (`apps/web/src/components/
  ui/GroupedTabs.tsx`), построенный ПОВЕРХ общего `Tabs`, который
  остаётся без групп для других экранов. `ChaveDeAba` остаётся плоским — сгруппировано
  только представление, чтобы не трогать deep-link `?tab=`. Chat и
  Chat RAG стали ОДНОЙ вкладкой (`ProjectChatShell.tsx`) с внутренним
  сегментированным управлением («Conversar»/«Buscar») — бизнес-различие между ними
  (RN-202: разговор активирует агента и тратит ключ владельца за ход; RAG —
  чтение по индексу, без агента) не изменилось, изменился только UI-контейнер.
- **Вкладка PR, на уровне проекта**: `ProjectApprovalsTab` ограничивал «PRs em
  revisão» самой свежей сессией — ревью PR из предыдущей сессии

## Ручной handoff выбранному агенту (RN-440/441, ADR 0109) {#handoff-manual-a-agente-à-escolha-rn-440441-adr-0109}

уже существующая карточка принятия (`SessionPage.tsx`) подхватывает его сама, ноль

`SOLO_CONVERSATIONAL_AGENTS` на стороне web (`apps/web/src/lib/agents.ts`)
НЕ сверяется тестом с зеркалом api — расхождение даёт в худшем случае
устаревший вариант в селекторе, который backend всё равно отклоняет с 400.

## Бюджет по области — закрывает отсечение ADR 0038 (RN-443, ADR 0110) {#budget-por-área--fecha-o-corte-do-adr-0038-rn-443-adr-0110}

## Автономный бинарник runner-а (2026-08-23, RN-451/452, ADR 0112) {#binário-standalone-do-runner-2026-08-23-rn-451452-adr-0112}
Пункт backlog ADR 0104 («standalone binary, `pkg`/`bun build
--compile`»), спутник ADR 0106 (распространение через npm). Явное решение
владельца продукта: по-настоящему ЕДИНЫЙ бинарник, полная матрица
с Windows с v1 — более дешёвая альтернатива («бинарник + папка
`node-pty-native/` рядом») была предложена и отклонена.

`bun build --compile` встраивает нативный `.node` из `node-pty` через
`with { type: 'file' }` и извлекает его в НАСТОЯЩИЙ ВРЕМЕННЫЙ каталог в
runtime (`native-pty-loader.ts`) — необходимо, потому что `node-pty` разрешает
собственный addon через `require()` по ВЫЧИСЛЯЕМОМУ пути
(`lib/utils.js#loadNativeModule`), который Bun не умеет встроить сам
(build проходит, runtime выбрасывает `Cannot find module`, протестировано до
проектирования исправления). Пять платформ
(`linux-x64`/`linux-arm64`/`darwin-x64`/`darwin-arm64`/`win32-x64`), каждая
собрана на своём НАТИВНОМ runner-е
(`.github/workflows/build-runner-binaries.yml`, триггер финального тега,
тот же шаблон, что `publish-runner.yml`), бинарник прикреплён к уже
существующему Release.

**Честная проверка, по платформам**: только `linux-x64` был действительно
выполнен в этой среде (`build:bin`+`smoke:bin` зелёные, многократно —
именно при запуске настоящего бинарника проявились два бага ниже). Остальные
четыре — особенно Windows, с ТРЕМЯ нативными файлами вместо одного —
были продуманы чтением исходного кода `node-pty`, ни разу не выполненные
на реальной машине той ОС; их первое настоящее выполнение — СЛЕДУЮЩИЙ
тег версии, а не этот PR. Ни один платформенный fallback не был применён
превентивно — ничто в этом расследовании не ДОКАЗАЛО, что какая-либо из пяти не
работает так; если настоящий тег покажет, что да, это станет новым пунктом, а не
сегодняшним предположением.

Два дефекта, найденные только запуском скомпилированного бинарника, а не чтением API:
`--external node-pty` должен быть в команде `bun build`, даже при отсутствии
какого-либо статического `import` `node-pty` в коде — fallback `await import(...)`
(используемый только вне бинарника) всё равно обнаруживается и встраивается Bun
и падает в runtime с обманчивой ошибкой; и защите
автозапуска (ADR 0106) понадобилась вторая ветка — `process.argv[1]` внутри
бинарника — ВИРТУАЛЬНЫЙ путь (`/$bunfs/root/...`), до которого `realpathSync`
не дотягивается, выбрасывая `ENOENT` вне любого `try/catch` до того, как
`main()` будет вызван.

## Конвертация execution_mode существующего проекта (RN-447..450, ADR 0111) {#converter-execution_mode-de-projeto-existente-rn-447450-adr-0111}
Закрывает исправление, которое Волна 1 runner-а (ADR 0104) зафиксировала в
`docs/explanation/backlog.md`: пункт 4 того ADR говорил, что конвертация
`execution_mode` между `container`/`mounted`/`runner` в уже существующем проекте
«становится разрешённой без пересоздания проекта», и до сих пор это было ложью —
`UpdateProjectDto` по-прежнему намеренно исключает оба поля.
`PUT projects/:projectId/execution-mode` (`maintainer`,
`ConvertProjectExecutionModeUseCase`) — ВЫДЕЛЕННЫЙ маршрут, а не ослабленный
`PATCH`: он оркестрирует миграцию, а не просто меняет столбец.

Отказывает с 409, пока любой dev agent проекта (в ЛЮБОЙ сессии,
прочитанный напрямую из `engine.dev_agent_states` по `project_id`, тот же путь, что у
RN-409) не находится в `idle` — `idle_tripped` здесь СЧИТАЕТСЯ активным, в
отличие от критерия «онлайн» RN-409, потому что у агента ещё есть
`workspace_root`, захваченный в памяти в ожидании человеческой разблокировки
(RN-447). `PermissionsFileStore` получил `move(from, to)`: содержимое
permissions.json никогда не меняется, меняется только физический путь, потому что `projectScopeRoot`
выводится из пары (режим, путь) (RN-448). При выходе из `container` с
подготовленным контейнером жизненный цикл (ADR 0081) доводится до `removed` — через
`stopped` сначала, если был `running`, — ДО изменения столбца, потому что
`RegistrarTransicaoDeContainerUseCase` отклоняет переход вне режима
`container`; вход В `container` никогда не готовит автоматически (RN-449).
`workspaceVerifiedAt` обнуляется при каждой настоящей конвертации, в том числе при возврате в
`runner` с внешне одинаковым путём (RN-450). Та же (режим, путь), что и
сегодня, — no-op, даже не проверяет активного dev agent.

**Объявленное, не скрытое следствие**: конвертация НИКОГДА не копирует
уже написанный код между старым и новым корнем. Это безопасно для того, что уже
ЗАКОММИЧЕНО — engine выводит worktree из bare-репозитория с нуля
(`Engine.Actions.Workspace.ensure!/4`) всякий раз, когда папка назначения ещё
не помечена готовой, поэтому следующий агент перестраивает рабочее
дерево в новом корне из настоящего git. Что НЕ выживает — это
НЕзакоммиченный diff в брошенном worktree: он остаётся сиротой на старом диске,
никогда не мигрируемый и не удаляемый. Предел активного dev agent (RN-447) снижает
риск (никогда не конвертирует при агенте `working`), но не устраняет: агент
`idle` между tasks может сидеть на грязном diff, и ничто здесь
не проверяет чистоту рабочего дерева перед конвертацией.

## Локальная папка, прикреплённая как справочник Chat RAG (2026-08-23, RN-455..457, ADR 0113) {#pasta-local-anexada-como-referência-do-chat-rag-2026-08-23-rn-455457-adr-0113}
Запрос владельца продукта: прикрепить папку СОБСТВЕННОЙ машины пользователя к
проекту как справочник ДЛЯ ЧТЕНИЯ агентами — без CLI
`brabo-runner` (ADR 0103). Явно НЕ является выполнением/workspace
проекта: `execution_mode: runner` (ADR 0104) нужен CLI, потому что нужен
настоящий путь ХОСТА, чтобы контейнер маршрутизировал команду; это больше
похоже на «прикрепить файлы к разговору». Браузер читает СОДЕРЖИМОЕ
(`File.text()`) и ОТНОСИТЕЛЬНЫЙ путь (`File.webkitRelativePath`)
выбранных файлов — никогда абсолютный путь хоста (API `File`
не открывает его ни одному сайту), и поэтому ADR 0113 прямо говорит, что это НЕ
пересмотр того, что отклонили ADR 0072/0107: те отклоняли
РАЗРЕШЕНИЕ пути хоста из браузера; здесь не существует никакого пути
для разрешения, только байты, которые браузер уже имел право читать.

`chunks.scope` (ADR 0079/0080) получает ЧЕТВЁРТОЕ значение, `'local'` (миграция
`0052`, `ALTER TYPE ... ADD VALUE`, добавочное — оба CHECK миграции
`0045` уже записаны как «это `session` или нет», поэтому `local` попадает на
ту же сторону, что `docs`/`adr`, без нового CHECK). `IndexLocalFolderUseCase`
близко отражает `IndexProjectDocsUseCase` — Markdown-aware чанкинг для
`.md`/`.mdx`, `RagEmbeddingService`, чанк без вектора вместо падения,
когда embedding отваливается (RN-233), — но ОТКЛОНЯЕТ (400) всю загрузку,
когда АГРЕГИРОВАННЫЕ пределы превышены (количество файлов, суммарные
байты), никогда не обрезает молча: это ЕДИНИЧНЫЙ жест пользователя с
селектором папки на экране, а не фоновое сканирование. Отдельный слишком большой файл
или файл с нераспознанным расширением лишь ПРОПУСКАЕТСЯ
(`filesSkipped`), никогда не роняет партию (RN-456). `origemDoChunk` не
понадобилась никакая новая ветка: `local` несёт `sourcePath`, как
`docs`/`adr`, и попадает в `kind: 'file'`, который цитирование уже умело отображать.

**Никогда не входит в общее «Reindexar agora» (RN-457)**: `ReindexProjectUseCase`
переиндексирует, читая из источника, который СЕРВЕР может снова посетить (репозиторий
проекта, event log); у `local` нет никакого источника для повторного посещения —
текст существует только в браузере того, кто прикрепил. Повторное прикрепление папки (новая
загрузка в `POST .../rag/local`, `maintainer`) И ЕСТЬ механизм
повторной синхронизации, намеренно отдельная кнопка, с перекрёстным комментарием
в обоих вариантах использования, указывающим друг на друга и на ADR 0113, чтобы будущее
«исправление» не связало их снова и не стёрло материал пользователя.
Покрытие (`RagCoverage.local`) — СОБСТВЕННОЙ формы — нет «итога в
репозитории» для сравнения — и `lastAttachedAt` — ЕДИНСТВЕННОЕ настоящее исключение из
правила «никогда X мин» (RN-237): настоящий `MAX(chunks.created_at)`, а не
угаданный (RN-458).

## Полоса активности хода — нить получает ответ только в конце (RN-459/460) {#faixa-de-atividade-do-turno--o-fio-só-recebe-a-resposta-no-fim-rn-459460}

Запрос владельца продукта: экран Сессии теперь показывает НАД
composer полосу, которая человеческим языком рассказывает, что разговорный агент
(Criativo, PO, Arquiteto, Dev Lead, UX Designer, Staff)
делает ВО ВРЕМЯ хода — визуальный эталон: строка статуса
Claude Code. Нить получает пузырь ответа только ПОСЛЕ того, как ход
заканчивается; правило относится к ЧАТУ (канал Phoenix) и действует только для шести
разговорных агентов — консультативный чат без активного агента (SSE,
`streamChatMessage`) остаётся с привычным потоковым пузырём,
нетронутым.

**Механизм**: шесть серверов уже выдавали ДОЛГОВЕЧНЫЙ `tool.call`; теперь они
также делают `broadcast(state, "tool.call", %{tool: name, agent: @agent})` —
ЭФЕМЕРНЫЙ, без `args` (RN-096/RN-412), — чтобы канал доставлял в реальном времени.
Нет общего behaviour/макроса между шестью `dispatch_tool`
(четыре разные структурные формы, подтверждено полным чтением) —
изменение — шесть правок, приспособленных к локальной форме каждого, а не
рефакторинг. На стороне web ЧИСТЫЙ reducer
(`reduzirAtividadeDoTurno`/`lib/atividade-do-turno.ts`) накапливает
`agent.delta` как текущий текст; при приходе `tool.call` архивирует
непустой текущий как строку повествования, обнуляет и всегда добавляет
строку инструмента с `fraseDaFerramenta(tool)` (словарь 19
инструментов, `lib/narracao-de-ferramentas.ts`, без собственной RN). СОБСТВЕННЫЙ
флаг (`turnoViaCanal`, никогда не выводимый из `statusAgent`/`streamingAgent`,
которые законно проходят через окна `null` посреди хода) решает, появляется ли
полоса или старый пузырь — никогда оба.

**Правило представления (история)**: `agruparNarracoesDoTurno`, новый
чистый проход после `afundarDesfechos` (RN-172) в том же `useMemo` —
последовательные `agent.response` одного `turno`+`autor` становятся компактным
`Disclosure` («Passos do turno · N»), только последний остаётся нетронутым
вне его. `turno === 0` (сторожевой пролог `turnoDoSeq`) остаётся
ВНЕ группировки — старые fixtures складывают `agent.response` без
границы хода, чтобы тестировать другой механизм (RN-138/RN-177), и без
исключения новая группировка дала бы там `Disclosure` внутри
`Disclosure`. Сам `afundarDesfechos` не изменился.

**Находка по пути, объём расширен по решению владельца продукта**:
расследование выяснило, что ЧЕТЫРЕ из шести серверов (Arquiteto, Dev Lead, UX
Designer, Staff) заканчивали МОЛЧА на пределе итераций —
`defp run_turn(state, remaining) when remaining <= 0, do: state`, без
какого-либо события, вопреки постоянному правилу, что цикл агента не
заканчивается молча. Только PO уже выдавал `toolloop.limit_reached` (RN-166);

### Handoff Infra нельзя было принять ни на одном экране (D0) (RN-499) {#o-handoff-da-infra-podia-ser-aceito-por-tela-nenhuma-d0-rn-499}

### Единая база смонтированных проектов (PR 1, BREAKING) (ADR 0141, RN-500) {#a-base-única-dos-projetos-montados-pr-1-breaking-adr-0141-rn-500}
Создание проекта `mounted` требовало строки bind-mount, написанной ВРУЧНУЮ в `api`
И `engine`, плюс перезапуска обоих — что убивает каждый ход агента, сокет
терминала и вызов LLM в полёте во всей установке, ради подключения ОДНОГО проекта.
Рождается `BRABO_PROJECTS_BASE`: ОДНА база, настраиваемая оператором один раз,
монтируемая по ИДЕНТИЧНОСТИ (`$X:$X`) в обоих сервисах, со всеми смонтированными
проектами внутри неё и НИЧЕГО не редактируется по проекту. Идентичность, а не фиксированная
точка монтирования, потому что `workspace_path` набирается пользователем и показывается ему обратно
— и это то, что позволяет `projectScopeRoot`/`workspace_dir/2` оставаться верными без
нового кода. СОБСТВЕННАЯ переменная (коллизия пространства имён с UNIQUE `workspace_dir_name`
привела бы к `git init` в папке другого проекта; противоположный владелец; база
навигируема, а управляемый корень не должен быть таковым). ОТСУТСТВИЕ — норма: `projectsBase:
null` (`GET workspaces/:id/projects-base`, `maintainer`), и режим не
предлагается. И `pnpm dev` ОТКАЗЫВАЕТСЯ стартовать при базе, пересекающейся с checkout-ом, —
единственная возможная проверка, потому что api сравнивает с `/workspace`. Две объявленные
цены: symlink под базой и только одна база

### Контейнер смонтированного проекта (PR 3) (ADR 0144, RN-503) {#container-de-projeto-montado-pr-3-adr-0144-rn-503}
Проект `mounted` не мог получить НИКАКОГО контейнера из-за двух независимых
блокировок — api отправляла каждый не-`container` режим в RUNNER (который требует
подключённого `brabo-runner`), а broker отклонял не-`container` в источнике. Обе
касались ГЕОМЕТРИИ, а не имени режима, и единая база ADR
0141 изменила геометрию. Ветвление становится по НАЗНАЧЕНИЮ: `container` И
`mounted` → broker, только `runner` → runner (и `container_stop`/`_remove` меняются
ВМЕСТЕ с `_start`, иначе поднимется на сервере и остановится на машине пользователя).
Инвариант ADR 0130 не сдвигается — ни один абсолютный путь не пересекает сеть:
broker получает ВТОРОЙ корень (`BRABO_PROJECTS_HOST_BASE`), а api отправляет
РАЗЛИЧЁННЫЙ локатор (`gerenciada` \|`montada` \|`indisponivel`), говорящий,
относительно какого корня действует относительный сегмент. ТРИ варианта, потому что
у `indisponivel` два разных исправления (`runner` × устаревший `mounted` вне
базы), и недостающий корень НИКОГДА не подменяется другим. `mounted` ВЫБИРАЕТ
образ, как `container`, — broker составляет из `artifact.project_image`, поэтому
незаписанный выбор — инертный выбор (ADR 0133 во втором режиме)

### Dev-агенты только после контейнера (PR 7) (ADR 0143, RN-502) {#agentes-de-dev-só-depois-do-container-pr-7-adr-0143-rn-502}
В реальном выполнении `exp001` ДЕСЯТЬ dev-tasks застряли разом — и
находкой была не упавшая папка, а то, что **ничто не упорядочивало контейнер до
dev agent**. `Engine.Dev.AgentIo.try_claim/2` — ЕДИНСТВЕННАЯ точка claim — начинает
запрашивать `ProjectContainerLifecycle.running?/1` (предикат, который ADR 0134
уже имел) ДО вызова api: без ЗАРЕГИСТРИРОВАННОЙ строки `running` агент падает
в `:idle`, сохраняется и выдаёт `dev.blocked_by_container`. В ENGINE, а не только в
`activate-execution` api, потому что РЕГИДРАТАЦИЯ доходит до `try_claim/2`, не
проходя ни через какой маршрут (`init/1` → `finish_restart_recovery/1`). `:idle`, а
НЕ новый статус, по причине, которую сам docblock `try_claim/2` уже
записывал с Фазы 12b, — это единственное состояние, из которого wake ещё спасает,
и все guard-ы `handle_info/2` на это опираются; «пустую
очередь» от «нет контейнера» отличает СОБЫТИЕ, никогда статус. Wake приходит через outbox:
`RegistrarTransicaoDeContainerUseCase` публикует `container.running` в ТОЙ ЖЕ
транзакции, которая записывает приход в `running`, в НОВОМ `aggregate_type`
(`container`, третий, который читает `Engine.Outbox.Drain`), вместо того чтобы одалживать `task`,
с ПРОЕКТОМ как `aggregateId`; доставляемое сообщение — уже существовавшее `{:wake,
:became_claimable}`. Вторая половина: `TerminalExecutor` перестаёт
молча деградировать — `container` без `running` падал в `System.cmd` ВНУТРИ
процесса engine, а теперь ОТКАЗЫВАЕТ, с `mounted` в той же ветке

### Docker становится настоящей предпосылкой режима Runner (RN-507/508, ADR 0145) {#docker-vira-pré-requisito-real-do-modo-runner-rn-507508-adr-0145}
`runner` маршрутизировал каждый одобренный терминал в CLI, как только проверенный workspace
+ подключённый runner совпадали, без проверки контейнера `running` — без запущенного Docker
runner сам падал в чистый ХОСТ, ТОТ ЖЕ молчаливый откат, который ADR 0143
уже закрыл для `container`/`mounted`. `Engine.Runners.RunnerReadiness`
объединяет ТРИ предусловия (проверен, подключён, контейнер `running`) с
двумя потребителями: `TerminalExecutor` и материализацией worktree dev
agent, которая перестаёт пытаться делать ЛОКАЛЬНЫЕ `File.mkdir_p!`/`git init` против пути
ХОСТА (пробел, открытый с RN-478) и начинает работать ВНУТРИ настоящего
контейнера, на машине пользователя, через ТОТ ЖЕ канал `exec`/`exec_result`
(`Engine.Actions.Workspace.RunnerGit`, новый) — `WorktreeManager` разветвляется по
тому же критерию, а периодический job очистки молча ПРОПУСКАЕТ проект
`runner` без готового сейчас runner-а. Протокол `exec` получает опциональный `env`, чтобы
учётные данные git (ADR 0056) передавались в окружении дочернего процесса ХОСТА —
слитые поверх `process.env`, никогда не передаваемые в `docker exec` и не логируемые.
`container_start` перестаёт обслуживать `runner` (его payload, с выбором
образа, там никогда не имел смысла); рождается `container_start_via_runner` — схема
только с `rationale`, поднимает уже решённый образ, — а новый инструмент Infra Lead
ЛОКАЛЬНО отказывает (без HTTP), вместо того чтобы предлагать вслепую

### ФАЗА 28 (сессия 5) — `join` локального агента перестаёт быть немым (RN-514, ADR 0147, пункт 1) {#fase-28-sessão-5--o-join-do-agente-local-deixa-de-ser-mudo-rn-514-adr-0147-ponto-1}
`join` канала `terminal:<projectId>` был немым с ОБЕИХ сторон — runner
отправлял `{}`, а сервер делал `_params`, — поэтому у сервера не было способа
узнать, понимает ли бинарник на другой стороне новое сообщение, и дефект был
наихудшим из возможных: сообщение приходит, обработчика нет, и НИЧЕГО не происходит, без
ошибки и без лога. Теперь runner ОБЪЯВЛЯЕТ в params
(`Engine.Runners.Capacidades`, словарь `exec`/`pty`/`espelho`), а
сервер ПРЕДОСТАВЛЯЕТ пересечение с тем, что ЗНАЕТ, в `socket.assigns` и НИКОГДА
в таблице (способность — свойство этого ПОДКЛЮЧЕНИЯ). Runner объявляет только
`exec` и `pty` — объявить `espelho`, не реализовав его, — ровно тот дефект,
который предотвращает согласование; он входит как ИМЯ словаря и не более, а
сессия 6 его реализует. Отсутствующие/пустые params — это УСТАРЕВШИЙ бинарник, и они предоставляют
`{exec, pty}` — ФАКТ, а не благосклонность: это две функции, с которыми runner
родился, а отклонение устаревшего было бы `breaking/` и MAJOR. Неизвестное ИГНОРИРУЕТСЯ
(runner НОВЕЕ engine подключается); требуемое-но-не-объявленное отклоняет join,
НАЗЫВАЯ недостающее, ДО `Registry` — механизм реализован и протестирован,
но сегодня НЕ срабатывает (`runner` требует `exec`, который есть у каждого бинарника; ничто пока не требует
`espelho`), и таков замысел. Половина, приносящая пользу СЕГОДНЯ:
сообщение без способности ОТКЛОНЯЕТСЯ с именованным ответом — `exec` отвечает в
формате `exec_result` (126 + причина), вместо того чтобы `RunnerRouter` ждал
timeout, а `pty_*` становится `pty_error` во вкладке вместо исчезновения. `RunnerReadiness`
байт в байт как есть

### ФАЗА 28 (сессия 6, половина B) — зеркало начинает существовать (RN-516, ADR 0147, пункты 2/3/4/8) {#fase-28-sessão-6-metade-b--o-espelho-passa-a-existir-rn-516-adr-0147-pontos-2348}
Способность `espelho` выходит из имени словаря и становится кодом с ОБЕИХ
сторон. НАЗНАЧЕНИЕ передаётся в ПРЕДОСТАВЛЕНИИ `join` (ответ перестаёт быть пустым
для `:runner`: `%{espelho: %{destino: ...}}`), живёт только в этом подключении, и
runner ОТКЛОНЯЕТ `mirror_sync` для непредоставленного назначения — никогда глобальная
конфигурация или переменная, из-за которой артефакт проекта B приземлился бы в папке
A. Непустой `mirror_path` начинает ТРЕБОВАТЬ способность, и это ПЕРВОЕ
настоящее срабатывание механизма отказа RN-514: старый бинарник в проекте с
назначением ПЕРЕСТАЁТ подключаться, именованно и фатально — opt-in, цена объявлена в ADR.
`espelho-guard.ts` рождается РОДСТВЕННИКОМ `guard.ts` (переиспользует три helper-а и двойной
проход, письменно наследует оговорку о TOCTOU) и отклоняет три вещи
ADR; находка при реализации: `realpathMaisProximo` падает к предку, а поскольку
назначение почти никогда не существует, схлопывание обеих сторон превратило бы `/base-outra` и
`/base` в `/` — второй проход разрешает предка и ВОЗВРАЩАЕТ
суффикс. ОДНО направление и НИКОГДА не удаляет: файл, удалённый в источнике, ОСТАЁТСЯ в
назначении (папка пользователя — накопление, а не реплика). Копируется СПИСОК
GIT (отслеживаемые + неотслеживаемые-неигнорируемые), без собственного списка
исключений; падающий git становится ИМЕНОВАННОЙ ошибкой, никогда `cp -r` как план Б; вложенный
git-репозиторий (worktree dev agent) возвращается как ОДНА запись и не обходится вглубь, а
symlink источника пропускается. СОБСТВЕННЫЙ предикат (`Engine.Runners.Espelho`), ДВА
предусловия и НИКОГДА `RunnerReadiness` с флагом — `runner_readiness.ex` остаётся
байт в байт. Триггер: COMMIT, именованный момент, fire-and-forget и никогда не
watcher; «конец хода агента» остаётся ОБЪЯВЛЕННЫМ и не подключённым, поскольку нет
однозначной зацепки

### Broker, который никогда не поднимался (исправление RN-512) (RN-512, ADR 0130/0146) {#o-broker-que-nunca-subiu-correção-da-rn-512-rn-512-adr-01300146}
RN-512 убрала broker из `profiles`, чтобы он был запущен в dev, и он НИКОГДА не
поднимался: `corepack prepare` выполнялся от ROOT при build (кеш в `/root/.cache`),
контейнер работает как uid 1000, а без кеша corepack пытается СКАЧАТЬ pnpm в
сервисе, чья единственная сеть — `internal: true`, — `EAI_AGAIN registry.npmjs.org`,
`Exited (1)` через пять секунд. Без healthcheck `up --wait` говорил
`Healthy`, а полный сброс объявлял «reset completo» с мёртвым процессом;
пока существовал profile, broker поднимал тот, кто уже на него смотрел.
Исправление убирает registry из RUNTIME и НЕ открывает сеть (первый из пяти
слоёв ADR 0130): `COREPACK_HOME`, подготовленный при build с владельцем uid
runtime, `pnpm install` как шаг BUILD, и — поскольку три тома
`node_modules` перекрывают то, что установил образ, а Docker заполняет только ПУСТОЙ
том, — entrypoint, сверяющий их с копией вне `/workspace`,
помеченной sha256 lockfile из build (та же метка ПРЕДУПРЕЖДАЕТ, что образ
отстал, не отказываясь стартовать). Healthcheck в сервисе, изнутри
контейнера. Production от этого не страдал и не меняется


### ФАЗА 28 (сессия 7) — локальный агент становится пользовательской службой (RN-518, ADR 0147, пункт 5) {#fase-28-sessão-7--o-agente-local-vira-serviço-de-usuário-rn-518-adr-0147-ponto-5}
`brabo-runner service install|uninstall|status`, и прецедент был НУЛЕВЫМ
(ни одного упоминания `systemd`/`launchd` в `apps/runner/`; моделью был
foreground, убиваемый SIGINT). Всегда уровень ПОЛЬЗОВАТЕЛЯ — `systemd
--user`/`LaunchAgent`, — а root — это ОТКАЗ, а не предупреждение: docblock `guard.ts`
объявляет «работает с ЕГО привилегиями» предпосылкой трёх настоящих
границ, а root-служба оставила бы best-effort защиту `cwd` единственной
преградой между одобренной командой и диском. Windows — ИМЕНОВАННЫЙ отказ (третий
механизм, а не вариация двух). Один unit на ПРОЕКТ, потому что сервер уже
навязывает один runner на проект — именование по папке создало бы два unit-а, которые никогда
не поднимутся вместе, и второй проявился бы как сбой подключения, а не как ошибка
установки; в Linux файл идёт туда, где systemd ИЩЕТ
(`$XDG_CONFIG_HOME/systemd/user`, иначе `~/.config`). `Restart=on-abnormal` и
НИКОГДА `on-failure` (в plist — `KeepAlive`/`Crashed`): exit 1 runner-а — это
фатальный отказ join (RN-514) или исчерпанный предел попыток, и перезапуск
был бы циклом, от которого CLI отказывается сам. Служба аутентифицируется КЛЮЧОМ
УСТРОЙСТВА и никогда токеном — запись его в unit оставила бы его на диске, а этот
CLI никогда не записывал учётные данные на диск. `uninstall` удаляет ВСЕ ТРИ, читая папку

### ФАЗА 29 (сессия 2) — конвейер подписывает то, что публикует (RN-524, ADR 0149) {#fase-29-sessão-2--a-esteira-assina-o-que-publica-rn-524-adr-0149}
Продукт не подписывал **ничего**: `cosign`/`sigstore`/`attestation` не существовали в
`.github/`, `scripts/` или `docker/`, а единственным происхождением был
`--provenance` **npm**-пакета runner-а. `release.yml` публиковал четыре
образа **без** `id-token: write`; `build-runner-binaries.yml` загружал пять
бинарников через `gh release upload` и ничего больше — тогда как уже существовавшие
`sha256sum -c` проверяют **сторонние** бинарники, шаблон, который репозиторий
умел применять и никогда не применял к самому себе. Теперь образы подписываются по
**DIGEST** (никогда по тегу, подвижному указателю), а бинарники получают **ОДИН**
подписанный `checksums.txt`, в job-е `checksums`, который ждёт матрицу, — а не пять
подписей, потому что тот, кто проверяет четыре и забывает пятую, не знает, что
забыл. Job намеренно `if: always()` (`fail-fast: false` в матрице) и
**называет то, что манифест не покрывает**. Оба workflow **проверяют перед
публикацией**. Keyless по истории дома: приватный ключ был бы ещё одним
секретом CI, а PAT уже однажды молча истёк (ADR 0139). Процедура
проверки — в runbook, с двумя **обязательными** флагами `--certificate-*` —
без них `cosign` принимает действительную подпись ОТ КОГО УГОДНО. Закрывает BRB-005
для образов и бинарников; вне остаются, объявлено, code-signing ОС и
прокси загрузки

### ФАЗА 29 (сессия 3) — установщик, который ещё не устанавливает (RN-526, ADR 0150) {#fase-29-sessão-3--o-instalador-que-ainda-não-instala-rn-526-adr-0150}
Рождается `install.sh` в КОРНЕ, версионируемый и раздаваемый через Release. Форма — `sh -c "$(curl …)"` и **никогда** `curl|sh`, по МЕХАНИЧЕСКОЙ причине: с pipe
`stdin` процесса ЯВЛЯЕТСЯ загрузкой, и каждый `read` читает байты самого скрипта или
находит EOF — установщик, который не спрашивает, сам выбирал бы, где создавать папку
на чьей-то машине. Он ПРОВЕРЯЕТ СОБСТВЕННОЕ ПРОИСХОЖДЕНИЕ (подпись
`checksums.txt` из RN-524 и свой хеш ВНУТРИ проверенного манифеста), с
закреплённым `cosign`, сверяемым через `sha256sum` с хешем, записанным в скрипте;
ОБНАРУЖЕНИЕ называет найденное, прежде чем спрашивать; без TTY сообщает и выходит с 0; и
**никогда не удаляет папку пользователя** — база проектов и папка зеркала остаются
вне любого подтверждения, по линейке зеркала (RN-516). Маркер в
`$XDG_STATE_HOME/brabo/`, никогда в `~/.brabo/`, который ПО ПРОЕКТУ. **В этой версии
ничего не устанавливает, и ГОВОРИТ об этом**, вместо того чтобы молча закончить.
`--print-plan`/`--print-state` раскрывают решение без TTY, без сети и без эффекта
— по образцу `--print-commands` из `bootstrap.sh`, тестируемые так же. Два бага
bash, найденные при запуске, оба одного рода: под `set -e`+`pipefail`, `[
cond ] && atribuição`, дающее ложь, УБИВАЕТ скрипт, а несовпавший `ls`
роняет всю подстановку — в функции, чей нормальный случай — «ничего
не нашёл». КОРЕНЬ репозитория не покрывался ни одним docmap (glob-ы
корня — буквальные имена); рождается правило `instalador`

### ФАЗА 29 (сессия 4) — установка поднимается из собственного compose (RN-527, ADR 0150) {#fase-29-sessão-4--a-instalação-sobe-de-um-compose-próprio-rn-527-adr-0150}

### ФАЗА 29 (сессия 6) — миграция требует ДОКАЗАННОГО бэкапа (RN-530, ADR 0150/0152) {#fase-29-sessão-6--migrar-exige-backup-provado-rn-530-adr-01500152}

ПЕРЕИСПОЛЬЗУЕТ уже существовавший `workspace_confirm`, и именно это экономит целый
фронт: **не рождается ни одного нового маршрута записи**, engine по-прежнему не
пишет таблицу, а единственный путь, штампующий `workspace_verified_at`,
остаётся единственным — с ПОРЯДКОМ как механизмом (confirm ДО результата,
потому что оба приходят в один процесс канала по порядку, а обработчик
confirm синхронный). Способность `workspace` входит в словарь В ТОЙ СЕССИИ,
В КОТОРОЙ ВХОДИТ КОД, с обеих сторон — RN-514 сделала противоположную ставку с
`espelho`, и она окупилась лишь потому, что кто-то её востребовал, — и это ЕДИНСТВЕННАЯ из
четырёх, чьё объявление зависит от СОСТОЯНИЯ данного выполнения: runner
объявляет её только при согласованной базе, и именно по этой строке и ни по какой другой
сервер ЗНАЕТ, что база существует (engine не читает диск пользователя). НИКТО её
не требует в join, намеренно: требование её в `runner` было бы `breaking/` и MAJOR
ради функции, которую этот проект, возможно, никогда не использует. СОБСТВЕННЫЙ предикат
(`Engine.Runners.PastaDoProjeto`), ДВА предусловия, `RunnerReadiness` байт
в байт — и здесь третье было бы хуже, чем ненужным, оно было бы ЦИКЛИЧЕСКИМ:
проект `runner` доходит до контейнера `running` только после того, как runner его
поднимет, а контейнер поднимается поверх папки, для создания которой существует это сообщение.
Он также не спрашивает `workspace_verified_at` (здесь это РЕЗУЛЬТАТ) и
режим. ДВА предусловия отвечаются в разных местах, потому что «согласованная
база» — свойство ПОДКЛЮЧЕНИЯ (`socket.assigns`, никогда таблица): канал
отказывает ДО отправки, с `motivo: "sem-base"` по тому же `ref`, в
формате, которого ожидает модуль, — никогда timeout. Пять именованных причин, которые не
схлопываются, идемпотентность с СОБСТВЕННЫМ исходом (`ja-era-repositorio` — успех),
и `estado.dir` НЕ меняется. Это не `proposed_action`, и ни один предел не получает исключения

### ФАЗА 29 (сессия 5) — бэкап начинает покрывать то, что больно терять (ADR 0152, RN-528) {#fase-29-sessão-5--o-backup-passa-a-cobrir-o-que-perder-dói-adr-0152-rn-528}
Бэкап покрывал ОДНУ базу и работал в ОДНОМ месте: `make test-restore` — путь
Kubernetes (требует `kubectl`, кластер и CronJob), а в `docker-compose.prod.yml`
не было НИКАКОГО сервиса `backup` — у миграции установки через compose не было
доказанного пути. Решение начинается с ОТКАЗА от лёгкого хода («бэкап
всех томов») и с КЛАССИФИКАЦИИ семи: `neo4j_data` и
`project_workspaces` — производные, `ollama_data` — получаемый заново,
`brabo_projects_base` — пользовательский: их копирование создаёт впечатление покрытия, не
добавляя восстановления. Источников истины ДВА, и находка — второй:
**`git_local_repos` не входил ни в один бэкап**, а проект с provider-ом
`local` хранит там *bare* — он не восстанавливается из Postgres (event log
хранит ПОВЕСТВОВАНИЕ, а не объекты git), так что потерять том — значит потерять
код агентов. Проза runbook утверждала обратное («the real
repositories live in GitHub/GitLab»), и именно она объясняет годы без
покрытия: это верно для `github`/`gitlab`, а для `local` upstream нет.
Гарантия архива ОБЪЯВЛЕНА и меньше, чем «снимок», — согласованность по
ССЫЛКЕ (git пишет объекты до сдвига ref и меняет ref атомарным
rename), без глобального момента и без `git fsck` (в образе намеренно нет
git); конкурентный `gc` становится СБОЕМ, а не частичным архивом, со статусом
`tar`, захваченным в ФАЙЛ, потому что в POSIX `sh` статус конвейера — статус
последней команды. Пять переменных S3 перестают быть обязательными и становятся
конфигурацией ОДНОГО назначения (`BACKUP_DIR` выбирает диск; без неё — S3,
этот вывод и сохраняет CronJob НЕТРОНУТЫМ). `make test-restore-compose`
запускает НАСТОЯЩИЙ бэкап и вызывает ТОТ ЖЕ `brabo-restore` с ТЕМИ ЖЕ тремя
проверками: меняется ОБЁРТКА, никогда суждение, и
`deploy/k8s/test-restore.sh` остаётся НЕТРОНУТЫМ (объединение сделало бы вариант compose
зависимым от `kubectl`); `restore.sh` по-прежнему не трогает ИСХОДНУЮ базу.
Восстановление репозиториев — РОДСТВЕННАЯ команда (`brabo-restore-git`, по умолчанию проверяет,
пишет только с `--restaurar`), а не фаза другой — два артефакта, два
суждения, и их объединение заставило бы сбой git проваливать проверку event log.
Находка ПРИ ЗАПУСКЕ, которую чтение бы не дало: том разделяется тремя
образами с разными uid и несёт владельца того, кто смонтировал его первым (измерено
`1000:1000`, режим 0755), тогда как образ работает как uid 70 — извлечение
умирало посередине, оставляя том наполовину; теперь отказывает ДО `tar`,
называя `--user 0:0`, а извлечённое от root возвращается владельцу КАТАЛОГА,
иначе том вернулся бы целым и БЕСПОЛЕЗНЫМ (api и engine, non-root, не
могли бы писать в только что восстановленное). Neo4j получает ПЕРЕПРОЕКЦИЮ, а
не бэкап — здесь не построена (BRB-018): мигрированная установка рождается с
ПУСТЫМ графом, названная деградация, а не потеря данных (RAG живёт в pgvector,
внутри дампа)

### ФАЗА 30 — локальный агент машины (ADR 0154/0155, RN-543..552, закрывается в сессии 8 с RN-549) {#fase-30--o-agente-local-da-máquina-adrs-01540155-rn-543552-fecha-na-sessão-8-com-a-rn-549}
ФАЗА 29 сдала установку одной строкой и ОСТАНОВИЛАСЬ в двух пунктах, которые сам
продукт уже письменно объявлял: локальный агент оставался сопряжённым по
ПРОЕКТУ (кто хотел использовать установленный бинарник, возвращался в браузер, чтобы вставить
команду в терминал), и **никто не мог войти** — сгенерированный `.env` не
содержит переменной e-mail, `MAIL_TRANSPORT` падает в `log`, а регистрация требует
подтвердить e-mail, так что выходом было выуживать ссылку в `docker compose logs api`.
Оба решались в одном месте, и именно это сделало из них одну фазу. Находка, которая
определила её РАЗМЕР, пришла из повторного измерения с `arquivo:linha` утверждения ФАЗЫ
29 о том, что «один runner на проект навязан в пяти местах»: **три из
пяти не нужно было менять**, потому что топик, socket id и тикет описывают
ПОДКЛЮЧЕНИЕ, а процесс, открывающий N подключений — по одному на проект, — удовлетворяет им байт
в байт, сохраняя отказ второму runner-у в том же проекте, что является настоящей
гарантией, а не случайностью. **Ничто в engine не изменилось за всю фазу**, и это
сохранило `RunnerReadiness`, зеркало и `workspace_create` нетронутыми. Осталось
то, что принадлежит ПРОЦЕССУ: учётные данные (`runner_device_keys.project_id` становится
nullable, RN-543 — и список начинает возвращать ОБА помеченных вида,
иначе ключ машины был бы невидимым и постоянным — дефект, который закрыла RN-519,
возродившийся) и unit (RN-545, `service install --machine`, один на
машину, СОСУЩЕСТВУЮЩИЙ с unit-ами по проекту). Два решения противоречили букве
ADR, и оба были ИЗМЕРЕНЫ: дискриминатор unit — флаг `--machine`, а не
отсутствие `--project` (`resolverProjeto` имеет два источника, и обычный путь —
запуск `install` без флага изнутри папки, которую настроил браузер, — буквально
ADR молча сконвертировал бы установку того, кто уже пользуется продуктом), и
`install` ОТКАЗЫВАЕТ, когда другой вид уже установлен, без `--force`, потому что
оба вместе были бы двумя процессами, оспаривающими один проект. Сессия 6
затронула бы три workspace разом и была РАЗДЕЛЕНА на три, причём две
непересекающиеся части вышли раньше, а `install.sh` — после них, как оркестратор и ничего
больше. Из этого разделения вышел самый интересный пересмотр фазы: при НУЛЕ подключений
агент перестал ЗАВЕРШАТЬСЯ и начал ЖДАТЬ, повторно опрашивая через 15s/30s/60s
(RN-550) — аргумент RN-544 против повторного опроса остаётся целым там, где он
действует (список, вернувшийся МЕНЬШИМ, неоднозначен, а обрыв ЖИВОГО подключения из-за неоднозначности
меняет верное состояние на догадку), а при нуле подключений обрывать нечего;
пал аргумент про `exit 0` («активная служба, которая ничего не делает»),
потому что процесс начал что-то делать и ГОВОРИТЬ, что делает. Измерено: `Restart=on-abnormal`
**не смотрит на код выхода**, поэтому ни один unit не изменился, а эффект в том, что unit машины
становится действительно `active (running)`. Другая часть (RN-551) закрывает «никто не СОЗДАЁТ
ключ машины» со стороны агента, и решение там — ОТСЕЧЕНИЕ: CLI **не**
говорит с api, потому что регистрирует установщик с `BRABO_SERVICE_TOKEN`
— каждая сторона хранит секрет, и ни одна не видит секрета другой. Отсюда вытекает замысел
из двух шагов, а из него — инвариант: `kid` ЯВЛЯЕТСЯ id записи и существует только
после неё, поэтому `create` записывает `.parcial`, который читатель игнорирует, а
`finish` записывает настоящее имя — **файл, который читает runner, никогда не существует без
`kid`**, дефект RN-475, ставший невозможным по построению. Половина api
(RN-552) объявила цену, вместо того чтобы её скрыть: учётные данные — service token,
и утёкший токен начинает мочь ФАБРИКОВАТЬ долговременные учётные данные — поэтому три
сдерживания живут в МАРШРУТЕ, а не в тексте (в теле нет `userId`; регистрация
ЗАМЕНЯЕТ активные ключи машины владельца в той же транзакции, так что
переустановленная машина проходит, а тысяча ключей невозможна по клаузе, без числа, которое
устаревает; и JWK с `d` отклоняется по имени). Сессия 6 (RN-547) связала
пять команд цепочкой и закрепила три правила: упавшее среднее звено ничего не откатывает, становится
именованной строкой в финальном блоке, и скрипт ВСЕГДА завершается с 0 (откат потребовал бы удалить
учётную запись и отозвать ключ, а маршрута для этого нет, и не должно быть такого, который
установщик вызывает сам); идемпотентность — это HTTP-КОД, и `409` — ОЖИДАЕМЫЙ
исход, а не сбой, с `000`, обрабатываемым отдельно, чтобы «api не поднялась» не
читалось как «api отказала»; а пароль передаётся через STDIN `curl`, никогда через
`argv`, потому что `/proc/<pid>/cmdline` читаем любым пользователем машины.
Находка этой сессии: `--help` ЛГАЛ месяцами (*«ESTA VERSÃO NÃO INSTALA
NADA»*), потому что печатает заголовок, являющийся комментарием, а правило, запрещающее
говорить о «сессиях фазы», читало только строки кода. Сессия 7 (RN-548) дала
потребителя метке вида, и решение было о ЧЕСТНОСТИ: с ключом и без
живого подключения — самый частый случай — экран говорит две вещи, которые знает, и называет
две, которых не знает (*зарегистрированный ключ — не работающий агент*, *список — от вашей
УЧЁТНОЙ ЗАПИСИ, а не этого браузера*), тон `accent` и никогда `success`. Сессия 8
(RN-549) — единственная, которая могла доказать всё вместе, и она РАСШИРИЛА workflow, который
ФАЗА 29 уже имела, вместо создания второго. Её центральное решение — СИГНАЛ:
`perguntarEstado` отображает `activating` в `rodando` — обоснованно, — поэтому
`systemctl is-active` и `service status --machine` дали бы зелёный процессу,
который умрёт через две секунды; выбранный сигнал — СТРОКА, которую агент
пишет при входе в ожидание, которая существует только после того, как он прочитал ключ,
взял тикет, поговорил с api и получил ПУСТОЙ список, и которая — ЗАПИСАННЫЙ ФАКТ,
а не выборка состояния. Исход доказывается через API, а не через
браузер, потому что субъект утверждения — АГЕНТ, а то, что он наблюдает, —
`GET /runner/projects`; браузер создал бы проект через тот же маршрут с лишним
слоем, падающим по посторонним причинам, а утверждение по-прежнему было бы
строкой журнала. И E2E остаётся ВНЕ `pull_request`, со следствием,
объявленным, а не скрытым (**PR, который его написал, его не выполнил**): открыть
эту дверь — значит дать установщику способ пропустить проверку происхождения, что
отвергает ADR 0150, — отсюда половина, работающая в PR, — это ТЕСТ
(`scripts/dev/install-e2e.spec.ts`), охраняющий два способа, которыми workflow может
молча сгнить: ослабленный gate и переписанная фраза `install.sh` (из-за которой
утверждения не падают, а ИСЧЕЗАЮТ). Проявились два дефекта, оба
невидимые, потому что workflow никогда не запускался: ответы TTY начинались с
`nao-migrar`, что на чистой машине попадает на вопрос МАРКЕРА и заставляло
скрипт выходить с 0, говоря «Nada foi gravado»; и НАХОДКА, оставшаяся находкой, —
опубликованный `install.sh` **ничего сам не поднимает на чистой машине**, потому что
`docker/docker-compose.install.yml` (вместе с `./postgres/init.sql`) не является
asset-ом Release, не входит в подписанный `checksums.txt`, и он его нигде
не скачивает, так что тот, кто следует `curl … install.sh` из runbook, умирает на «no
such file or directory» ПОСЛЕ того, как уже проверил подпись и записал
`.env`. Исправление — решение между подписанным asset-ом и clone, и это отдельная сдача.
Что фаза оставила ОБЪЯВЛЕННЫМ и не сделанным: отзыв по-прежнему достигает
`{projeto, usuário}` и никогда `{chave}`, и теперь это стоит дороже (роняет агента во
ВСЕХ проектах этой машины); нет экрана, где перечислить и отозвать ключ
устройства, а фаза добавила вид для перечисления, не построив экран, —
пробел стал БОЛЬШЕ, намеренно; один процесс на машину — единая точка
отказа, цена замысла; и `install --machine` по-прежнему не знает, является ли ключ
этой папки действительно ключом машины, потому что на диске оба вида — один и тот же
файл, а знает это сервер

### Golden-set QA снова измеряет и запускается по расписанию, еженедельно (AT-076/AT-149, ADR 0168) {#o-golden-set-do-qa-volta-a-medir-e-roda-agendado-semanal-at-076at-149-adr-0168}

Две сдачи, одно человеческое решение между ними. AT-067 измерила, что
время укладывается в `ubuntu-latest` без GPU и что инструмент не измерял: начиная с
RN-502 `npm test` проекта `container` без контейнера `running`
отклоняется, а seed никогда его не поднимал — 0/6 по построению. Мейнтейнер выбрал
«путь 1», и AT-076 его сдала: seed поднимает контейнер каждого случая

ExUnit (раньше `{:skip, _}` из тела молча проходил зелёным). Два раунда в CI
дали 3/6 и 3/6 против пола 1/6, с разными случаями, за 52 и 86 min

`workflow_dispatch`, никогда `pull_request`), в `golden-set-qa.yml`, по образцу
`golden-set-rag.yml`. Еженедельно, а не еженощно, потому что раунд стоит до 86 min и
МЕНЯЕТСЯ — тот же итог по разным случаям, — и одного в неделю достаточно, чтобы пол
обнаружил падение. `timeout-minutes: 150` по худшему измеренному случаю. Вердикт —
вердикт самого теста; workflow добавляет лишь две защиты ИНСТРУМЕНТА (строка
счёта должна существовать, а в event log не может быть отказа RN-502) и, при
сбое, печатает логи, как у RAG, — без issue. Образ для pull до seed
ЧИТАЕТСЯ из константы seed, никогда из второго литерала, потому что `docker run`
broker-а работает под управляющим пределом 30 s (RN-604). Раунд доказательства, с

ноль отказов RN-502, 10 min `mix golden_set.qa` и 13 min 41 s
job-а. Объявлено: у broker-а CI нет пяти слоёв compose, heartbeat
закрывает сессии seed, пока QA ещё в них работает (без видимого
эффекта), а PR, затрагивающий workflow, его не выполняет.

### Infra Lead разговаривает через composer (AT-141, ADR 0175, RN-617) {#o-infra-lead-conversa-pelo-composer-at-141-adr-0175-rn-617}

RN-584 (AT-098) убрала получателя по умолчанию из чата и оставила продуктовый вопрос

### Аутентифицированный git выполняется на хосте runner-а, код — в контейнере (AT-116, ADR 0193, RN-676) {#o-git-credenciado-roda-no-host-do-runner-o-código-no-container-at-116-adr-0193-rn-676}

2026-10-01, раунд 36. RN-558 закрыла половину МОЛЧАНИЯ — аутентифицированный `git
fetch` в режиме `runner`, при запущенном контейнере, перестал выполняться с
пустыми переменными и стал отклоняться с меткой
`credencial-nao-atravessa-o-container`, — и объявила другую половину незакрытым
ADR, потому что каждый известный вариант затрагивал порт сдерживания ADR 0130.
Решение владельца (01.10) выбрало тот, что не затрагивает: git-операция с учётными данными
на ХОСТЕ, код в контейнере. Измерено заранее: единственный `exec` engine с `env`
был fetch из `RunnerGit.fetch!/3`; не было ни `push`, ни аутентифицированного `clone`
через `exec` (clone при создании папки уже выполнялся на хосте, RN-532); и папка —
одна и та же с обеих сторон (`estado.dir`, смонтированная в `/work`). Выбранный
дискриминатор — явная МЕТКА engine (`gitCredenciado: true`, ставится только
через `RunnerRouter.exec_git_credenciado/5`), а не уже существовавший `env` —
с `env` в роли ключа любая команда с `env` ускользнула бы из контейнера. Отказ
RN-558 выжил в уменьшенном виде, для `env` без метки, и на практике
стал означать «runner старше ADR 0193». Доказательство — AT-111, с обеих
сторон: в runner-е настоящие `git credential fill` и `git fetch origin` с
helper-ом `GitAuth` проходят на хосте при активном контейнере; в engine цепочка
через настоящий `TerminalChannel` заканчивается `{:ok, _}`. ExUnit не запускались в
среде сдачи (`repo.hex.pm` 403) и остались для CI.

### Консультативная сессия без агента просит агента (AT-254, RN-682) {#a-consultiva-sem-agente-pede-um-agente-at-254-rn-682}

2026-10-01, раунд 36. В реальном использовании 29.09 консультативная сессия без агента
ответила «у меня нет доступа к предыдущим разговорам»: сообщение без
получателя шло в SSE `POST .../chat`, который отправляет привязанной модели только
текущий текст — без истории, без системного промпта — и записывает ответ с
именем модели в качестве актора. Решение владельца (01.10) — просить агента, а не
давать историю свободному чату. Измерено заранее: экран был единственным клиентом
маршрута (`curl`, печатаемый seed-ом, — подсказка для разработки, в креативной
сессии), а у варианта использования `SendChatMessageUseCase` был второй
законный потребитель, smoke-тесты provider-ов, которые используют его как сквозной инструмент
в сессии без агента. Поэтому отказ api живёт в МАРШРУТЕ, в собственной
защите, а вариант использования остался нетронутым. На экране строка получателя стала
нести собственный селектор ручного handoff, когда агента нет, — тот же
привычный жест, теперь в том месте, где он — единственный способ дать сообщению
назначение, — а Criativo остался вне списка, потому что консультативная сессия обещает, что он
не войдёт.

### Отзыв нацелен на ключ, а не на пару `{projeto, usuário}` (AT-013, ADR 0201, RN-685) {#a-revogação-mira-a-chave-e-não-o-par-projeto-usuário-at-013-adr-0201-rn-685}

2026-10-01, раунд 36. RN-520 заставила отзыв достигать живого
подключения, с целью `{projeto, usuário}`, потому что идентичность учётных данных умирала
в `PatAuthGuard`; ADR 0154 поставил *«отзыв по ключу»* в список того, чего он не
делал, а PR #534 дал ключу машины ту же пару, применяемую проект за
проектом. AT-013 была заблокирована по объёму и по решению, пока владелец не
выбрал (01.10): по КЛЮЧУ, с ADR, затрагивая engine. Измерено заранее:
тикет рождался из `{userId, kind}`, сокет хранил только проект/пользователь/kind,
а канал сравнивал пользователя — runner того же пользователя с PAT или другим
ключом падал вместе с ним; подключение ключа машины в проекте вне списка
api оставалось запущенным; тикет, выпущенный до отзыва, входил после него; а
отзыв PAT ничего не ронял. Сдано: два nullable-столбца в тикете
(миграция Ecto, таблица принадлежит engine, — журнал Drizzle остался на `0068`),
guard, аннотирующий учётные данные после авторизации, id сокета, получающий
вид и id учётных данных, и маршрут `runner/disconnect-credential`, который аннулирует
ожидающие тикеты и спрашивает каждый runner кластера, родился ли он из них.
Запрет AT-013 (не перестать ронять то, что падало) стал двумя переходными
частями: устаревшее подключение падает по паре в проектах строки, а engine
без маршрута заставляет api вернуться к паре. Пара осталась целью удаления
участника. Экран сменил лишь текст подтверждения (RN-561). Runner не изменился.
ExUnit не запускались в среде сдачи (`repo.hex.pm` 403) и остались
для CI.
