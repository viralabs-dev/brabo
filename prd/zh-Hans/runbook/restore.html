    Backup e restore

    Parte do Runbook operacional. Comece pela triagem do índice.

    Restore

    Decisões no ADR 0027.

    Testado. O procedimento abaixo é exatamente o que o make test-restore roda, e ele roda contra o cluster local. Não há passo aqui que ninguém nunca exercitou. O registro da última execução está no fim.

    O que tem backup, e o que deliberadamente não tem

    Existem sete volumes nomeados; dois são fonte da verdade e só esses são copiados. A classificação é o ADR 0152, e o motivo de fazê-la é que "fazer backup de todo volume" custa espaço enquanto esconde o que importa.

    volume natureza no backup?
    pgdata fonte da verdade — event log, ações, pgvector, tudo sim, como dump lógico. Nunca uma cópia de arquivo do diretório de dados: copiar um Postgres rodando produz um backup que pode não restaurar
    git_local_repos fonte da verdade — os repos bare dos projetos do provider local sim, e este era o buraco. Ele não é reconstruível a partir do Postgres: o event log guarda a narrativa, não os objetos do git
    neo4j_data derivado — uma projeção do event log (ADR 0101) não. A resposta para memória derivada é reprojeção, não restore — grafo:reprojetar, veja Perda do grafo
    project_workspaces derivado — worktrees que o WorktreeManager recria a partir do bare repo, e a pasta docs/ dos agentes dos projetos container e runner, que é uma projeção do event log (ADR 0148) não. A resposta é reprojeção — artefatos:reprojetar, veja Perda da pasta de artefatos
    ollama_data reobtível — os modelos baixam de novo não
    brabo_projects_base do usuário, não do produto não, e o instalador nunca o apaga

    Onde o backup mora

    o quê onde
    agenda Kubernetes: CronJob brabo-backup, 03:17 UTC, diário. Compose: não há agendador — você o roda, ou o instalador roda antes de uma migração
    destino disco (BACKUP_DIR) ou um bucket compatível com S3 (BACKUP_S3_ENDPOINT / BACKUP_S3_BUCKET). BACKUP_DIR definida vence; vazia cai para o S3, que é o que o CronJob faz
    layout daily/brabo-<ISO>.dump + weekly/… para o Postgres; git-daily/brabo-git-<ISO>.tar.gz + git-weekly/… para os bare repos
    retenção 7 diários + 4 semanais de cada tipo, por CONTAGEM (BACKUP_KEEP_DAILY / BACKUP_KEEP_WEEKLY)
    formato pg_dump --format=custom --compress=9; tar -czf para os repos
    histórico tabela backup_runs — o dump, chaveado por object_key. O arquivo dos repos leva o mesmo timestamp no prefixo irmão; o vínculo é o nome, não uma coluna

    No cluster local o destino S3 é um SeaweedFS (s3-local, o gateway weed server -s3 na porta 9000) dentro do namespace brabo — era MinIO até o MinIO parar de publicar a imagem comunitária dele (ADR 0169); em staging/prod é o bucket de verdade. O procedimento não muda — só o endpoint. Se o bootstrap para em rollout status deployment/s3-local com ImagePullBackOff, a imagem fixada deixou de ser servida: o digest impede os bytes de mudarem, não o publicador de ir embora.

    O destino padrão do compose é um volume nomeado, e isso serve para verificar e é errado para migrar. docker compose down -v apaga o backup_local junto com os dados que ele devia salvar. Aponte BRABO_BACKUP_HOST_DIR para um diretório do host antes de qualquer migração.

    O que o arquivo dos bare repos garante — e o que não garante

    Nada é congelado: os repos são copiados enquanto api e engine podem estar escrevendo neles. O que isso compra, exatamente:

    • Garantido. Consistência por referência. O git escreve objetos antes de mover uma ref, e troca a ref por rename atômico (ou reescrevendo o packed-refs sob lock, também por rename). Um tar cruzando um git push captura a ref no valor antigo ou no novo, nunca meio valor — e no caso novo os objetos que ela alcança já estão em disco.
    • Garantido. Um arquivo parcial reprova a execução em vez de passar como bom. Um git gc concorrente pode apagar um packfile entre o tar listar um diretório e lê-lo; o status de saída do tar é capturado num arquivo (em sh POSIX o status de um pipeline é o do último comando) e um não-zero vira uma linha failed em backup_runs, que é o que alerta. Rode de novo.
    • Garantido. O arquivo é legível de ponta a ponta antes de qualquer coisa ser escrita — brabo-restore-git é o pg_restore --list do lado do git. Um tar truncado tem tamanho plausível e só lê-lo diz.
    • Não garantido. Qualquer instante global. O tar percorre a árvore ao longo de um período, então dois repositórios — ou duas refs de um — podem vir de momentos diferentes. Irrelevante para o git, que valida por ref; relevante para quem lê "o backup das 03:17" como um retrato só.
    • Não garantido. Conectividade de objetos. Nada aqui roda git fsck: a imagem de backup não tem git, de propósito. O que se prova é a integridade do contêiner, não do conteúdo.
    • Não copiados. Arquivos *.lock, e objects/tmp_*. Restaurar um lock órfão dá um repositório onde todo git se recusa a trabalhar, com uma mensagem que nunca menciona backup.

    Antes de restaurar: o backup existe, e presta?

    select finished_at, kind, status, object_key,
       pg_size_pretty(size_bytes) as tamanho, error_message
  from backup_runs
 order by finished_at desc
 limit 10;

    Três coisas nessa saída importam mais que a última linha:

    • Um status = 'failed' recente com um sucesso antigo é o caso perigoso: existe backup, só que velho. O alerta Last backup run failed cobre exatamente isso.
    • Uma queda brusca em size_bytes entre execuções sugere um dump truncado, e o tamanho sozinho não o denuncia — é o pg_restore --list do script que o pega.
    • Nenhuma linha quer dizer que o CronJob nunca rodou com sucesso. Aí o problema não é o restore.

    O caminho automatizado (o mesmo que o teste roda)

    No Kubernetes:

    make test-restore

    Numa instalação compose — sem cluster, sem kubectl:

    make test-restore-compose

    Os dois disparam um backup real (mesma imagem, mesmo comando que roda em produção — não um pg_dump improvisado, que testaria um caminho que ninguém usa), restauram em brabo_restore_test, validam, e apagam o banco. Use-os quando o objetivo é verificar o backup, não recuperar dados.

    Os dois embrulhos ficam separados de propósito: unificá-los faria o caminho do compose depender de kubectl, que é a dependência que ele existe para não ter. O que não é duplicado é o julgamento — os dois rodam o mesmo brabo-restore, com as mesmas três validações. O do compose acrescenta um terceiro passo que o cluster não consegue pedir: ele verifica o arquivo dos bare repos, porque no Kubernetes o volume git_local_repos não está montado no pod de backup e o passo é legitimamente pulado, enquanto no compose ele está montado e pular seria um falso verde.

    Os dois são provados toda semana no propriedades.yml: make test-restore (e a quebra deliberada dele, make test-restore-mutacao) no job do cluster, e make test-restore-compose — com a verificação dos bare repos que só o caminho do compose faz — num segundo job, restore-compose, em outro runner (AT-195). A migração do instalador também roda o do compose.

    Restaurando de verdade, durante um incidente

    O script brabo-restore restaura num banco NOVO e nunca toca o de origem — de propósito. Restaurar por cima do banco vivo é irreversível e quase sempre a decisão errada nos primeiros minutos de um incidente.

    1. Suba um Job de restore apontando para o nome de banco que você quer:

    kubectl -n brabo create job restore-manual --from=cronjob/brabo-backup \
  --dry-run=client -o yaml \
| sed -e 's|\["brabo-backup"\]|["brabo-restore"]|' \
| kubectl -n brabo apply -f -

kubectl -n brabo set env job/restore-manual RESTORE_DB=brabo_recuperado
kubectl -n brabo logs -f job/restore-manual

    Para restaurar de uma cópia semanal em vez da última diária: RESTORE_PREFIX=weekly/.

    2. Confira o que voltou — as mesmas perguntas que o script faz, agora com os seus próprios olhos:

    -- quantas tabelas voltaram (compare com a origem, não com um número
-- fixo: toda migration nova muda esta contagem)
select count(*) from information_schema.tables
 where table_schema = 'public' and table_type = 'BASE TABLE';

-- o event log é denso por sessão: esta consulta tem de voltar VAZIA
select session_id, count(*), min(seq), max(seq)
  from session_events
 group by session_id
having count(*) <> max(seq) - min(seq) + 1 or min(seq) <> 1;

    3. Promova o banco recuperado apontando DATABASE_URL para ele e reiniciando api e engine. Este é o último passo, e o único destrutivo:

    kubectl -n brabo patch secret brabo-secrets --type merge \
  -p "{\"data\":{\"DATABASE_URL\":\"$(printf '%s' "$NOVA_URL" | base64 -w0)\"}}"
kubectl -n brabo rollout restart deployment/api deployment/engine

    O Secret é materializado pelo External Secrets a partir do provedor. Um patch direto é sobrescrito no próximo refreshInterval (1h): mude também o valor no provedor, ou o sistema volta em silêncio para o banco antigo dentro de uma hora — no meio da recuperação.

    Verificação: os passos 1 e 2 são o brabo-restore que o make test-restore roda toda semana, e as duas consultas do passo 2 são as que o docker/backup/restore.sh se faz. O passo 3 — o patch em DATABASE_URL e reiniciar api e engine contra o banco recuperado — nunca foi exercitado: a prova apaga brabo_restore_test ao terminar e nunca aponta uma api rodando para ele.

    Restaurando numa instalação compose (banco recém-criado)

    Este é o caminho da migração do instalador (AT-738, ADR 0256): depois do down -v a instalação nova sobe com o Postgres vazio e o dump provado precisa voltar nele. Não há kubectl; o comando é o mesmo brabo-restore, com --banco-vazio:

    # 1. Só o postgres de pé: api e engine PARADOS (eles migram o banco ao subir).
docker compose -f docker/docker-compose.install.yml up -d --wait postgres

# 2. Restaura o último dump da pasta do HOST (BRABO_BACKUP_HOST_DIR) no banco do DATABASE_URL.
docker compose -f docker/docker-compose.install.yml run --rm backup brabo-restore --banco-vazio

# 3. Só então suba o resto (api/engine) e restaure os bare repos git.
docker compose -f docker/docker-compose.install.yml up -d
docker compose -f docker/docker-compose.install.yml run --rm backup brabo-restore-git --restaurar

    O que ele garante, e o que não faz:

    • Recusa, antes de baixar qualquer coisa, se o banco tiver QUALQUER tabela em public, drizzle ou engine (inclusive a __drizzle_migrations de uma api que já subiu): a mensagem diz RECUSADO e quantas tabelas achou. Banco com dado nunca é sobrescrito — o ADR 0152 segue valendo, e o caminho de incidente continua sendo o restore em banco NOVO acima.
    • Restaura numa única transação (falha não deixa meio banco) e roda as mesmas validações do teste: lista de tabelas igual à do dump, contagem das tabelas críticas igual à do dump (a origem não existe mais; o número vem das linhas do COPY) e seq densa do event log. Zero linhas nas críticas reprova.
    • O destino do backup tem de ser a pasta do host: o volume backup_local é apagado pelo down -v.

    Provado em propriedades.yml, job restore-banco-vazio: postgres e backup do compose de instalação num projeto descartável, dado semeado, backup em pasta do host, restore num banco novo com contagens iguais, e a recusa sobre o banco já restaurado.

    O que o restore NÃO cobre

    • As credenciais de usuário ficam ilegíveis se CREDENTIALS_MASTER_KEY for diferente. O dump leva as DEKs embrulhadas, não as chaves. Restaurar num ambiente com outra chave mestra devolve um banco intacto com credenciais de LLM e de git inúteis. Veja Rotação da chave mestra.
    • Nada dos usuários fica de fora. Desde o corte do Keycloak (ADR 0032) não há banco de IdP separado: identidades, credenciais argon2id, refresh tokens e o event log de auth moram todos no mesmo Postgres e entram neste dump. O que não sobrevive é lê-los se o AUTH_TOKEN_PEPPER for diferente — mesmo raciocínio da chave mestra acima.
    • O brabo-restore restaura o banco, e só ele. Os bare repos são o comando irmão, brabo-restore-git — veja Recuperando os bare repos. São comandos separados e não duas fases de um só porque são dois artefatos com dois julgamentos: uma falha de git não pode reprovar a validação do event log, e o contrário seria pior.
    • Os worktrees dos agentes (project_workspaces) não são copiados, e não precisam ser: o WorktreeManager os recria a partir do bare repo. O que se perde é trabalho em andamento não commitado.
    • Os repositórios de verdade moram no GitHub/GitLab — isto estava escrito aqui e estava errado, e é por isso que o volume passou anos sem backup. Vale para projetos dos providers github/gitlab; para um projeto no provider local não há upstream em lugar nenhum, e o bare repo em git_local_repos é o código que os agentes produziram.
    • Não é PITR. A granularidade é o último dump; qualquer coisa escrita depois dele se perde. Se isso não é aceitável, o caminho é arquivamento de WAL no CloudNativePG, que está fora do escopo desta fase.

    Recuperando os bare repos

    Verificar não custa nada e não escreve nada — é o gesto semanal, e desde a AT-195 o job agendado restore-compose do propriedades.yml o faz (pelo make test-restore-compose, veja o caminho automatizado):

    docker compose -f docker/docker-compose.prod.yml run --rm backup brabo-restore-git

    Restaurar é o gesto de uma vez por incidente, e tem de ser digitado:

    docker compose -f docker/docker-compose.prod.yml \
  run --rm --user "$(docker run --rm -v brabo_git_local_repos:/v alpine stat -c %u:%g /v)" backup brabo-restore-git --restaurar

    Duas coisas sobre esse comando, as duas medidas e não supostas:

    • --user <dono do volume> não é opcional aqui, e root não serve (o serviço tem cap_drop: ALL; a mensagem de recusa imprime o uid:gid lido por stat). O git_local_repos é compartilhado por três imagens rodando com três uids diferentes (a api como node, o engine como engine, a imagem de backup como uid 70). O volume fica com o dono de quem o montou primeiro, modo 0755: o uid 70 o lê e não consegue escrever. Sem root o comando recusa antes de extrair, nomeando esta correção — ele não descobre o problema no meio do tar, deixando o volume escrito pela metade.
    • O que é extraído é devolvido ao dono do diretório, nunca deixado como root. Senão o volume voltaria intacto e inútil: api e engine, não-root, não conseguiriam escrever no que acabou de ser restaurado, e o sintoma apareceria muito depois do restore sem nada apontando para ele.

    Ele recusa extrair por cima de repos existentes. Sobrepor dois estados de repositório produz uma mistura de que nenhum git reclama e que ninguém nota até um fetch trazer de volta o histórico errado. Esvazie o volume, ou passe RESTORE_GIT_FORCE=1 se a sobreposição é genuinamente o que você quer.

    Verificação: as funções de shell por trás dos dois gestos são provadas em todo PR por scripts/ci/backup-lib.spec.ts — arquivar e restaurar vão e voltam idênticos, nenhum *.lock copiado, um arquivo truncado recusado na leitura, um destino em que ele não consegue escrever recusado antes do tar. Os próprios comandos, na imagem de backup contra o volume real, rodam pelo make test-restore-compose (a metade que verifica, nunca --restaurar), toda semana no propriedades.yml. Esse job primeiro cria um bare repo no volume (git init --bare, como o LocalGitProvider faz) e reprova se o veredito não o nomeia: com o volume vazio, brabo-restore-git responde "nada a restaurar" e sai com 0, o que seria um verde que não leu arquivo nenhum.

    Perda do grafo (Neo4j)

    O neo4j_data não está em backup nenhum, e isso é a decisão, não um descuido (ADR 0152, decisão 4). Restaurar uma projeção possivelmente velha ao lado de um Postgres restaurado noutro instante dá dois estados derivados de momentos diferentes sem nada para reconciliá-los. A resposta certa para memória derivada é reprojetar a partir da fonte — e esse comando existe (RN-569):

    # Kubernetes (o script vem dentro da imagem da api)
kubectl -n brabo exec deploy/api -- node scripts/reprojetar-grafo.js
kubectl -n brabo exec deploy/api -- node scripts/reprojetar-grafo.js --project <project-uuid>

# compose de instalação (mesma imagem do Kubernetes)
docker compose -f docker/docker-compose.install.yml exec api node scripts/reprojetar-grafo.js

# um checkout de dev (DATABASE_URL e NEO4J_* apontando para o banco e o grafo)
pnpm --filter api grafo:reprojetar
pnpm --filter api grafo:reprojetar -- --project <project-uuid>

    Saída esperada:

    [reprojetar] escopo: event log inteiro
[reprojetar] eventos: 4 projetados, cursor 01M2DTREY0TBKHCHG9NWXYF0A4
[reprojetar] sessões fechadas: 2 projetadas

[reprojetar] resultado

  eventos projetados=4  sessões fechadas projetadas=2  falhas=0
  grafo agora (inteiro): nós=80  arestas=80

    O que ele faz, e o que garante:

    • A mesma tradução do projetor vivo. Evento → nó/aresta mora numa classe só (GraphEventTranslator), chamada tanto pelo projetor de ida quanto por este comando. Ele lê handoff.offered, psychologist.hypothesis_proposed e anamnese.profile_updated de session_events, e a Interacao de toda sessão em closed/closed_abnormally de sessions (fechar uma sessão não deixa evento no log).
    • Idempotente, e nunca apaga. Toda escrita é um MERGE numa chave natural: rodá-lo duas vezes dá o mesmo grafo, e rodar de novo é como você tenta de novo depois de uma falha no meio. Ele só acrescenta ou converge; um nó já no grafo fica.
    • Em lotes, por cursor. O session_events é percorrido na ordem de id (ULID, a chave primária), 200 linhas por vez — nunca a tabela inteira em memória. A linha de progresso imprime o cursor; --after-event <id> retoma a fase de eventos depois dele. Recomeçar é igualmente seguro, só mais lento.
    • Ele não toca a outbox, então a api pode ficar de pé. O projetor vivo guarda o progresso dele em outbox_events.processed_at (aggregate_type = 'graph_projection'); este comando nem lê nem escreve essa tabela, então não consegue roubar, reabrir nem marcar uma linha. Os dois escrevem com MERGE nas mesmas chaves.
    • Ele falha nomeado, nunca como sucesso silencioso. Neo4j não configurado ou inalcançável é recusado antes de ler o log (um escopo vazio, senão, "daria certo" com zero projetados); o Neo4j caindo no meio para com o último evento completado; um --project desconhecido é recusado sem nada escrito; um item com payload incoerente é contado, nomeado, e a execução sai com 1 no fim.

    O que ele não reconstrói, e a única ressalva de ordem:

    • PromptTemplate/PromptVersion não vêm do event log. A fonte deles é o diretório prompts/: reenvie-os com node scripts/dev/seed-prompts.ts (idempotente por hash).
    • PerfilAnamnese é um retrato chaveado por usuário + dimensão, sem projeto. O último a escrever vence. Uma execução com --project reexecuta só os eventos de perfil daquele projeto, então pode deixar um retrato no último valor daquele projeto quando outro projeto escreveu um mais novo. A execução completa (sem --project) percorre o log inteiro em ordem e restaura o último global — use-a depois de perder o grafo; guarde --project para um reparo pontual.
    • Uma execução completa exige uma janela de manutenção, sem teto de tempo, e quanto ela leva num log grande não foi medido — veja Rodando uma reprojeção completa para a janela, a linha de progresso e como saber quanto falta.

    A prova é o make test-reprojecao (apps/api/test/scripts/reprojetar-grafo.spec.ts): ele monta um cenário com o projetor de ida, apaga esse subgrafo, reprojeta, compara as contagens de nós e arestas mais a lista de chaves, e reprojeta de novo. Ele precisa do Neo4j de pé e pula sem ele — o job de CI da api não tem Neo4j, então ali ele pula. Ele não depende de ter havido um backup, de propósito.

    A mesma prova também roda dentro do cluster local: make test-reprojecao-k8s (deploy/k8s/test-reprojecao.sh) é o quarto alvo do agendado propriedades.yml (veja Provas de propriedade agendadas). Ele roda o comando exatamente como esta seção manda rodá-lo num incidente (kubectl exec deploy/api -- node scripts/reprojetar-grafo.js --project <id>), contra o Postgres e o Neo4j do cluster, num projeto que ele mesmo cria. O Psicólogo e a Anamnese seguem pausados: a prova acrescenta os eventos que eles escreveriam e confere o que a reprojeção reconstrói a partir deles.

    O grafo vazio até você rodar isto tem um efeito nomeado: leituras que dependem do grafo degradam. O RAG não é afetado — ele mora no pgvector, que está dentro do dump.

    Rodando uma reprojeção completa: uma janela de manutenção, sem teto de tempo

    Uma reprojeção completa (do grafo ou da pasta de artefatos) é uma operação rara de recuperação, e roda numa janela de manutenção, sem teto de tempo — decisão do mantenedor (2026-09-27). Nada no produto a corta por tempo, avisa quando demora, ou a agenda: ela roda pelo tempo que o event log levar, e você planeja a janela para isso.

    Quanto tempo isso é num log de tamanho de produção não foi medido. A única execução real até agora é o compose de desenvolvimento (98 eventos em session_events, 2,5 s de ponta a ponta); uma extrapolação proporcional a partir disso não é medição, então cronometre a primeira execução completa da sua instalação e guarde esse número para a próxima janela.

    Acompanhando o progresso. O comando imprime uma linha por lote — a cada 200 eventos dos tipos que ele lê — antes do resultado final, então uma execução que ainda está imprimindo ainda está percorrendo o log:

    [reprojetar] eventos: 200 projetados, cursor 01M2DTREY0TBKHCHG9NWXYF0A4
[reprojetar] eventos: 400 projetados, cursor 01M2DV3K8Q2S7ZB1CXN4W6Y9HR
...
[reprojetar] sessões fechadas: 200 projetadas
[reprojetar-artefatos] artefatos: 200 projetados, cursor 01M2DTREY0TBKHCHG9NWXYF0A4

    O número é de quantos foram projetados (itens que falharam são impressos na própria linha e contados em falhas= no fim). A linha não leva um total. Para saber quanto falta, pergunte ao Postgres, com o cursor da última linha — só leitura, então é seguro enquanto a execução segue:

    -- grafo, fase de eventos: quantos no total, e quantos ainda depois do cursor
SELECT count(*) AS total,
       count(*) FILTER (WHERE id > '<cursor>') AS remaining
  FROM session_events
 WHERE type IN ('handoff.offered', 'psychologist.hypothesis_proposed',
                'anamnese.profile_updated');

-- grafo, segunda fase (a Interacao de cada sessão fechada)
SELECT count(*) FROM sessions WHERE status IN ('closed', 'closed_abnormally');

-- pasta de artefatos
SELECT count(*) AS total,
       count(*) FILTER (WHERE id > '<cursor>') AS remaining
  FROM session_events
 WHERE type IN ('artifact.note', 'artifact.business_rule',
                'artifact.decision_record', 'artifact.product_brief',
                'artifact.module_map', 'artifact.module_routing',
                'artifact.project_image', 'artifact.c4_diagram',
                'artifact.prototipo_navegavel', 'artifact.plano_de_teste',
                'artifact.threat_model', 'artifact.insight',
                'artifact.rfc_staff');

-- quando o evento do cursor foi escrito (os ids são ULIDs, ordenados por tempo)
SELECT created_at FROM session_events WHERE id = '<cursor>';

    Acrescente AND session_id IN (SELECT id FROM sessions WHERE project_id = '<project-uuid>') a uma contagem quando a execução tem --project. As listas de tipos são as que os comandos leem (EVENTOS_DO_LOG_PROJETAVEIS em apps/api/src/application/graph-projection/graph-event-translator.ts, ARTIFACT_PROJECTABLE_EVENT_TYPES em apps/api/src/domain/artifacts/artifact-projection-events.ts); se algum dos arquivos ganhou um tipo, a contagem aqui fica curta dele.

    O que esta decisão não acrescenta. Nenhum teto, nenhum aviso, nenhuma reprojeção dividida em janelas ou agendada pelo produto. --project e --after-event continuam exatamente o que já eram — um reparo pontual e uma retomada depois de uma interrupção — e não são o jeito de caber uma recuperação completa numa janela mais curta: uma execução com --project não consegue restaurar o retrato global de PerfilAnamnese (acima), e retomar no meio de um tipo de artefato versionado pode deixar uma versão mais velha (abaixo). A execução completa é a recuperação. Interrompê-la é seguro — a idempotência acima vale — e rodá-la de novo desde o início é sempre correto, só mais lento.

    Perda da pasta de artefatos (docs/)

    Todo artefato que os agentes emitem mora só no event log; a pasta docs/ do projeto é uma projeção dele (ADR 0148), então não está em backup nenhum e isso é a decisão, não um descuido (o ADR 0152 raciocina o mesmo para o grafo). Restaurar o banco não a traz de volta sozinho: as linhas da outbox que movem o projetor vivo já estão marcadas como processadas, então nada reescreve a pasta. O comando que reescreve existe (RN-590):

kubectl -n brabo exec deploy/api -- node scripts/reprojetar-artefatos.js --project <project-uuid>

# compose de instalação (mesma imagem do Kubernetes)
docker compose -f docker/docker-compose.install.yml exec api node scripts/reprojetar-artefatos.js

# um checkout de dev (DATABASE_URL apontando para o banco)
pnpm --filter api artefatos:reprojetar
pnpm --filter api artefatos:reprojetar -- --project <project-uuid>

[reprojetar-artefatos] artefatos: 6 projetados, cursor 01M2DTREY0TBKHCHG9NWXYF0A4

[reprojetar-artefatos] resultado

  artefatos projetados=6  falhas=0

    O que ele faz, e o que garante:

    • A mesma tradução do projetor vivo. Evento → pasta, nome de arquivo e Markdown moram numa classe só (ArtifactEventTranslator), chamada tanto pelo projetor de ida quanto por este comando.
    • Idempotente, e nunca apaga. O nome do arquivo é função do evento (tipos versionados: <tipo>.md; append-only: com o seq), então rodá-lo duas vezes reescreve os mesmos arquivos com o mesmo conteúdo, e rodar de novo é como você tenta de novo. Um arquivo que você criou em docs/ fica.
    • Em lotes, por cursor. O session_events é percorrido na ordem de id, 200 linhas por vez; --after-event <id> retoma depois do cursor impresso.
    • Ele não toca a outbox, então a api pode ficar de pé.
    • Ele falha nomeado, nunca como sucesso silencioso. Uma escrita que falha (disco cheio, pasta inalcançável, um projeto cuja pasta sumiu) é contada e nomeada por evento, não para o resto, e a execução sai com 1 no fim. Um --project desconhecido é recusado sem nada escrito.

    Onde ele escreve, e o que não cobre:

    • Ele precisa ver o mesmo disco que a api. A pasta é resolvida pela mesma função que o projetor usa (container/runner: <PROJECT_WORKSPACES_ROOT>/<workspace_dir_name>/docs/; mounted: dentro da pasta do projeto). Rode-o na imagem da api, com os volumes da api.
    • Ele escreve no local atual do projeto. Uma conversão de modo não move a docs/ (o código da conversão nunca a toca), então arquivos escritos antes dela ficam no local antigo; reprojetar os recria no atual.
    • Tipos versionados mostram o último evento, então não retome no meio deles. module_map, module_routing, project_image e c4_diagram sobrescrevem um arquivo; uma execução completa termina com a última versão emitida, enquanto --after-event começando entre duas versões pode deixar uma mais velha.
    • O que ele não lê: tipos fora da lista projetável (qa_verdict, secops_verdict, task_blocked, infra_delegation_files) nunca foram arquivos e não são recriados.
    • Ele roda numa janela de manutenção, sem teto de tempo, igual ao grafo: a linha de progresso e as consultas para acompanhá-la estão em Rodando uma reprojeção completa. Quanto ele leva num event log grande não foi medido; o comando é seguro de interromper e rodar de novo.

    A prova é apps/api/test/scripts/reprojetar-artefatos.spec.ts: ele monta um cenário com o projetor de ida num Postgres de verdade e num disco de verdade, apaga a pasta, reprojeta, compara cada caminho e conteúdo, e reprojeta de novo. Ele roda em todo PR. O comando como esta seção manda rodá-lo num incidente — node scripts/reprojetar-artefatos.js dentro da imagem da api — é provado pelo make test-reprojecao-artefatos-k8s (deploy/k8s/test-reprojecao-artefatos.sh, AT-198), o irmão do alvo de cluster do grafo: ele cria um projeto próprio com um artifact.note pela API, espera o projetor vivo escrevê-lo, apaga a pasta docs/<agente>/ do agente dentro do pod da api, roda o próprio script da imagem com --project, e exige que o arquivo reconstruído tenha o mesmo sha256 do que o projetor vivo escreveu — depois roda de novo e exige o mesmo hash (idempotência). Ele roda no agendado .github/workflows/propriedades.yml, e como o irmão não depende de nenhum outro alvo.

    Quando o restore falha

    sintoma causa provável
    no backup under .../daily/ bucket errado, credencial errada, ou o CronJob nunca rodou
    not an intact custom dump upload interrompido; use o objeto anterior ou weekly/
    pg_restore failed com erro de extensão o banco de destino precisa das mesmas extensões (pgvector); no CNPG elas vêm do cluster, não do dump
    missing tables in the restored copy um dump de outra versão de schema — o script diz QUAIS faltam; confira a data do objeto contra a migration mais recente
    out of window numa tabela crítica a contagem não bate com o timestamp do dump: investigue antes de promover
    server version mismatch o pg_dump do Job é 16; um cluster noutra major recusa a conexão
    timeout do Job banco grande demais para o activeDeadlineSeconds; suba o valor no Job, não no CronJob
    destination inaccessible … does not accept writes com BACKUP_DIR, o diretório existe e o uid do container não consegue escrever nele. É uma checagem de escrita, não de existência, de propósito: um destino só de leitura passaria no ls e reprovaria o dump, com o erro aparecendo depois do pg_dump e apontando para a coisa errada
    tar of the bare repos exited with N algo mudou sob os repos no meio da leitura — o mais provável é um git gc concorrente. A execução é marcada failed em vez de entregar um arquivo parcial. Rode de novo
    there are N bare repo(s) … and NO archive este volume não tem cobertura: o arquivo falta enquanto os repos não. Ausente-e-vazio é normal e informado de outro jeito
    does not accept writes by this user (uid 70) no --restaurar o caso do dono do volume compartilhado — restaure com --user <dono do volume>, veja Recuperando os bare repos

    Uma falha abre uma issue com o título Prova de propriedade falhou: <alvo>, uma por alvo, e uma falha repetida do mesmo alvo comenta na issue aberta em vez de abrir outra. O bootstrap tem título próprio: com o cluster fora do ar, os três alvos ficam skipped, e uma execução agendada pulada é o silêncio que isto existe para quebrar. A primeira execução em que o alvo passa fecha a issue dele com um comentário nomeando aquela execução (AT-212) — ninguém precisa lembrar. Só uma execução na branch default (a agenda, ou um workflow_dispatch nela) mexe em issues: um workflow_dispatch vermelho numa branch falha na própria execução, registra um aviso, e nem abre nem comenta na issue da agenda, e um verde numa branch não fecha nada. As execuções ficam em fila por ref (concurrency: propriedades-<ref>): dois dispatches em branches diferentes rodam lado a lado, dois na mesma ref esperam um pelo outro. Ele não é gate nem check obrigatório — nada espera por ele.

Uma convergência normal de 3 s torna "a órfã só precisava de mais de 15 s" a leitura menos provável; a mais provável é uma corrida intermitente na adoção ou na drenagem que a espera fixa por acaso pegou. Fica como está de propósito: o workflow existe para pegar exatamente isto, e a próxima ocorrência agora vai falhar com o teto que esperou, onde cada sessão vivia antes do rollout, e as linhas do engine que nomeiam a órfã. A correção é do engine, não desta prova.

    O que esta execução achou

    O restore dos bare repos não conseguia escrever no volume em que restaura, e só rodá-lo revelou isso. O git_local_repos é compartilhado por três imagens com três uids; ele fica com o dono de quem o montou primeiro (medido: 1000:1000, modo 0755) e a imagem de backup roda como uid 70. O primeiro --restaurar morreu no meio da extração com tar: can't make dir ./exp001.git: Permission denied, deixando o alvo escrito pela metade. Duas mudanças vieram disso, as duas acima: o comando recusa antes de extrair e nomeia --user <dono do volume>, e quando ele de fato roda como root devolve a árvore extraída ao dono do diretório em vez de deixá-la com dono root — o que teria produzido um volume que restaura perfeitamente e em que api e engine não conseguem escrever.

    Verificado depois com git de verdade (não a imagem de backup, que não tem): git fsck --connectivity-only limpo nos dois repos, refs e commits intactos, dono de volta em 1000:1000.
