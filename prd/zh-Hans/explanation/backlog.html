    这是提议。下面的分类和分组是关于什么等待代价更高的论证；优先级的决定权在用户。

    缺陷在于节奏，而不是内容：各阶段关闭了，却没有人回到这里标记它们。保留下来的——也是 保留这个文件的原因——是分类的推理：为什么每个条目等待比去做代价更高。把下面的每个 状态都视为在重新测量之前未经验证。

    如何分类

    P1——阻止产品做它承诺的事。P2——产品能做，但对观察者撒谎或造成困惑。P3—— 质量问题，没有人被卡住。

    成本：P（一个会话）、M（一个小阶段）、G（独立阶段，带 ADR）。

    等待风险是决定平局的一列：会损坏数据或抹去证据的缺陷，晚做比今天做代价更高；外观上的 缺陷代价相同。

    阶段 A — 解锁 task（P1）— 已完成

    从来没有任何 dev agent 完成过一个 task。 这是决定一切顺序的事实：FASE 15a 的 gate 登记显示 qa-verificada、secops-segura 和两个 infra gate 为 "nunca passou"——不是因为 缺少执行，而是因为从来不存在可供任何 gate 评判的 PR。

    条目 曾经是什么 如何关闭
    ADR 0052 待处理的审批把 status pending 作为工具结果返回并烧掉一次迭代；智能体在上限处死掉而什么也没写 循环挂起并恢复（RN-073）；结果的投递在之后被修正——事件诞生在一个 engine 排空器不读取的聚合中——这条路径现在已端到端覆盖
    O / B 会话和 dev agents 诞生在本地的 llama3.2:1b 上，而 ADR 0020 在语义步骤中禁止它 当级联落到 workspace 默认值时，继承的模型是 Criativo 的（RN-072）

    继承填补空位而从不覆盖：会话、智能体或项目的 binding 是显式选择，仍然胜出。而继承的 模型经过与级联相同的过滤——从目录中消失或不支持 tool calling 的不会被继承。

    关闭这个阶段并不足够，这是它最有用的发现：智能体开始运转了，又死于别的东西（阶段 F， 413）。"从来没有任何 dev agent 完成过一个 task" 依然成立——改变的是原因。

    等待风险：高。 在它关闭之前，远程 PR、QA/SecOps 的 gates 以及 13b 的测量都被堵在后面—— 而每一轮 dogfooding 都在花钱，只为再次确认同一个阻塞。

    阶段 B — 远程 provider 上的 engine（P1）— 已完成

    N——get_local_repo_path/1 对一切不是 local 的东西返回 unsupported_provider，四个 消费者随之停止。api 通过 HTTP 与 GitHub 对话；engine 在文件系统上工作，只认识本地 bare repo，因此远程项目会运行会话那一半，而在构建那一半停下。

    由 ADR 0056 和 RN-076 关闭：engine 向 api 请求工作用的远程，api 持有 主密钥，凭据按调用传入——写入 .git/config 的 origin 是干净的。

    缩小问题的发现： 四个消费者中有两个从来不需要凭据。Diff 和 ProjectContext 只使用 分支的名称——它们是因一个返回了比所需更多东西的函数而附带受损停止的。

    阶段 B 没有关闭的

    • 隔离，又一次。token 离开了磁盘，但智能体仍与 Brabo 的 monorepo 在同一个容器中。这是 ADR 0055 已经声明的同一个待办，现在有两个阶段指向它。
    • 针对真实 GitHub 的证明。 fetch 和 push 经过 GitAuth，测试端到端覆盖了本地路径 （推送到达另一端的 bare）和命名的错误。没有任何测试能给出带真实 token 的真实远程仓库—— 那是 13b 的执行，它现在有条件发生了。

    阶段 F — 执行器的边界和上限（P1）— 已完成

    hello-limpo 的执行死在这里，两个条目有同一个根源：终端执行器没有限制——既没有限制命令能 到达哪里，也没有限制它返回多少。

    条目 曾经是什么 如何关闭
    S 累积的上下文超出 provider 的字节限制，调用返回 413。每次终端输出都留在历史中，并随之后的每个轮次传递 执行器中的字节上限，带有写给模型的标记（RN-074）
    U 执行器内的 /workspace 是 Brabo 自己的 monorepo，而 /data/project-workspaces/*/ 能访问其他项目的 worktree 决策中的路径范围（RN-075，ADR 0055 已接受）

    范围一次性关闭了两个方向：收紧（指向外部的放行动词不再自动批准）和放宽（向内的 cd 不再让复合命令被拒，这是阶梯中代价最高的缺陷）。

    阶段 F 没有关闭的

    记录在案，而不是当作已完成：

    • 隔离。 ADR 0055 是策略，它自己也这么说。只要 Brabo 的 monorepo 挂载在执行命令的容器 中，边界就取决于规则是否判断正确。规范化是词法上的：.. 被拒绝，而从内部指向外部的 符号链接不会被检测到。
    • ADR 第 6 点——"总是允许"的泛化。 它仍然记录字面命令，而那永远不会再匹配。没有纳入， 因为泛化会扩大一次点击授权的范围（批准 cat foo 将放行对任何东西的 cat），这是 一个值得单独审视的产品决定，而不是顺带做。
    • ADR 第 7 点——事件记录是哪个范围授权的。 决策的原因已经说明了，但没有持久化到 proposed_action.created 中。

    阶段 C — UI 不能对智能体撒谎（P2）— 已完成

    五个条目有同一个根源：界面讲的故事与 event log 不同。

    条目 界面做了什么 状态
    C 实时气泡带着模型的标签；智能体只在持久化事件到达时才出现——而消息在重新加载之前是重复的 已完成——增量开始携带智能体，在轮次流式传输期间推迟重新获取
    G 在已创建的项目中不出现 Criativo 的邀请，因为对话流中已经有 bootstrap 的卡片 已完成——条件改为"对话已开始"，而不是"对话流为空"
    L 在离开 Criativo 的 handoff 之后，底部按钮仍是 "Estou pronto para produzir" 已完成——存在离开 Criativo 的 handoff 时消失
    H bootstrap 的事件全部显示为 "atividade em system" 已完成——五种类型有了自己的族，步骤已翻译
    I 更换会话的模型会追溯地改写旧动作的标签 已完成——卡片不再断言一个它无从得知的模型

    C 是五个中最严重的，是你在执行过程中指出的：说话的是智能体，模型是执行细节。

    I 值得一个决定，而不只是修复。 卡片接收的是会话的当前模型，而不存在按动作的模型的 真实来源——proposed_actions 不保存它，token_usage 也不关联到动作。在编造一个和停止断言 之间，后者是唯一诚实的：提议者已经以粗体在卡片上，那是智能体，是不变的东西。标签随 prop 一起移除了，该 prop 没有其他任何消费者。

    H 变成了措辞问题：五种 bootstrap.step_* 类型有了自己的族，步骤翻译成葡萄牙语，只有 step_failed 被标为坏——degraded 和 skipped 是预期的结果，把它们涂成红色会教人忽略 红色。create_rc_branch 即使已退役（ADR 0030）也仍然被翻译，因为之前 bootstrap 的项目在 日志中有这个事件。

    阶段 D — 向导说真话并且有出路（P2）— 已完成

    条目 曾经是什么 如何关闭
    D Protect branches 在免费计划的私有仓库上失败，而向导事先就提醒了这一点。之后提供的唯一操作是"重试"，它总是失败 RN-078

    F "Política de branches" 步骤把 rc 列为永久分支之一 之前已完成（提交 4dd7a073）

    E 和 F 在我去处理它们时已经被修正，在一个一次关闭四个发现的提交中。发现这一点花了一次 阅读；backlog 不知道，因为它是之前写的。

    条目 D 比描述所暗示的更大。 它不只是"没有出路的界面"：provision_failed 让仪表板把 对项目的点击重定向回配置页面，于是项目永远不可达，卡在一个不可能成功的步骤里。出路需要 路由、用例和事件——而不只是一个按钮。

    只有保护步骤可以被确认，这是关键的决定：它是最后一步，也是唯一一个失败后仍留下可用 仓库的步骤。在更早的失败上提供"继续"，会是叠加在第一个谎言之上的第二个谎言。

    阶段 G — 失败结果说真话（P2）— 已完成

    CLAUDE.md 的同一条规则被违反了三次：P（dev.blocked 带 origin: null）、Q （agent.error 带 "undetermined"）和 T（复发：dev.blocked 带 "undetermined"，而 失败的 diagnosis 字段在同一行中就说出了原因）。

    由 RN-077 关闭，对原因的诊断改变了修复的形式：分类器 早已存在并且本可以判对——FalhaDeTurno.origem/1 把 ≥ 400 的状态映射为 codigo，这正确 地分类了发现 T 的 413。缺陷从来不是缺少规则；而是 block_task 以 "undetermined" 作为 默认值，而调用点什么都不传。

    所以修复是结构性的，而不是又一条规则：默认值被删除了。忘记来源现在是编译错误，而不是 一个语法上有效、语义上空洞的事件。

    indeterminada 不再存在。它的意思是分类器没有识别这种形式——我们代码的缺口——而 codigo 是指向正确行动的来源。indeterminada 不指向任何行动，这正是该发现的抱怨。

    阶段 H — 会话状态不撒谎（P2）— 已完成

    V——会话 1f94de49 自 23:34:42 起显示为 closed，而执行一直持续到 00:56。

    原因不在状态机：而在心跳。会话在 23:34:12 诞生，在 23:34:42 关闭——正好是 SESSION_HEARTBEAT_TIMEOUT_MS 的 30 秒。RN-064 已经要求 在结束前检查是否有待处理的工作，但"待处理的工作"只是 offered 状态的 handoff——而自 23:34:13 起就有一个 pending 的动作，在会话诞生一秒后创建。

    等待决定的动作开始被计入。这是低一层的同一个 handoff 缺陷：有人在等你，而一个智能体可能 正挂起等待结果（RN-073）。

    规则的前一个版本白纸黑字地写着，纳入智能体的工作"在没有证明这种交互的测试之前就是猜测"。 执行产生了证明，这就是这次修复与一次猜测的区别。

    阶段 H 没有关闭的

    • 没有待处理动作也没有 handoff 的 in_progress task。 这个信号需要 api 读取 dev_agent_states，而它属于 engine——这是边界决定，不是顺带修复。
    • closed 仍然接受审批。 心跳修正后，会话不再在有悬挂动作时关闭，因此这种情况变得罕见。 在已关闭的会话上阻止决定是一个有其自身后果的行为改变：一个已结束会话中的孤立动作将无人 可以决定。

    阶段 E — 智能体产出的质量（P3）

    条目 发生了什么
    K 在同一个项目中运行两次 Criativo 留下了 10 条规则，5 条孤立——没有去重也没有提醒
    R PO 生成了两个覆盖同一端点的用户故事
    J Psicólogo 在刚打开的会话中带着前一个会话的假设和空日志运行，试图引用不存在的事件然后放弃
