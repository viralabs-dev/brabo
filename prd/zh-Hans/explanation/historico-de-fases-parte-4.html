    阶段历史，第 4 部分：从本地 runner 起

    2026年9月11日 的记录：描述当时的 Brabo

    从本地 runner（ADR 0102 和 0103）起，加上从 CLAUDE.md 索引迁出的章节，第 28、29 和 30 阶段就在其中。 文本原样移自阶段历史，未作改写。今天有效的内容位于 RN 和 ADR 中。

    本地 runner——在用户机器上执行（RN-418/419/420，ADR 0102/0103）

    产品所有者的请求：agent 在用户的机器上、在项目的本地目录中、通过用户的默认终端运行——外加 Code 标签页中真正的交互式终端。两项变更，一项依赖另一项。

    策略（ADR 0102——全局决定，在一条关于该变更的自动安全警告之后，由产品所有者明确确认）： git push/PR/部署（RN-106）和 sudo/doas（新增）从无条件的 deny 变为绝对上限——无条件的 require_approval，与相邻上限位于同一区块、采用相同模式（current.policy === 'auto_approve'），永远不能被 agent_autonomy（通配符 "*"）或 permissions.json 自动批准。原先的 deny 强行堵住的缝隙在源头被关闭：ApproveAlwaysActionUseCase/patternForAction 拒绝为带 git 外部效果或特权命令的动作在 allow 中写入模式——对于这两种情况，“sempre permitir”只批准该实例，从不批准模式。没有这另一半，上限就只是装饰。sudo/doas 在 comandoPrivilegiadoNoComando （external-effect.ts）中按动词匹配，扫描命令的所有段，与 efeitoExternoNoComando 原则相同。

    Runner（apps/runner，新的 Node/TS workspace，ADR 0103）：用户在自己机器上运行的 CLI （brabo-runner --project <id> --dir <pasta> --token brb_...），通过新的 Phoenix 通道连接到 ENGINE （/runner， 主题 terminal:<projectId>），由一次性ticket 认证（与 RN-108 模式相同，但 ticket 由 ENGINE 签发——schema "engine"，有自己的 migration——由 api 通过内部 HTTP 路由请求，与会话 ticket 的流程相反）。它在用户的 $SHELL 中执行 exec（已经批准的 agent 命令——TerminalExecutor 中的路由只在一贯的 decide()/proposed_action 管道之后发生，从不在之前），并为终端标签页提供交互式 PTY 模式（pty_open/pty_data/ pty_input/pty_resize/pty_close——engine 做纯粹的中继，从不解释字节）。每个项目只有一个 runner（Engine.Runners.Registry、 :global，:global.register_name/3 的排他性）；runner 模式在没有已验证的 workspace 或没有已连接的 runner 时会显式拒绝——从不退回到 System.cmd/bind-mount，对 runner 项目来说那并不存在 （由 ADR 0104/RN-423 修订，见上文；退回到一贯路径的行为仍然有效，但只针对 container/mounted）。PTY 是已认证用户的动作，不经过 proposed_action，但会被审计（event log 中的 terminal.session.started/ended，包括标签页在没有显式 pty_close 的情况下掉线时）。

    runner 的安全边界不是沙箱——而是认证（CLI 出示用户账号的 Personal Access Token）+ 一贯的审批管道 + 用户同意以自己的权限在自己的机器上运行 CLI。apps/runner/src/guard.ts 通过词法解析校验 cwd 位于根目录之内，但它被声明为尽力而为，不是真正的保证。

    PAT 填补了自动化 token 的缺口（ADR 0105/RN-424..426）。 第 1 波的真实发现——“产品没有用于自动化的长期账号 token 机制，所以 runner 复制了浏览器的登录（cookie/CSRF 持久化在 ~/.brabo/runner-credentials.json 中）”——在第 2 波中关闭：personal_access_tokens（brb_…，通过 hashDeToken() 的 HMAC-SHA256+pepper 哈希，从不用 argon2——它不适用于高熵机密）在项目配置中签发，限定于一个项目，可吊销，可选过期。apps/runner/src/auth.ts 完全去掉了交互式登录、cookie 和凭据文件——只校验格式并转发 --token/BRABO_ACCOUNT_TOKEN，CLI 从不把它写入磁盘。PAT 从构造上从不在 POST .../runner-ticket 之外认证（IS_PAT_ROUTE_KEY/ @RequirePatAuth() + PatAuthGuard）——从不是全局 JwtAuthGuard 中的一个分支，那会让 RolesGuard 为用户角色的任何路由授权 PAT。

    maintainer 可以吊销其他用户的 PAT（RN-427），关闭了 ADR 0105 暂时声明为超出范围的条目（事件响应——离职的 dev 的 token 泄露）。同一模型的扩展，没有新 ADR：单独的路由（GET .../personal-access-tokens/all、 DELETE .../personal-access-tokens/:tokenId/admin），范围按 projectId 而不是 userId——每个用户的自我吊销（RN-426）不变。

    @xterm/xterm/@xterm/addon-fit（web）和 phoenix/node-pty（runner）是四个新依赖——与 mermaid 同一把例外标尺（ADR 0068）：动态 import()，通过对已安装包的 grep 确认没有 eval/new Function（这不是针对混淆的正式保证，只是强证据——声明为不确定性，而不是断言为确定）。

    ADR 0104——第 1 波完成（RN-421/422/423）： ADR 0072 和 0103 从未相互沟通——RN-170 在创建时要求 bind-mount，而到 runner 的路由（RN-420）复用了同一个 workspace_mode == 'local' 标志而没有任何 bind-mount，所以真正使用 runner 仍然必须通过挂载目录的校验。workspace_mode（2 个值）变成了 execution_mode（container/mounted/runner，migration 0048）——RN-170（现为 RN-422）只对 mounted 生效；runner 诞生时路径只做词法校验（没有 I/O），workspaceVerifiedAt: null，当某个 runner 连接并在主机上确认路径时提升为已验证（POST /internal/projects/:projectId/workspace-verification，RN-423）——runner 是路径的事实来源，会覆盖向导中输入的内容。Engine.Actions.TerminalExecutor.decisao_de_execucao/1 获得了四个出口：只有在 workspace 已验证且 runner 已连接时才路由；两者缺一时显式拒绝——从不退回到 mounted 的 System.cmd/bind-mount，对 runner 项目来说那并不存在。

    实现中的发现，更正 ADR（ADR 不被编辑——更正位于这里和 backlog.md）： ADR 0104 中所说的已有项目在三种模式之间的转换“开始被允许而无需重建项目”是不正确的。UpdateProjectDto 仍然故意排除 executionMode/workspacePath——这不是简单的 PATCH（worktree、permissions.json 和 engine 的缓存都指向旧的范围）。第 1 波只交付了创建时的三值字段；已有项目的转换是未来的波次，有自己的设计，尚未计划。runner 的 backlog：第 2 波（PAT，ADR 0105）关闭了阻碍 npm publish @brabo/runner 的条目，第 3 波（ADR 0106）交付了分发本身——tsup 把 apps/runner 打包成单个 dist/index.cjs（node-pty 作为必需的 external，原生绑定），由一个独立的 workflow（publish-runner.yml）在每个最终 tag 上发布，与 release.yml 并行。经实际测试的真实发现：index.ts 的自动运行守卫需要对 process.argv[1] 使用 realpathSync——没有它，当 CLI 通过 npm install -g 安装的 bin 调用时 main() 从不运行（符号链接，process.argv[1] 从不通过 realpath 解析，而 import.meta.url 总会解析）。声明的运维待办：真正的发布需要产品所有者创建 npm 的 Automation Token 并配置 secret NPM_TOKEN——没有它，workflow 会发出警告并跳过，从不失败。按 {project_id, machine_id} 的排他性继续推迟，直到真正出现第二个并发开发者；尽力而为的 guard.ts 是重申的不变量，而不是缺口。参见 ADR 0104/ ADR 0105/ ADR 0106。

    开发工具——pnpm bootstrap

    scripts/dev/bootstrap.sh 中的终端菜单，汇集日常要做的事：Docker、K8s、Database 和 Test。它之所以存在，是因为这些命令位于三个互不相通的地方——package.json、Makefile 以及 deploy/k8s//docker/ 中的脚本——而死记硬背的知识会腐烂。

    它不重新实现任何东西：每个叶子都调用已有的命令。--print-commands 模式在没有 TTY、不执行的情况下解析整棵树，测试（scripts/dev/bootstrap.spec.ts）就运行在它之上——TUI 无法做单元测试，但菜单→命令的映射可以，而出错的正是它。零新依赖；颜色取自 design/tokens.css，以 24 位 ANSI 输出，并降级到 256 色和无色。

    正在执行的命令的输出是可滚动的（SGR 鼠标滚轮、j/k、PageUp/PageDown、G 回到末尾）。缺的不是读取滚轮：而是偏移——tail -n 只会显示末尾——所以窗口变成了用 sed -n 'a,bp' 截取的片段，可以通过 --print-window 在没有 TTY 的情况下测试。页脚会说明两个后果：向后滚动会冻结窗口（像 less +F 一样，否则 5 Hz 的重绘会撤销滚动），而只在执行界面开启的鼠标追踪会在每一种退出时关闭——restaurar_terminal 中的 \e[?1006l\e[?1000l，由 EXIT trap 覆盖。转义解析器是通用 CSI 的（读取到结束字节为止）：读取固定的两个字节会把序列的其余部分留在缓冲区中，而菜单把 [1-9] 当作选择，滚轮一转就会触发菜单项。

    记录的三项决定：Create 从零置备，Deploy 发布到已存在的环境（所以只有 Deploy 可以按服务选择）；在 K8s 中只有 All 可用，Api/Engine/Web 显示为禁用而不是消失，因为菜单应该说出产品不做什么；Database › Delete 会重建 pgvector 扩展，因为 docker/postgres/init.sql 只在卷首次初始化时运行——单纯的 DROP SCHEMA 会让下一次 migration 失败，而由于 engine 共享同一个数据库，恢复需要 db:migrate 和 engine:migrate。

    Docker › Reset total（scripts/dev/reset-total.sh）把整个序列合并到一个叶子中——preflight、up --build --wait（Compose v2.17+ 的 --wait 就是“直到全部健康”，无需手写健康检查循环）、与 Delete 相同的 DROP SCHEMA、db:migrate + engine:migrate 以及种子——带有自己的确认界面（confirmar_reset，要求输入 RESET），不同于 Delete 的确认界面（要求输入数据库名称），并且没有 Delete 的“postgres 已运行”前提，因为正是这个命令从零启动 compose。种子 （apps/api/src/db/seed.ts）增加了一个从 .env 激活 provider 凭据的步骤，复用 LLM smoke 已在使用的同一组 <PROVIDER>_TEST_KEY 变量 （apps/api/test/infrastructure/llm/*.smoke.spec.ts）——一个命名约定，两个使用方；没有定义变量的 provider 不会加入，也不报错，凭据归属 OWNER（RN-058）。

    第一次运行重置时的两个发现，而不是因为这一项本身——两个都不是假设的，两个都破坏了真实执行：

    1. gemma:1b 在 Ollama 的 registry 中不存在（manifest unknown——只有 gemma3:1b 存在），所以 ollama-model-loader 总是失败，--wait 从不以绿色结束。在以代码形式携带错误值的六个地方修正——docker-compose.yml/.prod.yml、 .env.example、docker/ollama/pull-models.sh、 scripts/dev/verificar-modelos-ollama.sh、 deploy/k8s/base/ollama/job-model-loader.yaml 以及 docs/business-rules.md 中的 RN-415——不触碰 ADR 0099/0100（已接受），也不触碰 CLAUDE.md 同一节中的历史叙述，它们描述的是当时请求/决定的内容，而不是当前的运维值。
    2. 更严重，也更久远——Database › Delete（第 3.4 项，自菜单创建时就存在）从未真正删除：DROP SCHEMA public CASCADE 触及不到 engine.*（Ecto/Oban 位于自己的 schema engine 中），也触及不到 drizzle.__drizzle_migrations（drizzle-kit 的控制表位于自己的 schema drizzle 中）。结果：mix ecto.migrate 在幸存的 engine 表上撞到 duplicate_table，而 pnpm db:migrate——更糟，没有任何错误——看到 drizzle-kit 的控制表完好，断定已经全部运行过，于是没有重建任何 api 的表。Delete/Reset total 现在也会删除 engine 和 drizzle，按此顺序，在 public 之前。

    分组标签页、项目级 PR、通过 Runner 的本地目录、PO 轮播（2026-08-20）

    五个独立波次，按争用文件并行运行，来自对项目界面的真实使用——没有一个是事先计划的。同一计划的第六波（产品和文档的完整翻译，i18n）比五波加起来还大；它的基础（第 6a 波——机制，尚无内容翻译）已经关闭：web 中的 react-i18next+i18next （en 成为应用的默认语言，pt-BR 保留——RN-425）、users 中嵌入登录/refresh payload 的 locale 列、证明该机制的新 AccountPage（/account），以及带有 i18n.defaultLocale: 'en'/locales: ['en', 'pt-BR'] 的 Docusaurus——docs/ 当前的 pt-BR 快照已保存在 website/i18n/pt-BR/docusaurus-plugin-content-docs/current/ 中。第 6b 波（界面的批量提取 + docs/ 的翻译）在 2026-08-22 以四条并行前线取得了很大进展——各前线的细节见 CHANGELOG.md（Unreleased/文档）——但仍未关闭：还缺 docs/business-rules.md（只翻译了 front-matter；包含数百条 RN 的正文仍 100% 是葡萄牙语——这是整个文档中最大的文件，增长速度快于顺手翻译的速度）以及一小部分较小的 .tsx 组件。真正关闭时，本节会加入最终总结，CLAUDE.md 的其余部分（Stack、“文档”）也会全面修订，以记录英语真正成为主要语言。

    • 分组的标签标尺：11 个零散标签页变成顶部的 6 个——概览、Agentes ▾（执行者、Criativo、聊天、Insights）、Dev ▾ （代码、PR、审批）、Documentação ▾（Backlog、架构）、花费、配置——通过新的 GroupedTabs（apps/web/src/components/ ui/GroupedTabs.tsx），构建在通用 Tabs 之上，后者在其他界面中继续不分组。ChaveDeAba 仍然是扁平的——只有呈现被分组，以免改动 ?tab= 深链接。聊天和 Chat RAG 变成一个标签页（ProjectChatShell.tsx），带有内部分段控件（"Conversar"/"Buscar"）——两者之间的业务区别（RN-202：对话会激活 agent 并在每个回合消耗 owner 的密钥；RAG 是对索引的读取，没有 agent）没有改变，只是 UI 容器变了。
    • PR 标签页，项目级：ProjectApprovalsTab 把“审查中的 PR”限定在最近的会话——一旦新会话提议了另一个 PR，旧会话中某个 PR 的审查就会从界面上消失。新的 prs 标签页直接从 git provider 列出（从不按会话），并通过新的 findPendingByProject 与待处理的 proposed_action 交叉，它位于已有的按会话方法旁边——决定使用动作自身的 sessionId，从不使用 latestSession（RN-423）。它是 UI 上第一个真正产出 git_merge 的地方；受保护分支锁（RN-154）仍然是绝对的、未被触碰——“Merge”按钮只提议，人工审批仍是执行的唯一途径。
    • 架构标签页：从概览中提取（module_map、C4 图、ADR、待办），概览保留一个精简摘要 + 链接。设计系统中的第一个 lightbox——Modal 获得了 size="full"——用于放大 C4 图（SVG，无损）（RN-424）。
    • 通过 Runner 浏览本地目录（RN-422，ADR 0104）：修订 ADR 0072（它曾明确拒绝目录选择器）而不编辑它——浏览是存在的，但通过 Runner，它已经以用户在自己机器上的真实权限运行，从不通过 api 枚举容器的文件系统。现有通道上的两个新事件（fs_list_dir/fs_home_dir），engine 纯中继，与 PTY 模式相同。FolderBrowserModal 在项目已存在的地方可用。在创建时（NewProjectWizard.tsx），这个缺口一直声明到 ADR 0108：在 mounted 模式中项目仍只在确认时诞生（路径校验在那里会触及磁盘），但在 runner 模式中，“Procurar pasta...”开始提前创建项目——通过身份快照复用，而不是每次点击都重复创建——以便在确认之前锚定通道的 ticket（RN-437，ADR 0108）。新的 RunnerOnboardingPanel（与终端标签页共享）取代了之前原始的 <code>。apps/runner 有了 README——真正发布到 npm/打包签名二进制仍然超出范围，在 README 中声明。目录浏览器本身变成三栏（快捷方式、单击选择/双击进入的列表、详情面板——RN-436），遵循产品所有者的视觉参考。

    第 28 阶段（第 5 次会话）——本地 agent 的 join 不再沉默（RN-514，ADR 0147 第 1 点）

    产品什么都没签名：.github/、scripts/ 或 docker/ 中不存在 cosign/sigstore/attestation，唯一的来源证明是 runner 的 npm 包的 --provenance。release.yml 发布四个镜像时没有 id-token: write；build-runner-binaries.yml 用 gh release upload 上传五个二进制，别无其他——而已有的 sha256sum -c 验证的是第三方二进制，这是仓库懂得应用、却从未应用到自己身上的模式。现在镜像按 DIGEST 签名（从不按 tag，那是可移动的指针），二进制获得一个已签名的 checksums.txt，由一个等待矩阵完成的 checksums 作业产生——不是五个签名，因为验证了四个而忘了第五个的人不会知道自己忘了。该作业故意是 if: always()（矩阵为 fail-fast: false），并且点名清单没有覆盖的内容。两个 workflow 都先验证再发布。按本仓库的历史选择 keyless：私钥会是又一个 CI 机密，而 PAT 已经静默过期过一次（ADR 0139）。验证流程在运维手册中，两个 --certificate-* 标志为必需——没有它们，cosign 会接受任何人的有效签名。为镜像和二进制关闭 BRB-005；操作系统代码签名和下载代理被排除在外，已声明

    第 29 阶段（第 3 次会话）——还不会安装的安装程序（RN-526，ADR 0150）

    install.sh 在根目录诞生，版本化并由 Release 提供。形式是 sh -c "$(curl …)"，从不是 curl|sh，原因是机制上的：用管道时，进程的 stdin 就是下载内容，每次 read 都会读到脚本自身的字节或遇到 EOF——一个不提问的安装程序会自行决定在别人的机器上把目录创建在哪里。它验证自己的来源（RN-524 的 checksums.txt 签名，以及它自身在已验证清单之内的哈希），使用固定版本的 cosign，并以 sha256sum 对照写在脚本中的哈希检查；检测会在提问之前点名它发现的东西；没有 TTY 时报告并以 0 退出；并且从不删除用户目录——项目 base 和镜像目录不在任何确认的范围之内，依据镜像的规则（RN-516）。标记文件在 $XDG_STATE_HOME/brabo/ 中，从不在 ~/.brabo/ 中，后者是按项目的。这个版本不安装任何东西，并且会说明这一点，而不是沉默地结束。 --print-plan/--print-state 在没有 TTY、没有网络、没有副作用的情况下公开决策——以 bootstrap.sh 的 --print-commands 为模板，测试方式相同。运行时发现两个 bash bug，属于同一类：在 set -e+pipefail 下，结果为假的 [ cond ] && 赋值 会杀死脚本，一个没有匹配的 ls 会让整个命令替换失败——而在一个正常情况就是“什么也没找到”的函数中。仓库根目录没有被任何 docmap 覆盖（根目录的 glob 是字面名称）；instalador 规则诞生
