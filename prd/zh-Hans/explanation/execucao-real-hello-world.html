    真实执行——hello world

    2026年8月5日 的记录：描述当时的 Brabo

    智能体链第一次使用 API 模型端到端运行，在一个带有真实 GitHub 仓库的新项目中。目标是找出真实使用中什么会坏。这不是第 13b 阶段的正式度量，因为中途 engine 被重启了多次。

    agent 链第一次以 API 模型端到端运行，代替本地的 Ollama。新项目（Hello API），GitHub 上的真实仓库，provider OpenRouter，模型 ~deepseek/deepseek-v4-flash-latest。

    目标不是交付 hello world。而是发现当产品像用户那样被使用时什么会坏——这一点它做到了，而且数量可观。

    这次执行**不是** FASE 13b 的官方测量

    中途 engine 多次重启，以加载执行本身所要求的修正。“零重启”标准已经丢失，下面的表格有意测量的是一次坎坷的运行。真正有效的测量仍需进行，在一切都已修正且没有中断的情况下。

    链走到了哪里

    步骤 结果
    GitHub 开通 ✅ daneiel/hello-api，Gitflow 的 5 步中完成 4 步
    Criativo ✅ 4 条业务规则，带可追溯性
    就绪 → brief ✅ product_brief 引用了这 4 条规则
    PO ✅ 1 个史诗，4 个带 RF/DOR/DOD 的故事
    手动晋升 ✅ 4 个故事由用户晋升（RN-048）
    Arquiteto ❌ 从未接到接力棒
    Dev、PR、gate ❌ 未达到

    bootstrap 的第 5 步（保护分支）因 GitHub 套餐的限制而失败：私有仓库在免费套餐中不接受分支保护。这不是产品的缺陷——但产品把它当作硬失败，没有事先提醒。向导开始在做选择时提醒。

    这次执行证明了什么，以及没有证明什么

    证明了 Criativo → PO 链在 API 模型下可以工作，并产出真实质量的构件：backlog 带着闭合的可追溯性产出，故事的 DOR 写着“formato e detalhes técnicos definidos pelo Arquiteto”——加在 Criativo 上的边界穿过了 brief，到达了 backlog。

    证明了产品在三个不同的层（回合、工具、进程）吞掉错误，而正是这一点让缺陷保持不可见。这三层现在都会说话。

    没有证明 Arquiteto、dev、远程 PR 以及 gate。没有证明任何关于一次完整执行的真实成本的东西。而且由于中途重启，它不能作为 FASE 13b 的测量。
