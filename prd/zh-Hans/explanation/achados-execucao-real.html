    流水线真实执行中的发现

    2026年8月5日 的记录：描述当时的 Brabo

    一次真实执行会话的发现，该会话通过浏览器、使用 API 模型和真实的 git provider 进行。每一项都有可证明它的 file:line 或事件。阻塞性的当场修复，并附有具名 PR。其余的进入了第 13c 阶段的分诊。

    在 2026-08-05 通过浏览器引导的一次执行会话中调研，使用 API 模型（非本地）和真实的 git provider。这是 FASE 13c 分类的输入：每个条目都有证明它的 arquivo:linha 或事件，没有一个是"顺带"修正的——已关闭的那些 都有命名的 PR。

    通过向导在 GitHub 上创建（而非采用）的项目。真实仓库：daneiel/hello-api，私有。向导的会话： f15b0cc9。健康的会话：36abf7e7。

    执行期间修正的（曾阻塞）

    1. 测量器没有在测量（PR #136，已合并）——db.execute 被当作数组解构 + 智能体从事件的执行者而不是载荷中 读取。
    2. llm_turn_stream 没有 receive_timeout（PR #137，已合并）——落到了 Req 默认的 15 秒；4 个会话型 智能体只走这条路。
    3. ApprovalCard 让会话界面崩溃（待提交）——web 的 ActionType 是后端的子集；对 git_repo_create/git_branch_create/git_branch_protect，ACTION_ICON[actionType] → undefined，而这 正是每个在 provider 上创建的项目都会生成的。"通用回退"只存在于注释中。它只是没有出现在采用的项目 中（没有 bootstrap）。

    未关闭的——供 13c 分类

    A. 配置阶段的会话诞生时在 engine 中没有进程（严重）

    已关闭——成为了 RN-067。下面引用的四个调用点改为通过 CreateSessionUseCase 创建会话（provision-repository:119 和 :125、adopt-repository、 activate-execution），而规则声明它是创建会话的唯一地方。之所以保留记录，是因为下面的对比证明是让缺陷 变得可见的东西。

    CreateSessionUseCase 是唯一在 outbox 中发出 session.created 的地方。以下这些直接在仓库中创建会话，跳过了 它：

    • apps/api/src/application/use-cases/git/provision-repository.use-case.ts:112 和 :121
    • apps/api/src/application/use-cases/git/adopt-repository.use-case.ts:176
    • apps/api/src/application/use-cases/execution/activate-execution.use-case.ts:156 ← 这就是 DEV AGENTS 运行的会话

    效果：engine 永远不知道会话存在 → 永远的 REFUSED JOIN，没有通道，没有实时更新，没有心跳，会话永远不会 关闭（永远保持 active）。UI 只在控制台中抱怨。

    对比证明：

    会话 session.created engine.session_states 通道
    向导 f15b0cc9 否 空 REFUSED JOIN
    正常路由 36abf7e7 是 active JOINED

    B. 启动模型（用户的决定）

    会话总是诞生在 workspace 的默认值上（llama3.2:1b，本地）——ADR 0020 在语义步骤中禁止本地 7B/1B，在两个会话中 都必须手工更换。请求：可配置的启动模型，在这个场景下继承 Criativo 的模型，因为它总是项目的入口。

    C. 说话的是模型，而不是智能体（缺陷，由用户指出）

    实时传输的气泡带着模型的名字作为标签（"DeepSeek V4 Flash Latest"）；只有当持久化的事件到达时，智能体 （po）才出现。效果：错误的名字先出现，消息在屏幕上重复（流的气泡 + 事件的气泡）。流没有与持久化的事件 对账。

    D. 不可能的步骤把向导卡住而没有出路

    Proteger branches 在免费计划的私有仓库上失败——向导本身事先就提醒了这一点。但之后提供的唯一操作是 "重试"，它总是会失败。缺少确认并继续的方式。

    E. 仓库预览在撒谎

    apps/web/src/routes/NewProjectWizard.tsx:331 有硬编码的 repo: brabo/{slug}。真正的 owner 来自 PAT （createForAuthenticatedUser），也就是 daneiel/hello-api。这个错误一直到达确认界面。

    F. 向导宣布了 rc

    "Política de branches" 步骤把 rc 列在永久分支中，并在级联中列出 rc ← qa。现行策略只有 dev/qa/main；rc 的回归在 ADR 0030 的 backlog 中。

    G. Criativo 的邀请在已创建的项目中不出现

    空状态 "A vez é sua" 只在对话流为空时渲染。在已创建的项目中，对话流已经有 bootstrap 的卡片，因此用户收不到 任何邀请。

    H. 通用的活动信息流

    bootstrap 的 10 个事件全部显示为 "atividade em system"，而不说明发生了什么。

    I. 动作卡片显示会话的当前模型

    更换会话的模型会追溯地改写旧动作卡片的标签。token_usage 冻结了正确的价格；只是界面的问题。

    J. Psicólogo 在空会话中运行

    已关闭——成为了 RN-079。分析只在有可分析的事件时才运行，而 "可分析"排除了 bootstrap 的机器步骤和分析者自己的痕迹——没有第二个排除，第一次分析就会让会话永远显得有内容。 没有材料时，发出 psychologist.analysis_skipped，不花任何钱。发现中的会话被复现为测试（14 个事件，没有一个 可分析）。 在刚打开的会话 b2fceb9e 中：它收到了上一个会话的假设和新会话的日志（空的），试图引用不存在的 seq 60-78， 证据被拒绝 2 次后放弃了（psychologist.analysis_failed）。验证拦住了编造——但在没有事件的会话上运行分析是白白 花钱。

    K. 重复的业务规则没有去重

    部分关闭——成为了 RN-080。完全重复（标题相同，忽略大小写、 重音和空格）在发出时被拒绝，范围是项目——它正是在会话之间产生的。语义重复仍未关闭并如此声明：把 "Saudação com nome" 与 "Quem chama pode se identificar" 区分开是判断，不是 if。 在同一个项目中运行两次 Criativo 留下了 10 条规则，5 条孤立（"descoberta — sem história"）。这是我的剧本造成的 效果，不是产品的，但它表明既没有去重也没有提醒。

    L. 底部按钮变得过时

    在对话流已经交给 PO 之后，它仍然是 "Estou pronto para produzir"。

    按设计工作的（也要记录）

    • RN-059：持久的 agent.error，带 origem: infra，智能体在对话流中说话并回到 idle（在 15 秒超时中看到 2 次）。
    • Psicólogo 的证据验证拒绝了编造的事件 id。
    • GitHub 上的 Gitflow bootstrap：5 步中 4 步，真实仓库带有 main/dev/qa。
    • proposed_action 管道：bootstrap 的 6 个动作，由策略自动批准。

    M. ARQUITETO 看不见自己的 module_map（P1——这一轮的失败）

    已关闭——成为了 RN-066，并在本页最后一节中在生产中得到确认： assign_story_modules 调用 4 次而不是 18 次，零个编造的名字，1 个 module_map 而不是 4 个。

    会话 36abf7e7，seq 80-131。Arquiteto 发出了映射（模块 saudacao 和 api_http），然后无法重新读取它。 没有读取现行 module_map 的工具，而 assign_story_modules 的拒绝不返回有效的名称。结果：暴力尝试。

    18 次以上的猜测：api、core、http、greeting、domain、web、hello-api、hello、greeting-api、 saudacao（碰巧猜中）、app、server、publico、public-api、api-publica……

    用它自己的话说（seq 94、99、124）：

    "os nomes que tentei (api, core) não batem. Vou descobrir os nomes válidos testando candidatos plausíveis" "Preciso descobrir os nomes reais dos 2 módulos. Vou testar candidatos adicionais."

    三个后果，按严重程度排列：

    1. 错误的数据，被宣称为正确。 4 个用户故事都落在 ["saudacao"] 上，包括 ENDPOINT 的那个。api_http 没有 任何用户故事。而结果（seq 130）断言："Todas as 4 histórias foram vinculadas com sucesso aos módulos." 日志以一个自信的谎言结束。
    2. 破坏下游的执行。 activate-execution 为每个模块启动一个 dev agent。一切都在 saudacao 中时，模块 api_http 收不到智能体，设计的架构也不是将要构建的那个。
    3. assign_story_modules 没有记录任何 tool.result。 整个循环在 event log 中不可见——只能从重复的 tool.call 推断。

    循环的成本：Arquiteto 的 9 次 LLM 调用，27.804 输入 / 8.012 输出。会话总计：7.271 micros（US$ 0,007）——便宜 只是因为它是 flash 模型。

    module_map 的循环（PR #135）是这个问题的症状：Arquiteto 重新发出映射，正是为了试图固定它无法读取的名称。 #135 关闭了数据损坏；盲目仍然存在。

    N. 执行那一半只在 local provider 下工作（P1，阻塞 13b）

    Engine.Projects.ProjectRepository.get_local_repo_path/1 对任何不是 local 的 provider 返回 {:error, {:unsupported_provider, "github"}}。这在 moduledoc 中被记录为范围削减：

    "Só suporta o provider 'local' (github/gitlab remotos ficam fora de escopo do executor de terminal por ora)" — apps/engine/lib/engine/projects/project_repository.ex:25-27

    五个调用点依赖它：

    • lib/engine/dev/worktree_manager.ex:20——dev agent 的 worktree
    • lib/engine/actions/terminal_executor.ex:39——命令执行
    • lib/engine/gates/diff.ex:17——QA 和 SecOps 读取的 diff
    • lib/engine/harness/project_context.ex:30——项目上下文

    观察到的效果：我在 GitHub 项目上激活了执行，3 个 dev agent 启动了，各领取了一个 task，然后 3 个在同一秒内以 falha ao preparar o worktree 被阻塞。

    不对称是关键：api 通过 HTTP 与 GitHub 对话（是它创建了仓库、提交了模板并创建了 dev/qa）。engine 在 文件系统上工作，只认识本地 bare repo。因此 GitHub 上的项目完成了会话那一半（Criativo、PO、Arquiteto）和 bootstrap，但没有完成构建那一半。

    对 FASE 13b 的后果：CLAUDE.md 的剧本（"projeto ADOTADO do fork via GithubProvider remoto, DevAgent real, dev implementa → PR remota → gates"）今天无法执行。这不是顺带的 bug：支持远程需要克隆、engine 内部的凭据和 推送——是一个带 ADR 的功能。

    O. dev agent 诞生在本地模型上（与发现 B 同根）

    三个 dev agent 以 Llama 3.2 1B (local) 启动，继承自 workspace 的默认值。ADR 0020 在语义步骤中禁止小型本地 模型，而写代码的 dev agent 是存在的最昂贵的语义步骤。

    P. 没有来源的阻塞事件

    {"origin": null, "reason": "falha ao preparar o worktree", "diagnosis": "{:unsupported_provider, \"github\"}"}。CLAUDE.md 要求每个失败结果都记录来源（infra | modelo | código | política）。这里是 código（产品的已知限制），而它是 null。诊断救了场，但规则没有被遵守。

    Q. 带"不确定来源"的 agent.error

    在 Criativo 中，轮次被中止：对话流显示 falha · origem indeterminada。RN-059 起了作用（持久的错误，智能体 说话了，干净的恢复），但"不确定"不是四种来源之一——它是 ADR 0020 禁止的排除法诊断。

    R. PO 生成了重叠的用户故事

    部分关闭——成为了 RN-081。标题相同的被拒绝；对其引用的规则不增加 覆盖的用户故事变成 backlog.story_overlap_warned，是提醒而不是阻止。这个发现中确切的那一对仍然通过—— 同一端点的不同标题和理由，没有任何机械的东西把它们联系起来。有一个测试断言这个限制，使它可见而不是隐含。 "Endpoint público de saudação determinística" 和 "Endpoint público GET /hello que responde saudação imediata" 覆盖同一个端点。没有去重也没有提醒。

    hello-limpo 的执行（项目 9c7c84f0，会话 1f94de49）——2026-08-06

    真实的 dev agent，通过 OpenRouter 的 DeepSeek V4 Flash，审批管道开启，每个动作都手工决定。task 是 "Expor rota GET pública /api/saudacao"。它从未开始：18 个轮次，292.211 个输入 token，US$ 0,0275，零行代码 被写下，这一轮以 provider 的错误结束。

    S. 累积的上下文超出 provider 的限制并杀死执行（P1）

    在第 18 个轮次，对模型的调用返回 {413, %{"message" => "request entity too large", "statusCode" => 413}}，ToolLoop 无法继续，task 被阻塞 （dev.blocked、artifact.task_blocked，seq 151–152）。

    原因是机械的且累积的：每个终端命令都把完整输出倒进循环的历史中，而历史随之后的每一个轮次一起传送。 token_usage 中记录的最大成功请求是 28.993 个输入 token；失败的那个根本没有记录用量。溢出的是请求的 字节大小，而不是上下文窗口——一个输出很长的 find 或 git ls-files 按字节计比按有用 token 计重得多。

    这与 ADR 0055 直接相关，从一个 ADR 没有预见的角度： 审批阶梯不仅让执行更昂贵，它还杀死执行。每次向用户提问都会推动智能体再执行一个探索性命令，其输出永远进入 历史。这场赛跑在第一行代码被写下之前就以 413 结束。

    分类需要决定的是修复归谁——ContextManager（按大小而不只是按时间压缩或截断工具输出）、终端执行器（每次输出的 字节上限，带截断标记），还是两者。目前路径上的任何地方都没有上限。

    • 证据： 会话 1f94de49 的 session_events seq 150–152；执行者 dev-http-api 的 token_usage。

    T. 故障来源仍在四种之外（P 和 Q 的复发）

    发现 S 的 dev.blocked 记录了：

    {
  "origem": "indeterminada",
  "reason": "parou sem concluir nem reportar bloqueio",
  "diagnosis": "falha na chamada ao modelo: {413, %{\"message\" => \"request entity too large\", \"statusCode\" => 413}}"
}

    这不是新发现：它是同一条规则被违反的第三次，因此作为复发而不是单独条目记录。P 在一个 dev.blocked 中抓到了 origin: null；Q 在一个 agent.error 中抓到了 "indeterminada"。这里两者相遇：阻塞事件，值为 "indeterminada"。

    这次出现增加了什么、使这个案例比之前的更有力：来源是可以轻易推导的。provider 的一个已知 HTTP 状态就是 modelo，没有任何歧义——diagnosis 字段本身就在 origem 放弃的同一行中说出了它。这不是边界情况，而是错误 路径没有看自己刚刚写下的东西。

    reason 也在撒谎："parou sem concluir nem reportar bloqueio" 描述的是沉默，而发生的是一次原因已识别的失败。 只在面板上读 reason 的人会得出模型迷路了的结论。

    • 证据： 会话 1f94de49 的 session_events seq 151。
    • 被违反的规则： CLAUDE.md（"todo desfecho de falha registra a ORIGEM — infra | modelo | código | política — nunca diagnóstico por eliminação"），来源于 ADR 0020。

    U. 终端执行器没有项目边界（P1）

    在执行动作的容器内部，/workspace 是 Brabo 自己的 monorepo——不是项目的 worktree，后者位于 /data/project-workspaces/<projectId>/.worktrees/<agentId>。

    hello-limpo 的 dev agent 在那里花了好几个轮次，以为那是它的项目：读了 apps/engine/mix.exs，甚至提议 cat lib/engine/actions/git_executor.ex 和 sed -n '1,120p' lib/engine/dev/context_builder.ex——正在执行它的 平台的 git 执行器和上下文构建器。

    而范围不止于 Brabo。对 /data/project-workspaces/*/ 的一个 for 列出了另一个项目 （dbd3e508-e0c7-4e29-b134-5d393f518269）的 worktree 及其提交和文件；智能体提议的下一步是进入它读取 git remote -v 和 git log。这被手工拒绝了。

    这一切都不是模型的恶意：它在寻找自己的项目，而文件系统不告诉它项目在哪里结束。在多租户部署中，同样的命令会 读取另一个客户的仓库。

    AB. GATE 智能体不会等待审批——变成 infra 失败（P1）

    已关闭——ADR 0057。gate 智能体现在会挂起并恢复，就像 自 ADR 0052 起的 dev agent：子智能体返回带有整个 ctx 的 {:awaiting, ...}，QaLeadServer 保存进行中的 状态，为子智能体订阅 Wake，并在决定到达时从停下的地方继续该领域。

    AC. 重定向（2>/dev/null）让任何命令都无法批准（P1）

    两个部件都已关闭。

    1. parseCommand 不再把 >/>>/< 当作分隔符——它们不串联任何命令。目标仍然作为片段的词元保留， 这是有意的：正是这样 echo x > /etc/passwd 仍被范围上限拦住。动词变得正确，而路径并没有因此放开。
    2. /dev/null、/dev/stdin、/dev/stdout 和 /dev/stderr 不再算作用户路径。列表就是这些，而不是 整个 /dev——有一个测试断言 /dev/sda 仍在范围之外，因为放开 /dev 会把一个麻烦换成一个漏洞。

    在两个方向上经变异验证：放宽 /dev 会让磁盘的测试失败，关闭串联会让 11 个测试失败。

    在 13b 的第 7 次执行中发现，那是在把允许列表扩展到 25 个动词之后。QA 智能体运行了：

    ls -la && echo "---" && cat package.json 2>/dev/null; echo "---"; ls *.md 2>/dev/null

    所有动词都已放行——ls、echo、cat。即便如此它还是变成了 require_approval。对这个命令运行纯函数：

    segmentos: [["ls","-la"],["echo","---"],["cat","package.json","2"],["/dev/null"],…]
tokens de caminho: ["/dev/null","/dev/null"]
no escopo? false

    parseCommand 把 > 当作片段分隔符，因此 2>/dev/null 变成一个独立的片段。这以两种独立的方式出错：

    1. 片段 /dev/null 的"动词"就是 /dev/null 本身，它永远不会在 allow 中——而复合命令要求每个片段都被 放行；
    2. /dev/null 是项目文件夹之外的绝对路径词元，因此 RN-075 的上限 把 auto_approve 降级。

    影响很大，因为 2>/dev/null 是惯用法。 模型一直用它来静默预期的错误。实际上，任何带输出重定向的命令 按策略都无法批准——只能靠人类点击通过。

    这不是列表中缺了一个动词：是命令的形式。扩展允许列表解决不了，第 7 次执行就是证明——放行了 25 个动词， 还是卡住了。

    两个不同的部件需要分类：

    • command-matcher.ts 中按 > 的分段（预先存在的，而且有争议：重定向不像 && 和 | 那样是命令的组合）；
    • 把 /dev/null 当作用户路径的范围上限（path-scope.ts，来自阶段 F）。

    AD. 智能体把命令包在 bash -lc 里，而允许列表对此没有答案（P1）

    13b 的第八次执行，发现 Y、AA、AB 和 AC 已经修正。dev agent 只做了一次工具调用：

    bash -lc npm test --silent

    动词是 bash。它不在 allow 中，变成了 require_approval。

    拒绝是对的，而且它对很重要。 放行 bash 会让整个允许列表失效：bash -lc <qualquer coisa> 绕过动词检查， 包括内置的 deny。一个接受 bash 的允许列表就不是允许列表。

    但这闭合了第 6、7、8 次执行一直在构建的论证：

    执行 卡在哪里 我做了什么
    第 6 次 head 不在列表中 扩展到 25 个动词
    第 7 次 2>/dev/null（形式，不是动词） 修正了解析器和范围（AC）
    第 8 次 bash -lc（调用方式） —

    每一轮都揭示了一个新类别，没有一个是"缺了一个动词"。动词允许列表不收敛，面对一个自由选择如何调用它想 运行之物的智能体——而这三种形态（动词、形式、调用）是不同的空间，而不是一个列表中的点。

    这不意味着：允许列表是错的。它恰好做到了它承诺的，对 bash 的拒绝证明了边界有效。它做不到的是在没有人类 干预的情况下使智能体自治成为可能。

    分类的两个方向，它们在性质上不同：

    1. 可挂起的 gate 智能体（发现 AB，未关闭的那一半）。它不消除审批——它让智能体等待审批而不是死掉，然后 用户的点击是解锁而不是失败。这是 ADR 0052 已经为 dev agent 打开的路径。
    2. 按智能体画像的策略。 在隔离 worktree 中的 dev agent 与触碰用户 workspace 的智能体不同。目前两者使用同一个 permissions.json。这是需要 ADR 的产品决定。

    AE. QA 智能体试图修复它所评判的代码（P2）

    AF. 两个 dev agent 一起启动时会损坏彼此的 workspace（P1）

    Engine.Actions.Workspace.ensure!/4 用 :global.trans 按项目串行化工作树的初始化——正是为了 N 个 dev agent 在执行激活时启动的情况。锁是对的。决定是否值得去拿锁的守卫，不对。

    为什么它穿过十次执行都没有出现。 只有当第二个智能体在初始化期间到达时窗口才存在，而激活只为每个模块启动 一个智能体。module_map 中只有一个条目时从来没有第二个智能体。这个缺陷属于 Fase 14d（并行），需要第一次真正 并行的执行才能显现。

    这与 Fase 14d 自身三个缺口的模式相同，记录在那里：测试部件不等于测试通往它的路径。 这里部件（锁）是正确的 并经过测试；做出错误决定的是通往它的路径。
