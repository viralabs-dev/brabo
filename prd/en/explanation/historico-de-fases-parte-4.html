    Phase history, part 4: from the local runner onward

    Record from September 11, 2026: describes Brabo as it was on that date

    From the local runner (ADR 0102 and 0103) onward, plus the section migrated from the CLAUDE.md index, where phases 28, 29 and 30 are. Text moved without rewriting from the Phase history. What holds today lives in the RNs and the ADRs.

    Local runner — execution on the user's machine (RN-418/419/420, ADR 0102/0103)

    The product owner's request: an agent running on the USER'S MACHINE, in the project's local folder, through the user's default terminal — plus a real interactive terminal in the Code tab. Two changes, one depending on the other.

    Policy (ADR 0102 — a GLOBAL decision, explicitly confirmed by the product owner after an automatic security warning about the change): git push/PR/deploy (RN-106) and sudo/doas (new) leave the unconditional deny and become an ABSOLUTE CEILING — unconditional require_approval, in the SAME block and SAME pattern as the neighboring ceilings (current.policy === 'auto_approve'), never auto-approvable by agent_autonomy (wildcard "*") nor by permissions.json. The gap the original deny plugged by force was closed at the SOURCE: ApproveAlwaysActionUseCase/patternForAction refuse to write an allow pattern for an action with a git external effect or a privileged command — "always allow" approves only the instance, never the pattern, for those two cases. Without that second half, the ceiling would be decorative. sudo/doas match by VERB in comandoPrivilegiadoNoComando (external-effect.ts), scanning all the command's segments, same principle as efeitoExternoNoComando.

    Runner (apps/runner, a new Node/TS workspace, ADR 0103): a CLI (brabo-runner --project <id> --dir <pasta> --token brb_...) that the user runs on their own machine, connects to the ENGINE through a NEW Phoenix channel (/runner, topic terminal:<projectId>) authenticated by a SINGLE-USE ticket (same pattern as RN-108, but a ticket ISSUED BY THE ENGINE — schema "engine", its own migration — and requested by the api through an internal HTTP route, inverting the session ticket's flow). It runs exec (an ALREADY APPROVED agent command — the routing in TerminalExecutor only happens AFTER the usual decide()/proposed_action pipeline, never before) in the user's $SHELL, and an interactive PTY mode for the Terminal tab (pty_open/pty_data/ pty_input/pty_resize/pty_close — the engine does pure RELAY, never interprets the bytes). Only ONE runner per project (Engine.Runners.Registry, :global, exclusivity of :global.register_name/3); runner mode WITHOUT a verified workspace or WITHOUT a connected runner REFUSES explicitly — it never falls into System.cmd/bind-mount, which doesn't exist for a runner project (revised by ADR 0104/RN-423, see above; the fallback to the usual path remains valid, but only for container/mounted). PTY is an action of the authenticated USER, it doesn't go through proposed_action, but it audits (terminal.session.started/ended in the event log, even when the tab drops without an explicit pty_close).

    The runner's security boundary is NOT sandboxing — it is authentication (the CLI presents a Personal Access Token of the user's ACCOUNT) + the usual approval pipeline + the consent of the user running the CLI on their own machine, with their privileges. apps/runner/src/guard.ts validates cwd inside the root by lexical resolution, but it is declared BEST-EFFORT, not the real guarantee.

    The PAT closed the automation token gap (ADR 0105/RN-424..426). The real finding of Wave 1 — "the product has no LONG-LIVED account token mechanism for automation, so the runner replicates the browser login (cookie/CSRF persisted in ~/.brabo/runner-credentials.json)" — was closed in Wave 2: personal_access_tokens (brb_…, HMAC-SHA256+ pepper hash via hashDeToken(), never argon2 — wrong for a HIGH-entropy secret) is issued in the project's Settings, scoped to ONE project, revocable, with optional expiry. apps/runner/src/auth.ts lost completely the interactive login, cookies and the credentials file — it only validates the format and passes on --token/BRABO_ACCOUNT_TOKEN, NEVER written to disk by the CLI. The PAT never authenticates outside POST .../runner-ticket, by CONSTRUCTION (IS_PAT_ROUTE_KEY/ @RequirePatAuth() + PatAuthGuard) — never a branch in the global JwtAuthGuard, which would let RolesGuard authorize the PAT for any route of the user's role.

    maintainer revokes another user's PAT (RN-427), closing the item ADR 0105 had declared out of scope for now (incident response — a dismissed dev with a leaking token). An extension of the same model, without a new ADR: SEPARATE routes (GET .../personal-access-tokens/all, DELETE .../personal-access-tokens/:tokenId/admin), scope by projectId instead of userId — each user's self-revocation (RN-426) doesn't change.

    @xterm/xterm/@xterm/addon-fit (web) and phoenix/node-pty (runner) are the four new dependencies — the same exception rule as mermaid (ADR 0068): dynamic import(), no eval/new Function confirmed by grep in the installed package (not a formal guarantee against obfuscation, only strong evidence — declared as uncertainty, not asserted as certainty).

    ADR 0104 — Wave 1 COMPLETED (RN-421/422/423): ADRs 0072 and 0103 never talked to each other — RN-170 required a bind-mount at creation, and the routing to the runner (RN-420) reused the same workspace_mode == 'local' flag without any bind-mount, so actually using the runner was still forced to go through the mounted-folder validation. workspace_mode (2 values) became execution_mode (container/mounted/runner, migration 0048) — RN-170 (now RN-422) applies only to mounted; runner is born with a path validated only LEXICALLY (no I/O) and workspaceVerifiedAt: null, promoted to verified when a runner connects and confirms the path on the HOST (POST /internal/projects/:projectId/workspace-verification, RN-423) — the runner is the SOURCE OF TRUTH of the path, overwriting what was typed in the wizard. Engine.Actions.TerminalExecutor.decisao_de_execucao/1 gained FOUR outcomes: it routes only with a verified workspace AND a connected runner; without either of the two, it REFUSES explicitly — it never falls into mounted's System.cmd/bind-mount, which doesn't exist for a runner project.

    A finding of the implementation, correcting the ADR (which is not edited — the correction lives here and in backlog.md): ADR 0104's sentence that converting between the three modes of an existing project "is now allowed without recreating the project" is INCORRECT. UpdateProjectDto still excludes executionMode/workspacePath on purpose — it isn't a trivial PATCH (worktree, permissions.json and the engine cache point to the old scope). Wave 1 delivered only the three-value field at CREATION; converting an existing project is a future wave, with its own design, not yet planned. Runner backlog: Wave 2 (PAT, ADR 0105) closed the item that blocked npm publish @brabo/runner, and Wave 3 (ADR 0106) delivered the distribution itself — tsup bundles apps/runner into a single dist/index.cjs (node-pty as a mandatory external, native binding), published on each final tag by its own workflow (publish-runner.yml), parallel to release.yml. A real finding tested empirically: the auto-run guard of index.ts needed realpathSync on process.argv[1] — without it, main() never ran when the CLI was invoked through the bin installed via npm install -g (a symlink, which process.argv[1] never resolves by realpath but import.meta.url always does). Declared operational pending item: the actual publication requires the product owner to create the npm Automation Token and configure the NPM_TOKEN secret — without it, the workflow warns and skips, never fails. Exclusivity by {project_id, machine_id} remains postponed until a second real simultaneous dev; best-effort guard.ts is a REAFFIRMED invariant, not a gap. See ADR 0104/ ADR 0105/ ADR 0106.

    DEVELOPMENT TOOL — pnpm bootstrap

    A terminal menu in scripts/dev/bootstrap.sh grouping what is done day to day: Docker, K8s, Database and Test. It exists because those commands live in THREE places that don't talk to each other — package.json, Makefile and scripts in deploy/k8s//docker/ — and memorized knowledge rots.

    It reimplements nothing: each leaf calls the command that already exists. The --print-commands mode resolves the whole tree without a TTY and without executing, and it is on it that the test runs (scripts/dev/bootstrap.spec.ts) — a TUI can't be unit tested, but the menu→command mapping can, and that's what goes wrong. Zero new dependencies; the colors come from design/tokens.css in 24-bit ANSI with degradation to 256 colors and to none.

    The output of a running command is SCROLLABLE (mouse wheel in SGR, j/k, PageUp/PageDown, G to go back to the end). What was missing wasn't reading the wheel: it was OFFSET — tail -n only knows how to show the end —, so the window became a slice with sed -n 'a,bp', testable without a TTY through --print-window. Two consequences the footer announces: scrolling back FREEZES the window (like less +F, otherwise the 5 Hz redraw undoes the scrolling) and mouse tracking, turned on only on the execution screen, is turned off on EVERY exit — \e[?1006l\e[?1000l in restaurar_terminal, which the EXIT trap covers. The escape parser is a generic CSI one (reads up to the final byte): reading two fixed bytes left the rest of the sequence in the buffer, and since the menu treats [1-9] as a choice, a wheel turn fired menu items.

    Three recorded decisions: Create provisions from scratch and Deploy publishes into an environment that already exists (that's why only Deploy has a per-service choice); in K8s only All works, and Api/Engine/Web appear DISABLED instead of vanishing, because the menu should say what the product doesn't do; and Database › Delete recreates the pgvector extension, since docker/postgres/init.sql only runs on the volume's first initialization — a plain DROP SCHEMA would make the next migration fail, and since the engine shares the same database, recovering requires db:migrate AND engine:migrate.

    Docker › Reset total (scripts/dev/reset-total.sh) adds up that whole sequence into a single leaf — preflight, up --build --wait (the --wait of Compose v2.17+ is the "until everything is healthy", with no health loop written by hand), the same DROP SCHEMA as Delete, db:migrate + engine:migrate and the seed — with its OWN confirmation screen (confirmar_reset, requires typing RESET), distinct from Delete's (which requires the database NAME) and without Delete's "postgres already up" precondition, because it is the command itself that brings up compose from scratch. The seed (apps/api/src/db/seed.ts) gained a step that activates a provider credential from .env, reusing the SAME <PROVIDER>_TEST_KEY variables that the LLM smokes already use (apps/api/test/infrastructure/llm/*.smoke.spec.ts) — a single naming convention, two consumers; a provider without a defined variable doesn't come in, without error, and the credential stays with the OWNER (RN-058).

    Two findings when running the reset for the first time, and not about the item itself — neither of them is hypothetical, both broke the real run:

    1. gemma:1b doesn't exist in the Ollama registry (manifest unknown — only gemma3:1b exists), so ollama-model-loader always failed and the --wait never closed green. Fixed in the six places that carried the wrong value as CODE — docker-compose.yml/.prod.yml, .env.example, docker/ollama/pull-models.sh, scripts/dev/verificar-modelos-ollama.sh, deploy/k8s/base/ollama/job-model-loader.yaml and RN-415 in docs/business-rules.md — without touching ADRs 0099/0100 (accepted) nor the historical narrative of this same section of CLAUDE.md, which describe what was requested/decided at the time, not the current operational value.
    2. More serious, and older — Database › Delete (item 3.4, existing since the menu was created) never really dropped: DROP SCHEMA public CASCADE doesn't reach engine.* (Ecto/Oban lives in its OWN schema, engine) nor drizzle.__drizzle_migrations (drizzle-kit's control lives in its OWN schema, drizzle). Result: mix ecto.migrate hit duplicate_table on the engine tables that survived, and pnpm db:migrate — worse, WITHOUT any error — saw drizzle-kit's control intact, concluded it had already run everything and recreated NO api table. Delete/Reset total now drop engine and drizzle too, in that order, before public.

    The runner's standalone binary (2026-08-23, RN-451/452, ADR 0112)

    A backlog item of ADR 0104 ("standalone binary, pkg/bun build --compile"), companion of ADR 0106 (distribution via npm). The product owner's explicit decision: a truly SINGLE binary, a complete matrix with Windows since v1 — the cheaper alternative ("binary + a node-pty-native/ folder next to it") was offered and refused.

    bun build --compile embeds node-pty's native .node through with { type: 'file' } and extracts it to a REAL TEMPORARY directory at runtime (native-pty-loader.ts) — necessary because node-pty resolves its own addon through a require() of a COMPUTED path (lib/utils.js#loadNativeModule), which Bun can't embed on its own (the build passes, the runtime throws Cannot find module, tested before designing the fix). Five platforms (linux-x64/linux-arm64/darwin-x64/darwin-arm64/win32-x64), each one built on its NATIVE runner (.github/workflows/build-runner-binaries.yml, final tag trigger, same pattern as publish-runner.yml), the binary attached to the already existing Release.

    Honest validation, per platform: only linux-x64 was actually executed in this environment (build:bin+smoke:bin green, repeatedly — it was by running the real binary that the two bugs below showed up). The other four — Windows especially, with THREE native files instead of one — were reasoned about by reading node-pty's source code, never executed on a real machine of that OS; their first real run is the NEXT version tag, not this PR. No per-platform fallback was applied preventively — nothing in this investigation PROVED that any of the five doesn't work this way; if a real tag shows that it does, that becomes a new item, not today's assumption.

    Two defects found only by running the compiled binary, not by reading the API: --external node-pty needs to be in the bun build command even without any static import of node-pty in the code — the fallback await import(...) (used only outside the binary) is discovered and embedded by Bun anyway, and fails at runtime with a misleading error; and the auto-run guard (ADR 0106) needed a second branch — process.argv[1] inside the binary is a VIRTUAL path (/$bunfs/root/...) that realpathSync can't reach, throwing ENOENT outside any try/catch before main() is attempted.

    Converting the execution_mode of an existing project (RN-447..450, ADR 0111)

    It closes the correction that the runner's Wave 1 (ADR 0104) had recorded in docs/explanation/backlog.md: item 4 of that ADR said that converting execution_mode between container/mounted/runner in a project that already exists "is now allowed without recreating the project", and that was false until here — UpdateProjectDto still excludes both fields on purpose. PUT projects/:projectId/execution-mode (maintainer, ConvertProjectExecutionModeUseCase) is a DEDICATED route, not a loosened PATCH: it orchestrates the migration instead of just switching the column.

    It refuses with 409 while any dev agent of the project (in ANY session, read straight from engine.dev_agent_states by project_id, the same path as RN-409) isn't idle — idle_tripped COUNTS as active here, unlike RN-409's "online" criterion, because the agent still has workspace_root captured in memory waiting for human unblocking (RN-447). PermissionsFileStore gained move(from, to): the content of permissions.json never changes, only the physical path, because projectScopeRoot derives from the (mode, path) pair (RN-448). Leaving container with a provisioned container, the lifecycle (ADR 0081) is taken to removed — via stopped first if it was running — BEFORE the column changes, because RegistrarTransicaoDeContainerUseCase refuses a transition outside container mode; entering container never auto-provisions (RN-449). workspaceVerifiedAt is reset on every real conversion, including going back to runner with a path that looks the same (RN-450). The same (mode, path) as today is a no-op — it doesn't even check for an active dev agent.

    Declared consequence, not hidden: the conversion NEVER copies the code already written between the old root and the new one. That is safe for what was already COMMITTED — the engine derives the worktree from the bare repo from scratch (Engine.Actions.Workspace.ensure!/4) whenever the destination folder isn't yet marked ready, so the next agent rebuilds the working tree in the new root from the real git. What does NOT survive is an UNCOMMITTED diff in the abandoned worktree — it stays orphaned on the old disk, never migrated nor deleted. The active dev agent ceiling (RN-447) reduces the risk (it never converts with a working agent) but doesn't eliminate it: an idle agent between tasks may be sitting on a dirty diff, and nothing here inspects the working tree's cleanliness before converting.

    A local folder attached as a RAG Chat reference (2026-08-23, RN-455..457, ADR 0113)

    The product owner's request: attach a folder from the user's OWN machine to a project as a READ reference for the agents — without the brabo-runner CLI (ADR 0103). Explicitly NOT project execution/workspace: execution_mode: runner (ADR 0104) needs the CLI because it needs a real HOST path for the container to route commands; this is more like "attaching files to a conversation". The browser reads the CONTENT (File.text()) and the RELATIVE path (File.webkitRelativePath) of the chosen files — never an absolute host path (the File API doesn't expose one, to any site), and that's why ADR 0113 is explicit that it is NOT a revision of what ADRs 0072/0107 refused: those refused RESOLVING a host path from the browser; here there is no path at all to resolve, only bytes the browser already had the right to read.

    chunks.scope (ADR 0079/0080) gains a FOURTH value, 'local' (migration 0052, ALTER TYPE ... ADD VALUE, additive — the two CHECKs of migration 0045 are already written as "it's session or it isn't", so local falls on the same side as docs/adr without a new CHECK). IndexLocalFolderUseCase mirrors IndexProjectDocsUseCase closely — Markdown-aware chunking for .md/.mdx, RagEmbeddingService, a chunk without a vector instead of failing when the embedding drops (RN-233) — but REJECTS (400) the whole upload when the AGGREGATE ceilings overflow (number of files, summed bytes), never truncates silently: it's a SINGLE gesture by the user with a folder picker on screen, not a background scan. An individual file that's too big or has an unrecognized extension is only SKIPPED (filesSkipped), never brings down the batch (RN-456). origemDoChunk didn't need any new branch: local carries sourcePath like docs/adr, falls into the kind: 'file' that the citation already knew how to render.
