    RN-037 — Infra становится областью: Workflows генерирует CI по провайдеру, Lead консолидирует в единый PR

    Второй экземпляр модели ADR 0038, после области QA (RN-036), — с одним структурным отличием: два делегирования области Infra выполняются ВСЕГДА (Dockerfiles/compose — самим Lead, "делегирует самому себе"; CI-конвейер — субагентом Workflows), ни одно никогда не отменяется. Workflows выбирает формат конвейера по gitProvider контекста (GetInfraContextUseCase, читается из project_repositories.provider — не из capabilities GitProvider, которые ОДИНАКОВЫ для GitHub и GitLab): "gitlab" генерирует .gitlab-ci.yml; любое другое значение ("github", "local" или неизвестное) генерирует .github/workflows/ci.yml. Каждый файл перед завершением проходит через validate_infra_file — hadolint для Dockerfile, actionlint для workflow GitHub Actions (ADR 0039; у .gitlab-ci.yml нет локальной проверки — задокументированный пробел, а не полурешение).

    Консолидация: файлы двух делегатов объединяются по path (при коллизии побеждает Workflows) в ЕДИНЫЙ PR — механизм предложения PR (propose_infra_pr) меняется с "инструмент напрямую вызывает api" на "инструмент сигнализирует Lead, который консолидирует и вызывает один раз", — open_infra_pr, который получает api, ТОТ ЖЕ, что и всегда, байт в байт (ExecuteInfraPrUseCase не тронут). Сбой любого делегата (источник infra/modelo/codigo/politica) НИКОГДА не открывает частичный PR — то же правило, что RN-036, снова уровнем выше.

    Каждый делегат (даже Lead сам для себя) отслеживается как строка delegations — переиспользуемая ровно так, как её оставила RN-036, с ОДНОЙ поправкой: колонка task_id стала NULLABLE (область Infra делегирует на СЕССИИ, за PR инфраструктуры нет задачи бэклога), а маршрут POST /internal/sessions/:sessionId/delegations перестал быть вложенным в /tasks/:taskId — taskId теперь идёт в теле, необязательно. У цикла K и бюджета нет отдельной колонки в области Infra (у исходного InfraAgent никогда не было бюджета на задачу, и эта работа его не ввела).

    • Где: apps/engine/lib/engine/infra/infra_lead.ex (consolidar/2), infra_lead_server.ex (связка), workflows_agent.ex, tools/validate_infra_file.ex (диспетчеризация по расширению), apps/api/src/application/use-cases/execution/get-infra-context.use-case.ts (gitProvider), record-delegation.use-case.ts (taskId необязателен)
    • Тест: apps/engine/test/engine/infra/infra_lead_test.exs (слияние и блокировка, чистые), infra_lead_server_test.exs (связка: единый PR с обоими наборами файлов, два делегирования, gitProvider: "gitlab" → .gitlab-ci.yml, сбой Workflows → без PR), workflows_agent_test.exs — и доказательство того, что контракт ExecuteInfraPrUseCase/InfraGateRunner не изменился: execute-infra-pr.use-case.spec.ts и infra_gate_runner_test.exs проходят вообще без изменений
    • Источник: ADR 0038, ADR 0039

    RN-411 — Четвёртый сигнал незавершённой работы: dev agents говорят dev.*, а не agent.status

    Найдено РЕАЛЬНЫМ использованием, а не тестом: в сессии выполнения поднялись пять dev agents, перешли в idle_tripped (автоматический выключатель RN-047, заблокированные в ожидании, пока пользователь вручную разблокирует задачу), а 30-секундный heartbeat (Engine.Sessions.SessionServer.handle_info(:heartbeat_timeout, state)) закрыл сессию снизу, пока работа — и ожидание решения человека — продолжались.

    У GetSessionPendingWorkUseCase уже был третий сигнал (RN-064) для той же проблемы: агент активирован, без последующего idle, удерживает сессию. Но этот сигнал читает только agent.status, словарь РАЗГОВОРНЫХ агентов (Criativo/PO/Arquiteto/Dev Lead/UX Designer/Staff/Infra). Engine.Dev.DevAgentServer (через Engine.Dev.AgentIo) никогда не испускает agent.status — он использует СОБСТВЕННЫЙ словарь в журнале событий сессии: dev.started, dev.working, dev.awaiting_gate, dev.awaiting_approval, dev.idle, dev.idle_tripped, dev.blocked, dev.blocked_by_container, dev.error. Сессия выполнения с dev agent, работающим ИЛИ заблокированным, всегда возвращала pending: false по третьему сигналу, потому что agent.status для него не существует.

    ЧЕТВЁРТЫЙ сигнал ищет ПОСЛЕДНЕЕ событие dev.* каждого actor.id (dev-<modulo>/dev-<modulo>-2, тот же ключ, что в RN-195), уже появлявшегося в сессии, — как третий сигнал, но по нескольким типам событий вместо одного, потому что состояние dev agent — это не ОДИН тип с переменным payload.status, а отдельные типы событий на каждый переход. Линейка: pending: true, когда последнее — dev.working, dev.blocked или dev.idle_tripped, — все три означают "идёт работа или человек должен действовать", а заблокированный в ожидании разблокировки — ЭТО незавершённая работа (буквально то, что пользователь делал, когда сессия закрылась при реальном выполнении). Не считается только dev.idle (никакой задачи, которую можно взять, действительно опустошён).

    dev.awaiting_gate и dev.awaiting_approval как последнее событие изначально НЕ запускали этот сигнал — они остались вне линейки в том виде, в каком она была решена тогда. awaiting_gate был ИЗВЕСТНЫМ остаточным пробелом; RN-412 закрыла его вместе с awaiting_approval (по новому аргументу, а не по исходному — см. RN-412).

    dev.blocked_by_container вошёл ПОЗЖЕ, по тому же аргументу и по столь же реальной находке. Тип родился с RN-502/ADR 0143 — dev agent не забирает задачу, пока у проекта нет зарегистрированного running-контейнера, — а список DEV_EVENT_TYPES сценария использования за этим не последовал. Поскольку именно этот список сценарий ЗАПРАШИВАЕТ, событие стало невидимым: api не видела его даже для того, чтобы проигнорировать. В реальном выполнении exp004 (сессия f782257e) пять dev agents испустили dev.started и dev.blocked_by_container в 22:41:38, engine закрыл сессию по heartbeat_timeout в 22:42:07 — ровно 30 секунд, — а события этой сессии продолжали приходить через 13 и 32 минуты. Последним ВИДИМЫМ событием по агенту был dev.started, который намеренно вне линейки. Все пятеро ждали, пока ЧЕЛОВЕК поднимет контейнер, что и есть определение незавершённой работы, которое уже используют другие сигналы.

    Утверждение, что список — "полный словарь, подтверждённый прямым чтением кода engine", было верным, когда его писали, — и именно оно молча устарело. Верным его теперь держит МЕХАНИЗМ: scripts/ci/vocabulario-de-eventos-dev.spec.ts извлекает типы dev.* из apps/engine/lib/**/*.ex и проваливается, когда они расходятся с двумя списками сценария использования, называя недостающий тип. Он СРАВНИВАЕТ, а не ГЕНЕРИРУЕТ (прецедент agent-areas.ts), потому что выводима только половина пары: DEV_EVENT_TYPES механичен, DEV_PENDING_TYPES — суждение о том, какие состояния означают "человек должен действовать".

    У ТОГО ЖЕ дрейфа был третий экземпляр, в WEB, и механизм стал покрывать и его. DEV_STATUS_EVENTS (apps/web/src/lib/agent-status.ts), к которому обращается панель команды, чтобы сказать состояние каждого dev agent, тоже не знал ни dev.blocked_by_container, ни dev.awaiting_approval — и там следствием была не невидимость, а ЛОЖЬ: оба попадали в default: return 'trabalhando' у switch, поэтому в exp004 панель говорила, что пять dev agents, стоявших ЧАСАМИ в ожидании, пока человек поднимет контейнер, работают. Оба отображаются на aguardando, то же состояние, что уже использовал dev.awaiting_gate (агент не продолжает, пока что-то ВНЕ его не произойдёт), без нового состояния в AgentStatus; dev.error, которого не было ни в одном списке и из-за чего панель возвращалась к предыдущему dev.working, отображается на falhou. Список перестал быть списком: он стал КАРТОЙ tipo -> AgentStatus, что убирает default и делает невозможным добавить тип, не ответив, что он значит. А перекрёстный тест получил пару engine × web с требованием, которого нет у api, — явное РЕШЕНИЕ по каждому типу, отображённый ИЛИ объявленный в DEV_STATUS_EVENTS_FORA (tipo -> motivo, сегодня пусто), — потому что в панели тип dev.* МОЖЕТ законно не представлять интереса; нельзя лишь остаться в стороне по забывчивости.

    • Где: apps/api/src/application/use-cases/sessions/get-session-pending-work.use-case.ts
    • Тест: apps/api/test/application/use-cases/sessions/get-session-pending-work.use-case.spec.ts (dev agent с dev.working/dev.blocked/dev.idle_tripped/dev.blocked_by_container в качестве последнего события → pending: true, включая пять агентов сценария exp004 и dev.blocked_by_container, побеждающий предыдущий dev.idle; dev.idle → pending: false; сессия без событий dev.* сохраняет прежнее поведение; важно только ПОСЛЕДНЕЕ событие каждого агента; dev-<modulo>-2 тоже удерживает; изоляция между сессиями), scripts/ci/vocabulario-de-eventos-dev.spec.ts (словарь dev.* engine × два списка api И × карта панели, плюс три сфабрикованных случая, доказывающих клапан DEV_STATUS_EVENTS_FORA, который сегодня не задействуют никакие реальные данные) и apps/web/src/lib/agent-status.test.ts (dev.blocked_by_container и dev.awaiting_approval → aguardando, dev.error → falhou, никогда trabalhando; и самое свежее событие продолжает решать)
    • Источник: найдено реальным использованием — реальная сессия выполнения с пятью dev agents в idle_tripped, закрытая heartbeat, пока пользователь ещё разблокировал задачи вручную; и позже — пять dev agents в blocked_by_container в exp004, тем же механизмом

    RN-498 — Золотой набор RAG реально выполняется в CI, ПО РАСПИСАНИЮ — и gate остаётся warn

    RN-490 записала, что золотой набор RAG (ADR 0132) рождается как ручной mix golden_set.rag, "никогда в CI", по той же причине, что золотой набор QA (ADR 0123): без секрета API LLM или новой инфраструктуры не было способа запускать настоящий Ollama на CI-раннере. Эта RN закрывает эту половину — только для RAG, никогда для QA — отдельным workflow (.github/workflows/golden-set-rag.yml, schedule + workflow_dispatch), который подтягивает nomic-embed-text в реальный сервис Ollama (та же закреплённая версия, что в остальном продукте, сегодня 0.34.4) и реально запускает mix golden_set.rag.

    Различие, делающее это осуществимым для RAG, но не для QA: золотой набор RAG вызывает только модель ЭМБЕДДИНГОВ — CPU, детерминированно, без сэмплирования, — никогда модель ЧАТА, выносящую суждение, чего требует золотой набор QA (дорого, измеряет нечто по природе недетерминированное, как записывает сам ADR 0123, с реальными прогонами от 1 до 5 попаданий из 6). ubuntu-latest без всякого GPU здесь достаточно — для QA этого не хватило бы. Золотой набор QA ничуть не меняется этой RN: он остаётся полностью ручным, TODO(humano) в CLAUDE.md.

    severidade: warn (apps/api/config/gates.yml) ОСТАЁТСЯ warn, и причина изменилась. Это больше не "нет CI с LLM" — это частота: workflow ЗАПЛАНИРОВАН (ночной + ручной запуск), никогда не выполняется по pull_request. block обещал бы блокировку merge, которой нет, — то же рассуждение, что уже действовало на Этапе 2, применённое теперь к правильной причине. Регрессия точности поиска становится видимым сигналом тренда в течение 24 ч (или сразу, через workflow_dispatch), никогда gate, блокирующим PR, — компромисс, явно принятый владельцем продукта с учётом стоимости подтягивания модели и выполнения 17 поисков (несколько минут) в каждом окне.

    Никаких секретов генерировать в workflow не нужно. seed-golden-set-rag.ts никогда не задаёт NODE_ENV, а четыре секрета, которые api отклонила бы с литералом-примером в продакшене (RN-114), проверяются только при NODE_ENV === 'production' — скрипт попадает в ветку разработки и использует литералы dev без жалоб, в отличие от docker/smoke.sh, который намеренно поднимается с NODE_ENV=production и поэтому генерирует свои через openssl rand.

    Постоянное исключение тега :golden_set_rag в test_helper.exs (RN-490) не меняется.     RN-549 — E2E на чистой машине доказывает ВСЮ установку: пять звеньев, агент на ногах в ожидании и первый проект, подхваченный без возврата в терминал

    Сессия 8 ФАЗЫ 30, последняя — и единственная, которая могла ответить на вопрос, которого добивается вся фаза: на чистой машине install.sh заканчивается с локальным агентом на ногах и сопряжённым, а человек создаёт первый проект в режиме Runner, не возвращаясь в терминал? До сих пор ответом было записанное намерение: RN-547 связала пять команд и письменно объявила, что в её тестах brabo-runner — дублёр на shell, а api — node:http: «доказывается СВЯЗЫВАНИЕ, никогда интеграция».

    Harness родился не здесь: его РАСШИРИЛИ. .github/workflows/install-e2e.yml существует с ФАЗЫ 29 (RN-534) и уже запускает опубликованный установщик на эфемерном runner Actions — буквально чистой машине, без Brabo, без .env, без маркера. То, что он доказывал, останавливалось на .env: план, состояние, три обещания никогда не удалять, путь без TTY и подъём с имитируемым TTY. Второй workflow дублировал бы дорогую сторону (ждать Release, скачать, проверить подпись), чтобы измерить дешёвую.

    Он НЕ запускается в pull_request, и следствие заявлено, а не скрыто. Установщик проверяет собственное происхождение против подписанного checksums.txt Release (RN-526), который существует только после финального тега; единственный способ запустить его в PR — дать ему дверь для ПРОПУСКА проверки, дверь, которую отвергает ADR 0150 и которая, однажды открытая, действовала бы для любого, а не только для CI. Следовательно: PR, написавший этот E2E, его не выполнил, и его проверки прошли, не проверив ни строки добавленного. Это то же решение, что у golden-set RAG (ADR 0138), по той же причине.

    Отсюда половина, которая ВЫПОЛНЯЕТСЯ в PR, и в этом причина её существования. Workflow, запускаемый только на теге, — workflow, чья ошибка проявляется на теге, когда релиз уже выходит и никто больше не смотрит на сломавший его PR. scripts/dev/install-e2e.spec.ts измеряет два известных способа, которыми этот E2E молча гниёт: кто-то ослабит gate (добавит pull_request в триггер или передаст флаг пропуска проверки), и кто-то перепишет фразу в install.sh — тогда каждый grep workflow перестаёт что-либо находить, и утверждения не падают, они ИСЧЕЗАЮТ. Канарейка приглашений выведена, а не заучена: ответы TTY идут через файл, по порядку, и новый read -r в установщике сдвигает все последующие — база стала бы паролем, — поэтому тест считает приглашения и велит смотреть файл ответов.

    Что E2E начал доказывать, и у каждого утверждения есть владелец. Пять звеньев RN-547, по одному, против НАСТОЯЩИХ api и бинарника, — учётная запись (RN-546), пара, сгенерированная на машине, и поставленный kid (RN-551), регистрация публичного (RN-552) и unit машины (RN-545). Плюс инвариант RN-475, измеренный на ДИСКЕ, а не в выводе (файл, который читает runner, имеет kid, имеет d, а .parcial исчез, когда finish закрылся), пароль, отсутствующий в .env, маркере и логе, и ownerEmail, присутствующий в маркере.

    ОТРИЦАТЕЛЬНОЕ доказательство ценнее всего, и это отсутствие блока ожидающих пунктов. RN-547 велит сообщать о каждом падающем звене в именованном финальном блоке — и выходить с 0 всё равно. E2E, смотрящий на код выхода, дал бы зелёный с четырьмя из пяти сломанных звеньев. «Ни одного ожидающего пункта» — единственный способ утверждать, что все пять замкнулись, включая те, которые workflow не умеет называть.

Это ровно та гонка, которую прячет фиксированный sleep, а измерение здесь не того артефакта — бинарника на диске, записанной unit — самый лёгкий способ для E2E дать зелёный, ничего не доказав. Отсутствие цели — предусмотренный итог (::notice::), никогда ошибка; отсутствие Release остаётся именованной ошибкой, потому что этот workflow только ПРИКЛАДЫВАЕТ и никогда не создаёт; а ни одного приложенного бинарника — по-прежнему ошибка, потому что пустой checksums.txt утверждал бы, что у релиза нет бинарников, тогда как на деле упала вся матрица.

    Потолок бинарников — 1200 с, и число не произвольно: это timeout-minutes: 20 самого job build — максимум, который цель с runner может занять после начала. Чего он намеренно не покрывает — время очереди, и непокрытие времени очереди и есть весь смысл. Цикл выходит рано, когда все цели пришли, — это счастливый путь.

    Ничто из того, что job ДЕЛАЕТ, не меняется. Он по-прежнему собирает манифест из assets (а не из dist-bin/, там пустого), подписывает keyless cosign и проверяет перед приложением — RN-524 нетронута, один манифест, а не пять подписей. А цель, приложившая ПОСЛЕ потолка, не остаётся сиротой: --clobber уже существовал для этого, а пересборка манифеста — это workflow_dispatch с тем же тегом.

    Чего это правило НЕ делает: darwin-x64 по-прежнему не собирается. Смена label, удаление платформы или оплата runner — решение владельца, и манифест не может от него зависеть — именно из-за зависимости от него он и не выходил.

    Измерено позже, в AT-065 (2026-09-13, через workflow_dispatch в пробном прогоне): macos-13 — label без runner (образ, выведенный GitHub в декабре 2025; 30 мин в очереди, отменён, run 34769280227). macos-15-intel планируется за 3–22 с и собирается, но падает на --self-test-pty, потому что под Bun onData из node-pty не доставляет вывод дочернего процесса (oven-sh/bun#25822, открыт); то же доказательство проходит под Node на том же runner (run 34770476634). Ожидающее решение перестало касаться runner и стало выбором: ждать Bun или убрать платформу. Правило выше от этого не меняется.

    Решено 2026-09-27 (ADR 0174, AT-065): платформа убрана. Матрица стала из ЧЕТЫРЁХ целей, и ALVOS_ESPERADOS последовал — именно против него объявляется отсутствие, и оставить там darwin-x64 заставило бы каждый манифест вечно объявлять нехватку, которая является решением.
