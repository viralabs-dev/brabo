    为什么拆分，何时不拆

    适合谁： 正在决定是否把产品拆成多个仓库的人。

    读完之后你可以： 列出拆分的收益与代价，并判断自己的情况是否值得付出这个代价。

    起点

    Brabo 起初是一个单体仓库：api、engine、web、runner、broker、基础设施、文档和端到端测试都在同一个仓库里，只有一个版本、一份历史、一条流水线。2026 年 11 月，产品负责人决定把它拆成组织内的多个仓库。决定与地图记录在 ADR 0252 中，供有兴趣的人日后阅读。

    拆分带来了什么

    ADR 记录为原因和直接后果的内容：

    • 独立的版本。 每个仓库有自己的版本，产品的版本在入口仓库。修复 api 不必强制重新发布 web。
    • 每份文档都有明确的归属。 docs/ 和业务规则存放在拥有代码的仓库里，各仓库自己的 docs:check 检查自己那一份。
    • 各自的制品。 发布容器镜像、二进制文件或软件包的仓库，在自己的仓库里发布，并有自己的签名链。
    • 一个入口。 只想安装的人只需认识一个仓库，而不是十一个。

    TODO(humano)： ADR 0252 没有列出带编号的"何时拆分"标准（例如团队规模或发布节奏）。如果负责人希望路径写明这些标准，需要由他来撰写。

    拆分花费了什么

    拆分把复杂度转移到仓库之间的边上。以下是 Brabo 实测并不得不解决的代价，以及采用的方案：

    代价 发生了什么 采用的方案
    站点要读取兄弟仓库的代码 文档站点需要其他仓库的代码。读取各 dev 的最新提交，会让同一个 PR 在没有新提交的情况下由绿变红。 入口仓库中的 SHA 锁（irmaos.lock），由机器人更新。ADR 0274
    翻译对等 翻译度量汇总了所有仓库的文档，因此别处的一次合并会让无关的 PR 变红。 对等性只度量所属仓库自己的文档。ADR 0273
    跨仓库的合并顺序 GitHub 没有仓库之间的依赖。一个仓库的 dev 在两次顺序错误的合并之间变红，而顺序只存在于负责推进的人的记忆里。 PR 声明自己依赖哪个 PR（Depende-de:），由检查等待。ADR 0276
    推进顺序 把 dev 推进到 main 同样有顺序。 顺序由仓库的层级推断。ADR 0284
    地图会过时 仓库列表被手工复制到 14 个地方，有 11 种不同的写法。 单一来源（repos.yml）生成每个 README 的区块。ADR 0281
    CI 策略的固定版本 每个仓库固定了策略的不同版本；11 个仓库之间有 5 个不同的 SHA。 固定指向一个标签，并由检查校验。ADR 0280
    共享契约 契约仓库的新标签需要在多个使用方中升级版本。 按精确标签消费，并由脚本在每个使用方中升级版本。见第 3 页。

    注意其中的规律：每一项代价都变成了一件自动化的工具。没有这些自动化就拆分，是得到一组无人能维护的仓库的最常见途径。

    何时不拆

    这些迹象来自上面的代价，而不是 Brabo 的规定。如果其中几条适用于你，请推迟拆分：

    • 没有人需要独立版本。 如果一切总是一起发布，单体仓库已经免费提供了这一点。
    • 一个人或一个小团队负责全部。 边的成本（锁、合并顺序、固定版本）是固定的，而自主性的收益很小。
    • 你无法自动化跨仓库的事务。 没有合并顺序、固定版本和地图的检查，这组仓库会悄悄腐烂。
    • 代码总是一起变化。 如果几乎每次变更都涉及三个仓库，你搭出来的是一个难用的单体仓库。
