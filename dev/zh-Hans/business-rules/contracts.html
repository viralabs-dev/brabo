    RN-028 — Capability decides, not the provider's name

    An unsupported operation (branch protection on the local provider) is declared in capabilities and rejected with GitNotSupportedError — never a silent failure.

    There are four capabilities: protectBranch and pullRequests since Phase 2, and listTree and pullRequestDiff since PHASE 26 (Code tab, read-only). The rule did not change with them — its scope did. And the criterion for declaring one stays proof: a capability is only true when the suite exercises it on that provider; without proof, it is declared false and degrades (same criterion as ADRs 0041/0042).

    RN-087 — The Dev Lead is the only external address of the execution

    There is a dev-lead agent, conversational, that receives the handoff from the Architect (since RN-672, from Infra, with the project container running) and proposes the execution plan: how many agents per module and why. It does not write code — it distributes work and answers for it.

    Before it, the phrase "the lead decides" from RN-083 had no owner. The Architect finished and the execution started from a button, with nobody in the middle to evaluate how much work there was.

    The dev-<modulo> agents stopped being addressable by handoff. This is not a new exception: it is the rule of ADR 0038 — external handoff addresses only an area lead or an agent without an area — now applying to the dev as it already applied to QA and Infra. While there was no Dev Lead, they were agents WITHOUT an area and so were valid targets; once they become members, they stop being so.

    The dev area is the first DYNAMIC one, and it is what forced the predicate: the members are one per module of the module_map, decided by the Architect and different in each project, so there is no list to enumerate. dev-lead matches the same dev- prefix as the members, and what excludes it is the generic rule the lead is never a member of its own area — which applies to any area and lives in one single place. The first version repeated this exclusion in three points, and mutation verification showed that none of the copies was reachable by a test: each one survived the mutation of the others.

    The plan is proposed_action (revised by ADR 0086, RN-284). Until that change the plan became a simple EVENT, with no approval: the argument was that proposing has no external effect — the spending happens when the agents start, and that is where the ceiling charges authorization; turning the proposal into an action to decide would make you decide the same thing twice. An audit of packages/contracts/fluxo.yml × code found that the flow had already declared this exit as via: proposed_action since ADR 0085, and the code had never been adjusted to match — the product owner decided the code was wrong: the plan is the FIRST real decision on how much the session will spend on parallelism, and the user started deciding to enable execution having SEEN a real approval, not just read a line in the thread. The old lesson did not disappear — it is the reason why propose_execution_plan did NOT enter the block of absolute ceilings in decide.ts (see RN-284).

    The SUCCESSFUL plan ends the turn — on the path WITHOUT suspension. In the first real execution the Dev Lead registered two execution.plan_proposed events in the same session — different texts, same total —, because the loop went back to the model and it proposed again. The event log is immutable: there were two proposals and nothing saying which one was valid. The instruction "use it once" in the tool spec is a request, not a guarantee; what guarantees it is the loop stopping. Since ADR 0086, when the proposal stays pending, what ends the turn is the STOP by suspension (RN-284) — the immediate success (auto_approved/executed/approved, see RN-284) keeps closing the loop in the same way as always.

    Successful, and not "called the tool": a refused plan (empty, or with zero agents in a module) lets the loop continue, otherwise the refusal becomes the end of the turn and the model never gets to correct it. The first version of this guard looked only at the tool name and had this defect — found by the behavioral test, not by reading.

    An empty plan, or one with zero agents in a module, is refused before proposing anything — the proposal, once created, is a real decision by the user, and a half-proposed plan would have no way to be represented.

    RN-110 — blame is the 13th operation of the GitProviderContract, with the same vocabulary of absence as the other reads

    Foundation of the blame pending declared in PHASE 26 (no screen consumes it yet — it comes in the next wave). blame(ref, path) returns GitBlame | null, with null meaning exactly what it already means in getFileContent/ listTree: the file is missing at that ref, or the ref does not exist.     RN-112 — listBranchesDetailed is its OWN operation, separate from listBranches

    Foundation of the rich dropdown, now consumed by CodeBranchPicker.tsx (ahead/behind, PR badge — the wave following PHASE 26b closed the pending that CodeShell.tsx declared). GIT_BRANCH_DETAIL_LIMIT (30) cuts for the same traffic reasons as item 34 of PHASE 26 — without it, a repository with hundreds of branches would become hundreds of calls per opening of the dropdown.

    RN-341 — The QA strategy is the second MOMENT of the qa-lead, and it never suspends

    packages/contracts/fluxo.yml declared the role qa-estrategia as proposto, with the separation criterion written in the record itself: "can be the sameqa-lead in a second MOMENT, not necessarily a new agent — the separation is of deliverable". The ADR 0090 builds exactly that: Engine.Gates.QaEstrategiaAgent is a STATELESS module (it is not a GenServer), triggered by Engine.Gates.QaLeadServer.run_design/3 — a NEW and ADDITIVE entry point in the SAME qa-lead process, without touching run/2 (the usual path, PR review, tied to DevAgentState.find_by_task_id).

    The context is LIGHT, and that is where the separation of deliverable shows. Engine.Gates.QaEstrategiaContext.fetch/3 fetches ONLY the story (from EngineApiClient.list_backlog/1, the tree the PO already reads — RN-164) and the current module_map (from EngineApiClient.get_infra_context/2, the SAME GetInfraContextUseCase that the Infra Lead consumes, here only through the moduleMap field) — with NO dev_state, NO worktree_path: the implementavel gate runs PRE-DEV, before any dev agent, worktree or task_id exists. No new route in the api — both functions already existed.

    It never suspends. The tool registry (ReadFile, SearchWorkspace, EmitPlanoDeTeste) does not include terminal or write_file — the TWO only tools that Engine.Harness.Hooks.ActionPipeline intercepts to create proposed_action. With no call at all going through the action pipeline, the ToolLoop of this agent never produces :pending, and run_design/3 runs SYNCHRONOUSLY inside the handle_cast itself — with no suspension/resumption mechanism, unlike the rest of the QA area.

    The iteration ceiling stays at 8 (conversational), not 60 (gate) — on purpose, not a gap. This agent runs WITHOUT token_budget_micros — there is no task or budget yet. The criterion of RN-085 is not "who works a lot": it is "what holds the spending beyond the iteration ceiling". With no budget underneath, raising the ceiling would multiply the worst case with nothing to contain it — the SAME reason why infra-workflows stays at 8 even using tools. "qa-estrategia" did NOT get its own clause in Engine.Harness.Iteracoes.tipo/1: falling into the default is the right decision.

    RN-605 — The image pull is a NAMED step of start, under the control ceiling, and the overflow says that a large image does not come up

Measured in real use: the 36 QA automation commands with pkill -f were dying with 143, because the pattern matched the argv of the sh itself. Outside the scope, declared: the runner on the host (apps/runner/src/exec.ts), which RN-507 already conditions to a running container.
    • Where: packages/docker-port/src/docker-cli.ts:303 (EMBRULHO_DO_EXEC).
    • Test: packages/docker-port/src/docker-cli.spec.ts ("o comando que estoura volta timedOut e MORRE dentro do container", against real Docker: self pkill -f survives, exit 3 returns 3, the command does not appear in ps).
    • Origin: AT-622 (EP-030).

    RN-1024 — The app is restarted in place: only its process, never the container or the other execs

    • Rule: the DockerPort gains a sixth operation, reiniciarApp(workspaceDirName, comandoDoApp), which restarts ONLY the supervised app process inside the running container; the lanes share that container, so it is neither stopped nor recreated, and no other process is touched. The supervisor (SUPERVISOR_DO_APP) now launches the app through a launcher whose inner sh writes its own PID to /tmp/brabo-app.pid and then execs the command, so the recorded PID is the leader of the app's group and session. The constant script REINICIAR_APP sends TERM to that group (KILL after 5 s), removes .pid and .exit, relaunches with the same launcher and waits up to 10 s for /tmp/brabo-app.exit: if it appears the app died. Without .pid (the app never ran, e.g. a container born with sleep infinity) it only launches. The user command travels only as $1 of the script via docker exec argv, never concatenated (RN-807). The result is typed: { reiniciou: true } or { reiniciou: false, motivo } with motivo one of sem_container, tempo_esgotado, falha_no_exec or app_saiu (the last one with the exitCode). The result NEVER carries a log excerpt, because the app command may hold secrets in plain text; the log stays in /tmp/brabo-app.log inside the container. Revises ADR 0228 decisions 1 ("an app that dies stays dead", now only until the next restart) and 5 ("five operations"). The broker, api and engine consume it by the TAG of this repository.
    • Where: packages/docker-port/src/docker-port.ts:625 (reiniciarApp), packages/docker-port/src/docker-cli.ts:604 (reiniciarApp), packages/docker-port/src/docker-cli.ts:408 (REINICIAR_APP), packages/docker-port/src/docker-cli.ts:398 (SUPERVISOR_DO_APP)
    • Test: packages/docker-port/src/docker-cli.spec.ts:862 (argv, typed results, no log), packages/docker-port/src/docker-cli.spec.ts:921 (real sh: kills the old group, KILL after TERM is ignored, writes the new .pid, app-exit on a dead app)
    • Origin: AT-617 (EP-030), ADR 0264.
