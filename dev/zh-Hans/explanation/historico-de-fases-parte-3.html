    阶段历史，第 3 部分：28 计划与审计

    2026年9月11日 的记录：描述当时的 Brabo

    28 计划（一波接一波）、fluxo.yml × 代码审计、团队的新智能体和知识图谱。 文本原样移自阶段历史，未作改写。今天有效的内容位于 RN 和 ADR 中。

    28 计划——第 1 波，A 前线：主题不再无法访问（RN-182..185）

    浅色主题存在于 design/tokens.css 中，有奇偶测试，并且在 design/README.md 中被描述得像是一个界面——而**apps/web 中没有任何东西写入 data-theme。看到它的唯一方法是在 DevTools 中手动输入该属性。两个对比度测试都知道并说了出来：其中一个用 expect 断言浅色主题中有三**对不通过，“是对所继承内容的记录，而不是对所渲染内容的保证”。在此期间，这个论证是诚实的——测量一个谁都打不开的界面，就是在测量一个意图。随着主题按钮的到来，它的符号反了过来。

    启动是一个文件**（apps/web/public/theme-boot.js），在 <head> 中同步执行，在 bundle 之前。handoff 要求使用内联脚本；镜像在 script-src 'self'（ADR 0058）下提供服务，所以内联在 pnpm dev:web 中能工作，在生产中却会被阻止——换了主角的 ADR 0036 式失败。tema.ts 是 shell 使用的 API；按钮不在其中。会抛异常的 localStorage 退化为“绘制但不持久化”，未知值退回到默认值。

    浅色主题的六个 token 改变了值（ADR 0074），因为浅色中要求最高的背景是纸质的 --code-bg：accent 3,56 → 4,81，warning 3,15 → 4,98，success 3,89 → 5,12，violet 4,16 → 4,95，text-muted 2,76 → 5,17，再加上低一级的 accent-hover。深色主题没有改变任何一个，它的欠账仍锁定在同样的五个数字上。记录了两个副作用：在深色中属于欠账的五对在浅色中通过，而“设计系统的已知例外”（--accent 上的 --on-accent，3,20:1）在浅色中消失——测试注释所描述的修复，即加深到 --terracota-500，正是浅色主题现在所做的。

    handoff 的八个 --syn-* 值中有五个因测量而被拒绝**（最差的 --syn-cm 在浅色中只有 2,32:1）。handoff 不通过的地方，以测得的数字为准：这与字体是同一把尺。八个角色以 --syntax-* 前缀开始存在；仍在着色的五个语义 token 被测量后放在它们旁边。

    28 计划——第 1 波，D0 前线：按 provider 的花费（RN-186..188）

    约束改变了性质，这才是重要的——而不是新的轴。 provider 重新成为 sumGroupedBy 的维度，根据产品所有者的决定修订了 ADR 0063。之前，成员够不到按凭据的拆分，因为它不存在——ADR 0063 写道“没有可以传入的参数”。现在它存在了，约束它的是类型：两个重载，而携带 actor 的范围（成员视图唯一的范围）只接受 Exclude<SpendDimension, 'provider'>。保证从“无法表达”变成了“无法编译”，后者更弱——这就是为什么屏障有两道且相互独立：成员的路由也没有任何维度参数。故意没有任何针对该组合的 if（与 RN-153/154 相同的教训），证明是通过反转完成的：没有 @ts-expect-error 时，tsc 会在确切的行上报 TS2769。

    porOwner/porAgente 是 porAtor 按 actor_kind 的划分，没有额外查询；system 不属于两者，仍计入总数。ADR 0063 测量并推迟的 token_usage(created_at) 索引进入了 migration 0044。界面没有变化——那是后续的波次。

    28 计划——第 2 波，H2 前线：不编造评分的模型排行（RN-210，ADR 0077）

    handoff 要求两样东西，它们都依赖产品所没有的同一项数据：按能力的质量评分（mock："código → claude-sonnet-4 / qwen2.5-coder:14b (9.4)"），以及当模型覆盖“agent 所要求的所有能力”时在 ModelPicker 中显示“ideal”徽章。调查两次确认第二项数据不存在：ModelsSection 本身已因此把“Agente · capacidades”一列重命名为只有“Agente”，而 agent binding 的 ModelPicker 读取 GET /projects/:id/models（viewer 角色）——策展（uses，ADR 0051）只存在于 ModelComCuradoria 中，来自一个仅限 maintainer 的路由。徽章没有构建；“Melhores modelos por capacidade”表格构建了，使用两个真实信号：项目中已有多少 agent 通过级联解析到每个策展过的模型，以及作为平局决胜的目录成本——从不使用计算出的评分。

    28 计划——第 2 波，B 前线：侧栏可折叠（RN-195..201）

    264px/62px，折叠时为图标轨道；可展开的项目会显示标签页（从 project-tabs.ts 读取，从不硬编码）；活动区按真实的基础 agent/实例分组——extraDevAgentId 的 -2 后缀，从不是编造的 -01/-02 计数器（第 1 波/B0 前线的发现）——并限定在当前路由的项目中，而不是全部，以免产生事件的 N+1。主题按钮在底部；两个无效的全局条目移除，只有项目和活动是全局的；代码标签页通过 AutoCollapseContext（sidebar-state.ts）自动折叠，不写入偏好。持久化集中在 sidebar-state.ts 中，即 handoff 的六个 brabo.* 键。

    两处与 handoff 的分歧已记录且未解决（RN-197）：项目徽章仍然是 pendingApprovalsCount（RN-151 胜出，它更新），handoff 的身份颜色只出现在折叠的轨道中——展开的行只保留现有的状态圆点（RN-039），两个圆点会是噪声。

    28 计划——第 2 波，C 前线：界面框架（RN-202/203，ADR 0078）

    handoff 中“界面框架”检查清单的四项字面修正： .headerTop 获得了 min-height: var(--header-h)——下限，而不是上限，因为项目的标题（身份 + 紧凑的 TokenMeter）比 handoff 中 6 个内部界面的通用标题更丰富，强制 60px 会截掉预算告警，这正是 RN-088 禁止的那类错误；活动标签页使用 box-shadow: inset 0 -2px 0 var(--accent) 而不是 border-bottom；标尺的水平滚动；文档式标签页中内容容器的 max-width: 1040px（不包括 semRespiro 的）。自第 16 阶段起作为后代 CSS 覆盖存在于 ProjectPage.module.css 中的标尺间距值迁移到了 Tabs.module.css，现在归属同一个所有者。

    需要决定、而不只是 CSS 的部分：handoff 列出 7 个项目标签页，而注册表（project-tabs.ts）有 10 个。executores（RN-121）、backlog （RN-048）和 insights（Psicólogo 的假设）诞生于 handoff 之后，有真实数据和自己的 RN，它们保留——handoff 是视觉保真的参考，而不是产品标签页数量的上限（RN-203，ADR 0078）。并且 sessions 键仍标为“Chat”，从不是较新的 handoff 所要求的“Chat RAG”（RN-202）：“Chat RAG”会描述一个不存在的功能——embedding 契约已就绪（ADR 0075），但还没有任何东西使用它，没有索引管道，也没有引用 UI——今天重命名标签页，就是 ADR 0042 已经对目录模型拒绝过的错误：在能力存在之前就宣布它。导出的形式都没有改变（AbaDoProjeto、ABAS_DO_PROJETO）；只有 code 的标签从 "Code" 改为 "Código"。

    28 计划——第 2 波，H1 前线：可见焦点（ADR 0036）

    Select、Modal（关闭按钮）和 ProjectCard 获得了 :focus-visible，与 Input.module.css 采用同样经过校准的处理，包括 forced-colors 区块：三者都没有仅凭键盘可达的焦点指示。Modal 的关闭按钮从 30px 增加到 32px，即桌面端触控目标的下限。Table 和 Badge 经过审计，不需要修改——两者都不暴露自己的交互能力：Table 的行纯属展示（需要可点击行的地方已经在单元格内通过 render 使用 <button>/<a>），而 Badge 在产品中任何地方都没有配合 onClick 使用。

    28 计划——第 3 波，H3 前线：Criativo 标签页获得 KPI，而不假装拥有不存在的数据（RN-227..230）

    handoff 为会话的 5 种真实状态（created/active/closing/closed/closed_abnormally）要求 4 个状态标签。closed_abnormally→ 中止、created→等待 是直接对应的；closing 没有与“已关闭”合并——它获得自己的标签（“encerrando”，accent 色调，脉动），因为在 closing 状态下结果尚不可知，称它为“已关闭”会就此撒谎。药丸式筛选器（同样原因只有 4 个）按轨迹而不是外观把 created 和 closing 分组：created 归入“Ativas”（仍在进行中），closing 归入“Fechadas”（正在无错误地关闭）——行上的标签从不被筛选器改写，只改变分组。4 个 KPI 中有两个因数据缺失而保持诚实：“本月成本”复用 getMySpend（与花费标签页相同的 queryKey，成员视图/RN-101），从不显示项目总额——那是 owner 的数据（porProjeto），而 Criativo 标签页对任何成员可见；“构思 → 提交 比率”被声明为缺失（显示“—”），因为如今产品中会话与提交之间不存在关联——编造计算就是 ADR 0042 对模型评分已经拒绝的那类错误。

    28 计划——第 4 波，G2 前线：Chat RAG 获得索引管道和混合搜索（RN-231..238，ADR 0080）

    基于第 3 波的 chunks 表（ADR 0079）：对三个诚实的范围进行手动索引（没有 watcher，POST .../rag/reindex，幂等的完全重建——在重建之前删除该范围/会话）——docs/adr 通过 ReadProjectCodeUseCase（与 Code 标签页相同的凭据/闸门/路径检查），session 只取 chat.message/agent.response。按标题/段落分块，1200 个字符、150 个字符重叠——记录为起点，而不是针对真实数据的校准（目前还不存在针对索引运行的问题集）。混合搜索是两个独立的查询（通过 HNSW 的向量、通过 GIN 的词法），以加权和（0.6/0.4）融合，并在阈值（0.2）处截断——这些数字同样是起点。当 embedding provider（固定为 ollama）没有响应时，管道会写入不带向量的块，并在报告中声明这一缺口——从不假装索引完整，搜索会降级为仅词法并发出警告。界面（Chat RAG 作为独立标签页）属于第 5 波；这条前线只有后端。

    28 计划——第 4 波，F1 前线：容器生命周期变成表，没有编排器（RN-243..248，ADR 0081）

    参见第 25 阶段的第 31 项（部分撤销）：project_containers （migration 0046）记录可变的状态——provisioning → running ⇄ stopped，failed 可从三者到达，removed 只能通过重新置备离开——不同于 artifact.project_image（Arquiteto 不可变的决定）。经调查确认（grep，零出现）：产品中没有任何服务挂载 /var/run/docker.sock 或以 privileged 运行——两个用例都只写入和读取，没有对 Docker 的任何真实调用。第一次转换要求镜像已经决定（RN-105），并在行中冻结版本/资源；local 项目（ADR 0072）被拒绝，因为它不启动自己的容器。资源上限（cpus/memory_mb/pids_limit）是声明的，而不是施加的——没有任何界面断言“容器被限制为 X”，只说“记录的意图是 X”。当时没有新的 HTTP 路由：在还没有真实使用方时公开一个，就是在猜测契约——由紧随其后的第 5 波/F2 前线关闭。

    28 计划——第 5 波，G3 前线：Chat RAG 获得独立标签页（RN-252..254，ADR 0082）

    RN-202（第 2 波/C）推迟的界面——“Chat RAG”会描述一个尚不存在的能力——随第 4 波/G2 的后端一起到来：key: 'rag'，新标签页（ordem: 28，位于代码和 Backlog 之间），从不重命名 sessions。区别保持不变，只是理由变了：sessions 是与已激活 agent 的对话（每个回合消耗 owner 的密钥，RN-058）；rag 是在已构建索引上的搜索，中间没有任何 agent，本质上只读。界面使用 ADR 0080 的三个契约而不猜测其形式，并显示后端早已声明、却没有任何界面读取的两种诚实降级——vectorAvailable: false 变成可见的警告，覆盖率从不编造“Xmin 前重新索引”。来源为 session 的引用会导航到确切的事件，复用 Psicólogo 证据标签已在使用的机制；来源为 file 的引用以文本显示路径/标题，不带链接——代码标签页如今没有按路径的深链接，不在此范围内。

    28 计划——第 5 波，F2 前线：容器生命周期的真实使用方（不是终端）（RN-267/268，ADR 0083）

    这条前线最初的计划是完整的交互式终端。调查确认第 25b 阶段仍被裁剪：没有服务挂载 /var/run/docker.sock，即使在 ADR 0081 之后，生产中也没有任何东西转换 project_containers——不存在可以在其内部打开终端的真实容器。实现一个假的终端，或者在 Brabo monorepo 的同一个容器中运行的终端（ADR 0055 已经描述为策略而非隔离的那笔债），就是在编造能力——与 ADR 0041/0042 对 LLM provider 和目录模型所拒绝的错误相同。真实的交付：GET /projects/:projectId/container/lifecycle （role:viewer），生命周期第一次通过 HTTP 公开（修订了因缺少使用方而推迟该路由的 ADR 0081），以及显示该状态的终端标签页——翻译后的徽章、失败原因——位于已有说明文字之下，从不取代它，只在标签页打开时获取。null（从未置备）是如今诚实且最常见的结果。

    28 计划——第 5 波，I 前线：社交登录撤销 ADR 0031 backlog 的禁令（RN-272..283，ADR 0084）

    产品所有者的明确请求，清楚其安全后果——禁令只对 GitHub/GitLab 解除；MFA、OIDC provider 和通用联合仍不在范围内（参见“O que NÃO fazer”）。 SocialLoginCallbackUseCase 最终落到与密码登录相同的 EmitirSessaoUseCase——没有第二种会话格式。它复用现有的 OAuth 客户端，但 state 有自己的用途 （purpose: 'social_login'，在任何其他字段之前检查）：从不接受把 git 连接到项目这一连接流程的 state，那会是权限提升。新表 social_identities（migration 0047），键为 (provider, provider_user_id)——从不是电子邮件/登录名。三步决策：已知身份 → 登录；电子邮件与现有账号匹配并且已由 provider 验证 → 关联（如果账号的电子邮件尚未验证，则一并验证）；电子邮件匹配但未验证 → 拒绝——输入的电子邮件不是所有权的证明，接受它会打开账号接管的口子；没有对应账号 → 置备一个没有密码的新账号，与 Keycloak 迁移时相同的“待定”状态。复用 git 连接的同一个 OAuth 应用——零新环境变量，只是每个流程的 redirect_uri/scope 不同；操作者需要在 provider 中登记第二个回调，这一动作正是 breaking/ 分支的理由。
