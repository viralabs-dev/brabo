    O mapa

    Para quem é: quem quer enxergar o conjunto antes de entrar nos detalhes.

    Depois de ler, você consegue: dizer o papel de cada repositório, apontar de quem ele depende e desenhar o mapa de memória.

    Os sete papéis

    Papel Repositório O que faz
    Porta de entrada brabo Documentação agregada, site, install.sh e a release do produto.
    Código brabo-api, brabo-engine, brabo-web, brabo-runner, brabo-broker Os componentes do produto. Quatro publicam imagem de contêiner; o runner publica um binário.
    Contrato brabo-contracts Pacotes e arquivos de dados que os outros compartilham.
    CI brabo-ci Workflows reutilizáveis e a política de PR, a escada de aprovação, a promoção e a tag.
    Orquestração brabo-infra Composes, Dockerfiles de integração, manifestos de Kubernetes, scripts de desenvolvimento e a imagem de backup.
    Qualidade brabo-qa Testes de ponta a ponta no navegador, golden-sets e o catálogo de funcionalidades. É o portão da main.
    Pasta-mãe brabo-workspace A pasta onde os clones ficam lado a lado e o clonar-tudo.sh. Não tem código de produto.

    O diagrama

    As setas dizem quem usa quem, e o rótulo diz por qual canal (a página 3 explica cada canal). Para não virar um novelo, o desenho mostra as arestas principais; a lista completa, com a prova de cada uma, está no repos.yml.

    flowchart LR
  WS["brabo-workspace<br/>pasta-mãe"]
  BRABO["brabo<br/>porta de entrada"]
  subgraph CODIGO["código"]
    API["brabo-api"]
    ENG["brabo-engine"]
    WEB["brabo-web"]
    RUN["brabo-runner"]
    BRK["brabo-broker"]
  end
  CON["brabo-contracts<br/>contrato"]
  CI["brabo-ci<br/>CI"]
  INFRA["brabo-infra<br/>orquestração"]
  QA["brabo-qa<br/>qualidade"]

  WS -. "clona" .-> BRABO
  WS -. "clona" .-> CODIGO
  CODIGO -->|"contrato: tag"| CON
  CODIGO -->|"workflow: SHA"| CI
  BRABO -->|"workflow: SHA"| CI
  INFRA -->|"workflow: SHA"| CI
  QA -->|"workflow: SHA"| CI
  CI -->|"dispara o E2E"| QA
  QA -->|"imagens por digest"| CODIGO
  INFRA -->|"código: compose"| CODIGO
  BRABO -->|"imagem/binário: pin"| CODIGO
  BRABO -->|"pin: ref"| INFRA
  BRABO -.->|"doc: trava de SHAs"| CODIGO

    Duas leituras úteis do desenho:

    • O brabo-ci é a base. Todo repositório o chama; ninguém importa nada do brabo-ci em tempo de execução do produto.
    • O brabo está no topo. Ele pina as versões que formam o produto, lê o código dos outros para gerar a documentação e publica a release do produto. Por isso a promoção dele é a última.

    Uma fonte só para o mapa

    Esta tabela e este desenho não são mantidos à mão. A fonte única é o arquivo repos.yml, na raiz do brabo: por repositório, o papel, o propósito, como é usado e a lista depende_de, em que cada aresta diz o repositório, o tipo de canal e a prova (o arquivo e um trecho literal, de uma linha, onde o código usa a dependência; o número da linha não é gravado, porque muda a cada commit).

    brabo-web:
  papel: código
  depende_de:
    - { repo: brabo-contracts, tipo: contrato, prova: { arquivo: package.json, trecho: '"@brabo/shared": "npm:@viralabs-dev/brabo-shared@' } }
    - { repo: brabo-ci, tipo: workflow, prova: { arquivo: .github/workflows/carimbo.yml, trecho: "brabo-ci/.github/workflows/tag-release.yml@" } }

    O bloco "Onde se encaixa" do README de cada repositório é gerado desse arquivo pelo brabo-ci, e um check reprova o README cujo bloco divergiu. Assim o mapa de um repositório nunca discorda do de outro. Quem mexe numa dependência edita o repos.yml e regenera os blocos. Para saber mais: ADR 0281 e a arquitetura.

    Para o seu projeto: comece pela tabela de papéis. Se você não consegue dizer em uma frase o papel de um repositório, ele provavelmente não deveria existir separado.
