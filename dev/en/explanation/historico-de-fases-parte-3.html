    Phase history, part 3: Program 28 and audits

    Record from September 11, 2026: describes Brabo as it was on that date

    Program 28 (wave by wave), the fluxo.yml × code audit, the team's new agents and the knowledge graph. Text moved without rewriting from the Phase history. What holds today lives in the RNs and the ADRs.

    PROGRAMA 28 — Wave 1, front A: the theme stops being unreachable (RN-182..185)

    The light theme existed in design/tokens.css, had a parity test and was described in design/README.md as if it were a screen — and nothing in apps/web wrote data-theme. The only way to see it was to type the attribute in DevTools. The two contrast tests knew and said so: one asserted by expect that THREE light pairs fail, "a record of what is inherited, not a guarantee of what is rendered". While it lasted, the argument was honest — measuring a screen nobody can open is measuring an intention. With the theme button arriving, it flips sign.

    The boot is a FILE (apps/web/public/theme-boot.js), synchronous in <head>, before the bundle. The handoff says to use an INLINE script; the image serves under script-src 'self' (ADR 0058), so inline would work in pnpm dev:web and be blocked in production — ADR 0036's failure with another subject. tema.ts is the API the shell consumes; the button doesn't live in it. A localStorage that throws degrades to "paints and doesn't persist", and an unknown value falls to the default.

    Six light-theme tokens changed value (ADR 0074), because the light theme's most demanding background is the paper --code-bg: accent 3.56 → 4.81, warning 3.15 → 4.98, success 3.89 → 5.12, violet 4.16 → 4.95, text-muted 2.76 → 5.17, plus accent-hover one step below. The DARK didn't change any, and its debt stays locked at the same five numbers. Two side effects recorded: the five pairs that are debt in the dark PASS in the light, and the "known exception of the design system" (--on-accent over --accent, 3.20:1) disappears in the light — the fix the test's comment described, darkening down to --terracota-500, is what the light theme now does.

    Five of the handoff's eight --syn-* values were REFUSED by measurement (the worst, --syn-cm, gives 2.32:1 in the light). Where the handoff fails, the measured number holds: it's the same rule as the fonts. The eight roles now exist with the prefix --syntax-*; the five semantic ones that still paint are measured alongside them.

    PROGRAMA 28 — Wave 1, front D0: spend by provider (RN-186..188)

    The containment changed nature, and that is what matters — not the new axis. provider became a dimension of sumGroupedBy again, revising ADR 0063 by the product owner's decision. Before, the member couldn't reach the breakdown by CREDENTIAL because it didn't exist — ADR 0063 wrote "there is no argument to pass". Now it exists, and whoever contains it is the TYPE: two overloads, and the scope that carries actor (the only one of the member's view) only accepts Exclude<SpendDimension, 'provider'>. The guarantee went from "impossible to express" to "impossible to compile", which is weaker — and that is why the barriers are TWO and independent: the member's route also has no dimension parameter at all. No if on the combination, on purpose (same lesson as RN-153/154), and the proof was by INVERSION: without the @ts-expect-error, tsc flags TS2769 on the exact line.

    porOwner/porAgente are a partition of porAtor by actor_kind, with no extra query; system stays out of both and remains in the total. The index on token_usage(created_at) that ADR 0063 measured and postponed came in in migration 0044. The SCREEN didn't change — that's a later wave.

    PROGRAMA 28 — Wave 2, front H2: model ranking without an invented score (RN-210, ADR 0077)

    The handoff asked for two things that depended on the SAME data the product doesn't have: a quality score per capability (mock: "code → claude-sonnet-4 / qwen2.5-coder:14b (9.4)") and an "ideal" badge in ModelPicker when the model covers "all the capabilities required by the agent". The investigation confirmed twice that this second data doesn't exist: ModelsSection itself had already renamed the "Agent · capabilities" column to just "Agent" for that reason, and the agent-binding ModelPicker reads GET /projects/:id/models (role viewer) — the curation (uses, ADR 0051) only exists in ModelComCuradoria, from a maintainer-only route. The badge was NOT built; the "Best models per capability" table WAS, with two real signals: how many of the project's agents already resolve, through the cascade, to each curated model, and the catalog cost as a tiebreaker — never a calculated score.

    PROGRAMA 28 — Wave 2, front B: the sidebar collapses (RN-195..201)

    264px/62px with an icon track when collapsed; expandable projects revealing the tabs (read from project-tabs.ts, never hardcoded); the Activities section grouped by REAL base agent/instance — the -2 suffix of extraDevAgentId, never an invented -01/-02 counter (finding of Wave 1/front B0) —, scoped to the current route's project, not all of them, so as not to open N+1 event reads. Theme button in the footer; the two inert global items go, only Projects and Activities are global; auto-collapse of the Code tab via AutoCollapseContext (sidebar-state.ts), without saving a preference. Persistence centralized in sidebar-state.ts, the handoff's six brabo.* keys.

    Two divergences from the handoff documented and NOT resolved (RN-197): the project badge remains pendingApprovalsCount (RN-151 wins, it's more recent) and the handoff's identity color only appears on the collapsed track — the expanded line keeps only the existing status dot (RN-039), two dots would be noise.

    PROGRAMA 28 — Wave 2, front C: screen frame (RN-202/203, ADR 0078)

    The four literal fixes of the handoff's "screen frame" checklist: .headerTop got min-height: var(--header-h) — a FLOOR, not a ceiling, because the project header (identity + compact TokenMeter) is richer than the generic header of the handoff's 6 internal screens, and forcing 60px would cut the budget alert, the same class of error RN-088 forbids; the active tab with box-shadow: inset 0 -2px 0 var(--accent) instead of border-bottom; horizontal scrolling on the ruler; a content container with max-width: 1040px on the document-shaped tabs (not on the semRespiro ones). The ruler's spacing values that lived as a descendant CSS override in ProjectPage.module.css since FASE 16 migrated to Tabs.module.css, now with the same owner.

    The part that required a decision, not just CSS: the handoff lists 7 project tabs and the registry (project-tabs.ts) has 10. executores (RN-121), backlog (RN-048) and insights (Psicólogo hypotheses) were born AFTER the handoff, with real data and their own RN, and they STAY — the handoff is a VISUAL fidelity reference, not a ceiling on how many tabs the product has (RN-203, ADR 0078). And the sessions key remains labeled "Chat", never "Chat RAG" as the handoff's most recent version asks (RN-202): "Chat RAG" would describe a feature that doesn't exist — the embeddings contract is ready (ADR 0075) but nothing consumes it yet, with no indexing pipeline and no citation UI — and renaming the tab today would be the same error ADR 0042 already refuses for a catalog model: announcing a capability before it exists. No export SHAPE changed (AbaDoProjeto, ABAS_DO_PROJETO); only the code label went from "Code" to "Código".

    PROGRAMA 28 — Wave 2, front H1: visible focus (ADR 0036)

    Select, Modal (close button) and ProjectCard got :focus-visible with the same calibrated treatment as Input.module.css, including the forced-colors block: none of the three had a focus indication reachable by keyboard alone. The Modal close button went up from 30px to 32px, the desktop touch-target floor. Table and Badge were audited and did NOT need change — neither exposes an interactive affordance of its own: a Table row is pure presentation (whoever needs a clickable row already uses <button>/<a> inside the cell, via render) and Badge is not used with onClick anywhere in the product.

    PROGRAMA 28 — Wave 3, front H3: the Criativo tab gets KPIs without faking data that doesn't exist (RN-227..230)

    The handoff asks for 4 status seals for the session's 5 real states (created/active/closing/closed/closed_abnormally). closed_abnormally→ aborted and created→waiting are direct; closing was NOT merged with "closed" — it gets its own seal ("closing", accent tone, pulsing), because in closing the outcome isn't known yet and calling it "closed" would lie about that. The pill filters (only 4, for the same reason) group created and closing by TRAJECTORY, not appearance: created falls in "Active" (still in play), closing falls in "Closed" (on the way to closing without error) — the row's seal is never rewritten by the filter, only the grouping changes. Of the 4 KPIs, two are honest about missing data: "cost this month" REUSES getMySpend (same queryKey as the Spend tab, the member's view/RN-101) and never shows the project total — which is the owner's data (porProjeto), and the Criativo tab is seen by any member; "ideation → commit rate" is DECLARED absent (shows "—"), because there is no link between session and commit in the product today — inventing the calculation would be the same class of error ADR 0042 already refuses for a model score.

    PROGRAMA 28 — Wave 4, front G2: the RAG Chat gets an indexing pipeline and hybrid search (RN-231..238, ADR 0080)

    On top of the chunks table from Wave 3 (ADR 0079): MANUAL indexing (no watcher, POST .../rag/reindex, idempotent full rebuild — deletes the scope/session before recreating) of the three honest scopes — docs/adr via ReadProjectCodeUseCase (same credential/gate/path check as the Code tab) and session only from chat.message/agent.response. Chunking by heading/paragraph, 1200 characters with 150 of overlap — documented as a starting point, not a calibration against real data (there isn't, yet, a body of questions run against the index). Hybrid search is TWO independent queries (vector via HNSW, lexical via GIN), fused by a weighted sum (0.6/0.4) and cut at a threshold (0.2) — numbers that are also a starting point. When the embedding provider (fixed: ollama) doesn't answer, the pipeline writes the chunks WITHOUT a vector and declares the gap in the report — it never fakes complete indexing, and the search degrades to lexical-only with a warning. The screen (RAG Chat as its own tab) belongs to Wave 5; this front is just the backend.

    PROGRAMA 28 — Wave 4, front F1: the container lifecycle becomes a table, without an orchestrator (RN-243..248, ADR 0081)

    See item 31 of FASE 25 (PARTIALLY REVOKED): project_containers (migration 0046) writes the mutable STATE — provisioning → running ⇄ stopped, failed reachable from all three, removed only leaves by reprovisioning — distinct from artifact.project_image (the Arquiteto's immutable DECISION). Confirmed by investigation (grep, zero occurrences): NO service of the product mounts /var/run/docker.sock nor runs privileged — both use cases only WRITE and READ, no real call to Docker. The first transition requires the image already decided (RN-105) and FREEZES version/resources in the row; a local project (ADR 0072) is refused, because it doesn't bring up its own container. The resource ceiling (cpus/memory_mb/pids_limit) is DECLARED, not applied — no screen asserts "the container is limited to X", only "the recorded intention was X". No new HTTP route at the time: without a real consumer yet, exposing one would be guessing a contract — closed by Wave 5/front F2 just below.

    PROGRAMA 28 — Wave 5, front G3: the RAG Chat gets its own tab (RN-252..254, ADR 0082)

    The screen that RN-202 (Wave 2/C) had postponed — "Chat RAG" would describe a capability that didn't exist yet — arrives together with the backend of Wave 4/G2: key: 'rag', a NEW tab (ordem: 28, between Code and Backlog), NEVER renaming sessions. The distinction stays the same, only the reason changed: sessions is a conversation with an ACTIVATED agent (spends the owner's key per turn, RN-058); rag is a search over an already built index, with no agent at all in between, read-only by nature. The screen consumes the three contracts of ADR 0080 without guessing shape and shows the two honest degradations the backend already declared and no screen read — vectorAvailable: false becomes a visible warning, and the coverage never invents "reindexed Xmin ago". A citation with session origin navigates to the exact EVENT, reusing the mechanism the Psicólogo's evidence chips already use; file origin shows path/heading as text, without a link — the Code tab has no deep link by path today, out of scope here.

    PROGRAMA 28 — Wave 5, front F2: the real consumer of the container lifecycle (not the terminal) (RN-267/268, ADR 0083)

    The original plan for this front was the complete interactive terminal. The investigation confirmed that FASE 25b remains cut: no service mounts /var/run/docker.sock, and even after ADR 0081 nothing in production transitions project_containers — there is no real container to open a terminal INSIDE it. Implementing a faked terminal, or one running in the same container as Brabo's monorepo (the debt ADR 0055 already describes as policy, not isolation), would invent capability — the same error ADRs 0041/0042 refuse for an LLM provider and a catalog model. The real delivery: GET /projects/:projectId/container/lifecycle (role:viewer), the first HTTP exposure of the lifecycle (revises ADR 0081, which had postponed the route for lack of a consumer), and the Terminal tab showing that state — translated badge, failure reason — UNDER the explanatory text that already existed, never in its place, fetched only while the tab is open. null (never provisioned) is the honest and most common result today.

    PROGRAMA 28 — Wave 5, front I: social login revokes the prohibition from the ADR 0031 backlog (RN-272..283, ADR 0084)

    Explicit request from the product owner, aware of the security consequences — the prohibition goes away only for GitHub/GitLab; MFA, OIDC provider and generic federation remain out of scope (see "What NOT to do"). SocialLoginCallbackUseCase ends in the SAME EmitirSessaoUseCase as the password login — no second session format. It reuses the existing OAuth client, but the state has its OWN purpose (purpose: 'social_login', checked BEFORE any other field): it never accepts the state of the git CONNECTION flow to a project, which would be privilege escalation. New table social_identities (migration 0047), key (provider, provider_user_id) — never email/login. A three-step decision: known identity → login; email matches an existing account AND verified by the provider → links (and verifies the account's email if it wasn't yet); email matches but NOT verified → refuses — a typed email isn't proof of ownership, accepting it would open account takeover; no matching account → provisions a new account without a password, same "pending" state as the Keycloak migration. It reuses the SAME OAuth app as the git connection — zero new environment variables, only different redirect_uri/scope per flow; the OPERATOR's action of registering the second callback in the provider is what justifies the breaking/ branch.

    fluxo.yml × code audit — the Dev Lead's plan becomes a real approval (RN-284, ADR 0086)

    Not a planned phase: it closes the divergence a read-only audit of docs/fluxo.yml × code found (finding A2, docs/explanation/auditoria-fluxo-vs-codigo.md) — the flow already declared the dev-lead's plano-de-paralelismo output as via: proposed_action since ADR 0085, and the code was never adjusted to match. The product owner decided the code was wrong.

    propose_execution_plan entered decide.ts (minimum role maintainer), DELIBERATELY outside the absolute ceilings block — it can be configured to auto-approve, unlike parallelize/raise_max_parallel. The Dev Lead is the FIRST conversational agent (they all run a synchronous turn via GenServer.call of up to 180s) to suspend waiting for a human decision — the pattern already existed for the dev agent (ADR 0052) and the QA/Infra gates (ADR 0057), but those two are triggered by cast and never had to deal with a pending synchronous from. TurnoAssincrono.tratar_resultado/2 gained a branch: when the :aguardando_aprovacao key is present (checked by VALUE, not by presence — the Dev Lead carries it as nil since init/1), it replies to from the same way and at the same time as always, but emits only agent.status: awaiting_approval instead of agent.done — the turn hasn't ended. LiveBroadcast.agent_status/4 got the new status in its guard. The resumption uses the SAME Engine.Dev.Wake that QaLeadServer already reuses for the QA subagents (delivery is per AGENT, not per type).

    Accepted gap, declared: without its own state table, an engine restart while the Dev Lead is suspended loses the subscription — the decision remains recorded and visible in Approvals, but it doesn't narrate the outcome on its own. Closing this would require the same persistence mechanism as ADR 0052; out of scope for this fix, which only aligns the behavior with what docs/fluxo.yml already declared.

    UX Designer — the fifth conversational agent, brought forward (RN-285..287, ADR 0087)

    It's not a triggered separation trigger — docs/fluxo.yml always declared "when the MANAGED project has its own interface to design" as the criterion, and it didn't fire: the design system remains static input. A CONSCIOUS decision by the product owner to bring the role forward anyway.

    Engine.Agents.UxDesignerServer mirrors DevLeadServer — a GenServer per session, ceiling of 14 iterations, activated by an accepted handoff addressed to "ux-designer" through the already existing GENERIC mechanism (no line changed in ActivateAgentUseCase). SOLO: no area, no subagents. The kickoff reads the most recent artifact.product_brief — the SAME "business need" the Criativo produces, without a new artifact — and the design system (design/tokens.css, design/COMPONENTS.md) is DESCRIBED in the agent's identity (Engine.Harness.Agents), static text: the conversational agents have no tool to read repository files.

    propose_prototype is the ONLY tool (personas, jornadas, prototipo with telas/anotacoes, resumo). It writes artifact.prototipo_navegavel without a dedicated use case in the api — unlike choose_project_image/create_c4_diagram, which need one because they have content DERIVED from another artifact or a shared domain refusal; neither reason holds here, so the shape validation lives in the engine (ArtifactSchemas) and the write uses the generic append_event_returning the api already exposes, the same path as artifact.product_brief. One single artifact, two handoffs about it — to "po" and to "dev-lead" — never a second artifact for "spec-visual": the prototype (screens + annotations) IS the visual spec, and duplicating it would risk the two copies diverging later. It reuses the half of ADR 0086's design that survives without its suspension: a successful propose_prototype ends the turn, so the model doesn't propose again and duplicate the artifact — without the "aguardando_aprovacao", because proposing a prototype has no external effect.

    apps/web/src/lib/agents.ts got the entry (color: var(--accent), the least reused semantic token of the roster; icon: PencilIcon). uxDesignerActive entered the roster in BOTH sources RN-090 requires in sync — the team panel (agent-status.ts) and the dashboard card (projects-summary.repository.ts, the same infraActive query widened, no new query).

    Out of reach, declared: teste-de-usabilidade requires a real human user — no agent replaces that. metricas-de-uso remains a gap even with analytics active (ADR 0089): the funnel report measures session→commit→PR→merge, not feature adoption by the FINAL users of the project Brabo builds — "evidence of adoption per feature" is DECLARED as a metric with no path to exist today, not a pending item to close next round.

    Staff — code ready, dormant for automatic triggering (RN-305/306, ADR 0088)

    Not a planned phase: docs/fluxo.yml declares the Staff/Principal Engineer as status: planned since ADR 0085 ("contract ready, activation decided, waiting for a trigger"). A CONSCIOUS decision by the product owner: bring the CODE forward knowing the AUTOMATIC trigger (the Anamnese noticing a RECURRING systemic problem) won't fire — the Anamnese is paused (ANAMNESE_ENABLED=false, decision of 2026-08-10). Dormant for automatic triggering, not for MANUAL invocation.

    The sixth solo conversational agent (Engine.Agents.StaffServer), alongside Criativo/PO/Arquiteto/Dev Lead/UX Designer, mirroring the Arquiteto (bounded loop, ceiling 14) with two differences: NO kickoff/1 (there is no session artifact to summarize — it comes up and stays idle until the first user_message, which is how whoever addressed the handoff explains the problem) and activated by the GENERIC path of canActivateAgent (an accepted handoff addressed to "staff"), without entering USER_STARTED_AGENTS — investigation confirmed that no domain change in the api was necessary, because assertHandoffTargetAllowed only refuses an area subagent and the Staff has no area. The only tool, propose_rfc (problem, options with trade-offs, recommendation, disposable PoC), writes artifact.rfc_staff DIRECTLY via append_event_returning — the same tableless pattern as emit_insight, and not that of artifact.c4_diagram (which derives the Container level from the module_map in the api) — and returns the handoff to the Arquiteto in the SAME tool call, without a proposed_action (recording a document is not an external effect).

    staffActive entered the team panel roster and the dashboard card (ProjectCardSummary.roster), same criterion as infraActive, so as not to open the divergence the RosterFacts comment already warned about. Declared, not hidden: SessionPage.tsx/AGENTES_DE_CHAT were not touched — the same pattern already accepted for infra (a REAL and ACTIVE lead also outside that list). The end-to-end usage path today is the internal route (POST .../agent/message, agent: "staff"), not the Session screen; the generic "manual handoff to an agent of choice" UI remains in the backlog.

    The implementavel gate active — QA strategy as the qa-lead's second moment (ADR 0090)

    A conscious decision by the product owner to bring forward the trigger docs/fluxo.yml already foresaw ("when the implementavel gate activates") — the trigger HERE is the very work of building the mechanism, not a usage symptom waiting to happen. docs/gates.yml, implementavel: status: planned → active (owner dev-lead, severidade: warn untouched — the registry already said "it's born warn even when it activates").

    QA strategy stops being a proposto role: it is the qa-lead ITSELF, in a second MOMENT — same process, a deliverable separate from the PR verdict, exactly as docs/fluxo.yml already declared ("it may be the qa-lead itself in a second MOMENT, not necessarily a new agent: the separation is by deliverable"). Engine.Gates.QaLeadServer.run_design/3 is a NEW and ADDITIVE entry point (without touching run/2, the usual path, tied to DevAgentState.find_by_task_id), triggered by Engine.Gates.Dispatcher.run_qa_estrategia/3 (the same test-swappable indirection run_qa/2/run_secops/2 already use).

    Engine.Gates.QaEstrategiaAgent is a STATELESS module (not a GenServer), the same shape as QaPerformanceSegurancaAgent — a registry without Terminal (ReadFile, SearchWorkspace, EmitPlanoDeTeste) —, but the CONTEXT is different: Engine.Gates.QaEstrategiaContext.fetch/3 fetches ONLY the story (from list_backlog) and the current module_map (from get_infra_context, reused only for the moduleMap field — zero new route), without dev_state or worktree_path, because the gate runs PRE-DEV: there is no dev agent, worktree or task_id yet. None of the three tools goes through the ActionPipeline (only terminal/write_file do), so this agent NEVER suspends — run_design/3 runs synchronously inside its own handle_cast. The iteration ceiling stays at 8 (conversational), not 60 (gate) — ON PURPOSE: with no token_budget_micros underneath (there is no task, PRE-DEV), the same reason infra-workflows stays at 8 even while using a tool (RN-085). The deliverable (emit_plano_de_teste: synthesis, executable criteria, a GENERIC automation strategy with no framework) becomes artifact.plano_de_teste in the event log of the calling session.

    assess_implementability, a new Dev Lead tool, reads the most recent artifact.plano_de_teste of the story in its OWN session's history: with no plan yet, it triggers the assessment and returns an error asking for a retry (a tool error is loop INPUT, not the end of the line — RN-163); with a plan, it proposes the opinion (implementavel/inviavel + justification, plan embedded in the payload) as a proposed_action, the SAME three-outcome pattern as propose_execution_plan (ADR 0086) — maintainer, DELIBERATELY outside the absolute ceilings block of decide.ts.

    appsec stops being proposto — the SecOps second moment comes in the next section.

    appsec gets the secops second moment (RN-360/361, ADR 0090)

    docs/fluxo.yml (id: appsec, camada_seguranca) declared in advance "same pattern as QA: two MOMENTS, not two agents for now" — a conscious decision by the product owner to bring the activation forward, without waiting for the implementavel gate (front qa-estrategia, same conceptual ADR 0090) that the registry itself cited as the trigger.

    Engine.Gates.SecOpsAgentServer.run_design/2 runs in the SAME process as the PR secops (same Registry key), without any Diff/Scanner/ DevAgentState: it fetches the story from the backlog + the current module_map (Engine.Gates.AppSecContextBuilder, without dev_state/worktree_path) and calls Engine.Gates.AppSecAgent.run/3 — a STATELESS module (not a GenServer, the same shape as QaPerformanceSegurancaAgent), a tool registry WITHOUT Terminal, running a STRIDE-lite checklist via ToolLoop.run/1 over the story's DESIGN, never over code. It ends by emitting artifact.threat_model and creating a handoff to the three declared leads (arquiteto, dev-lead, infra — the addressable AGENT of the id area-infra, RN-361).

    Declared gap, not a bug: run_design/2 is INVOKABLE, but nothing invokes it on its own yet — the natural trigger is the Dev Lead's assess_implementability (front qa-estrategia), out of scope for this delivery, which was kept self-contained (decide.ts/docs/gates.yml/dev_lead_tools.ex untouched).

    analytics/delivery-metricas become a report (RN-320..322, ADR 0089)

    A conscious decision by the product owner to BRING FORWARD two roles of the target model (docs/fluxo.yml, status: proposto) without waiting for the organic trigger each one already declared. The shape is the one the flow itself prescribed: analytics "absorbed by medicao" until a PRODUCT metric becomes mandatory PO input, delivery-metricas "never becomes an agent — it becomes a REPORT of medicao".     It measures FOR REAL, over proposed_actions.execution_result of the dev agent's three git actions (git_commit/pr_open/git_merge, only status: 'executed'): a real funnel (how many sessions produced a commit / opened PR / merged PR, and the conversion between stages — it counts SESSIONS, not actions), real lead time (first commit to the session's first merge, by the EXECUTION's updated_at, not the proposal's) and real deployment frequency (merge into a PROTECTED_BRANCHES branch, per day, cross-referencing the backmerge gate of docs/gates.yml — whose evidence is CI, out of reach of a script that only reads the database).

    secops-runtime as a report script (RN-375..377, ADR 0091)

    A decided bringing-forward by the product owner of the secops-runtime role (docs/fluxo.yml, camada_seguranca, previously proposto), without waiting for the declared trigger ("production with real traffic, after DEPLOY_ENABLED + platform active"). It's a SCRIPT, not an LLM agent nor a GenServer: there's no decision to make about the data, only aggregation.

    Automatic incident detection, incident response and security postmortem remain OUT — they depend on the same trigger that didn't fire — and the report lists them in a PERMANENT "not measured" section, without simulating an example incident nor inventing a number (same principle as ADRs 0041/0042/0077). The retained window is short by design (DomainGaugesCollector.pruneRateLimit deletes hits older than 2 × RATE_LIMIT_WINDOW_MS, 240s by default), and the report declares both windows — CONFIGURED and OBSERVED — never letting the second pass for a longer history than it is.

    platform gets a first delivery: an on-demand telemetry report (RN-385/386, ADR 0092)

The role's gate_saida: { id: operavel, status: planned } doesn't change; docs/fluxo.yml only gets a nota on the telemetria-consolidada output saying the manual/on-demand version is already real.

    Real SMTP in MailSender (RN-408, ADR 0096)

    It closes the backlog item open since the Keycloak cutover (ADR 0032, "real SMTP remains future config"). nodemailer over pure SMTP transport (a LINE protocol with state/MIME/STARTTLS/AUTH, unlike the HTTP JSON APIs the rest of the product integrates), behind MAIL_TRANSPORT — log (default, INCLUDING in production: sending real email is the operator's opt-in) or smtp, selected by useFactory in AuthUseCasesModule without touching any use case (RegisterUseCase, RequestPasswordResetUseCase, LoginUseCase, the migrate-keycloak-users.ts script keep just injecting MailSender).     "N agents online" on the dashboard — LIVE status, never historical presence (RN-409, ADR 0097)

    An item of the previous backlog closed. Prior investigation confirmed there was no liveness aggregate at all, neither per project nor per workspace — only HISTORICAL presence (RosterFacts, "has appeared at some point") and real live status only on the client, derived from the event log, only when a project is OPEN. ProjectCardSummary.onlineAgentCount adds two mechanisms by the SAME rule ("not idle, not stuck"): dev agents (engine.dev_agent_states.status NOT IN ('idle', 'idle_tripped'), aggregated in batch in the engine) and conversational agents (the last agent.status of the most recent session with status !== 'idle', a payload that only accepts working/idle/awaiting_approval). QA/SecOps never count — they don't emit agent.status, a single verdict per invocation, with no notion of "idle" between calls.

    The architecture decision worth recording: the query reads engine.dev_agent_states DIRECTLY, via raw SQL batched by workspace, inside the SAME Promise.all that already adds up eleven queries of the RN-090 read model (TWELVE → FOURTEEN, still CONSTANT) — instead of opening a new internal HTTP route in the engine. api and engine share the SAME physical database, separated only by Postgres schema, and there was already a precedent (apps/api/scripts/medir-execucao.ts already reads engine.oban_peers); this decision raises the pattern from a manual script to TESTED production code (a minimal, declared fixture of the engine table in test/support/global-setup.ts). Consequence accepted and declared in ADR 0097: the query assumes whoever operates the product migrates both sides together (db:migrate AND engine:migrate), and fails loudly/visibly if only the api migrated — no try/catch hiding the error.

    An execution session no longer closes with a pending dev agent (RN-411)

    A fix for a defect found in a REAL execution session, not a script item: five dev agents came up, became idle_tripped (RN-047, the circuit breaker) stuck waiting for the user to unblock task by task, and the session's 30s heartbeat (Engine.Sessions.SessionServer) closed the session underneath while the manual unblocking went on. The third signal of GetSessionPendingWorkUseCase (RN-064) only reads agent.status, the conversational agents' vocabulary — dev agents speak dev.* (Engine.Dev.AgentIo) and never emit agent.status, so no dev agent ever held the session through that signal. The fourth signal reads the last dev.* event of each dev-<modulo>/dev-<modulo>-2 in the session: dev.working/dev.blocked/dev.idle_tripped hold the session (stuck waiting for a human decision IS pending work); only dev.idle (truly drained) doesn't hold it. dev.awaiting_gate/dev.awaiting_approval ENTERED the rule through RN-412 — see below; the residual gap this paragraph described was closed.

    Automatic personal workspace on sign-up (RN-410)

    Found while browsing: the dashboard's "New project" button did NOTHING, with no error. Root cause: RegisterUseCase and SocialLoginCallbackUseCase (in the branch that provisions a new account) created a user and a credential but NEVER a workspace — EVERY new sign-up hit that wall, and it only didn't show before because seed.ts always creates a workspace along with the demo data.     413 on PRs and Executors "without execution" — the two ends and the chain (RN-412, ADR 0098)

    Not a planned phase: a fix requested by real USE ("on PRs it's always blowing up with entity too large") plus the sibling defect of the Executors tab showing up empty with real work going on. Investigation found the two chained: the gate dies with 413 → devs get stuck in dev.awaiting_gate → that state didn't hold the session (the gap of RN-411) → the 30s heartbeat closes the session underneath → the tab requires an active session and vanishes with the whole roster.

    The cause of the 413 was Brabo's API, not the LLM provider — the comments that attributed the error to the provider (runtime.exs, terminal_executor.ex, docker-compose.yml) were wrong; FalhaDeTurno.origem({413, _}) already classified it as "codigo", and was right. apps/api/src/main.ts never configured Express's body limit — the 100 KB default applied, far below the 8 MB that Phoenix accepts, in the transport's heaviest direction (engine → api, POST /internal/sessions/:sessionId/llm-turn, which resends the WHOLE history on each ToolLoop iteration). API_JSON_BODY_LIMIT (default 10 MB) closes the transport end.

    The second end, without which raising the limit would only postpone the overflow: the engine's ContextManager (ADR 0098) had TWO defects that kept compaction unreachable before the body overflowed — estimate/1 counted only content, so assistant messages full of toolCalls cost ~zero tokens in the estimate; and the compaction window used only context_window (128,000 tokens in the gate agents), which gave ~350 KB before compacting — well after any reasonable transport ceiling. The EFFECTIVE window is now min(context_window, teto_de_transporte), with the cut always on a ToolLoop ITERATION BOUNDARY (never separating an assistant with toolCalls from the role: "tool" ones that answer it — it would break the provider's tool-use protocol).

    RN-412 extends RN-411: DEV_PENDING_TYPES gained dev.awaiting_gate (the original argument — a gate can die and lock the dev agent in that state indefinitely) and also dev.awaiting_approval, by a new argument found in the investigation: the approval decision writes proposed_actions.status SYNCHRONOUSLY, but the dev agent's resumption via outbox/Oban is ASYNCHRONOUS — in the window between the two, nothing held the session, the same defect as RN-411 one level deeper.

    The Executors/Overview tab had the sibling defect on the web side: executionActivated was derived from events.some(...) over the window of only 200 events of useSessionEvents — execution.activated is among the FIRST events of a session and left the window in any real execution, erasing the whole roster. The correct value already existed, aggregated over ALL the events, in the workspace summary (RN-090, projects-summary.repository.ts) — the two screens started consuming that value. A bonus finding along the way: ExecutionSection (Overview) recomputed activated again, independently, over the same window — a long execution went back to offering "Activate execution" as if it had never started; fixed along with it. gatesEverOpened suffers from the SAME class of defect and was DECLARED as a known limitation, not fixed here — fixing it would require changing the signature of deriveAgentRoster/rosterFactsFromEvents, out of scope for this targeted fix.
