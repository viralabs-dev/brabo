    Как потребляется каждый репозиторий

    Для кого: для тех, кому нужно решить, как один репозиторий передаёт что-то другому.

    После прочтения вы сможете: выбрать подходящий канал для каждого ребра вашей карты и сказать, какой файл фиксирует версию и какая проверка это доказывает.

    Правило, проходящее через всё: каждый канал закрепляет точную версию и имеет проверку, которая её контролирует. Потребление «последней» версии другого репозитория - то, из-за чего один и тот же коммит переходит из зелёного в красный.

    Шесть способов

    # Способ Кто публикует Кто потребляет Что фиксирует Кто доказывает
    1 Контракт по тегу brabo-contracts api, web, runner, broker, engine, qa, infra точная версия в package.json и lock-файле contracts-alinhado
    2 Политика по SHA brabo-ci все 11 репозиториев uses: ...@<sha> и ci_ref pins-do-brabo-ci
    3 Соседний клон каждый репозиторий (его dev) brabo-infra и brabo irmaos.lock (в brabo) docs:check
    4 Образ по digest api, engine, web, broker и образ резервного копирования brabo-qa и установщик digest sha256 E2E do brabo-qa
    5 Подписанный бинарный файл brabo-runner install.sh в brabo подписанный checksums.txt install.sh и release.yml
    6 Пин продукта все компоненты brabo componentes.json Pins dos componentes

    1. Контракт по тегу

    brabo-contracts публикует пакеты в GitHub Packages (@viralabs-dev/brabo-shared и @viralabs-dev/brabo-docker-port) и три файла данных, загружаемых по raw-ссылке с тем же тегом. Потребитель закрепляет точную версию через алиас pnpm, не меняя импорты:

    pnpm add "@brabo/shared@npm:@viralabs-dev/brabo-shared@1.2.0"

    Закреплять ветку нельзя никогда. Когда выходит новый тег, каждый потребитель поднимает версию скриптом subir-contracts.sh, а проверка contracts-alinhado отклоняет расхождение между алиасом, lock-файлом и константой скриптов загрузки.

    2. Политика по SHA

    Каждый репозиторий вызывает workflow brabo-ci так:

    uses: viralabs-dev/brabo-ci/.github/workflows/pr-police.yml@<sha>  # v1.4.0
with:
  ci_ref: <тот же sha>

    uses: выбирает YAML, а ci_ref выбирает скрипты, поэтому оба должны быть одним и тем же 40-символьным SHA. Комментарий сообщает версию читателю, а проверка pins-do-brabo-ci проверяет, что комментарий соответствует SHA (ADR 0280). Пошаговое описание - в руководстве по внедрению.

    3. Соседний клон

    Два репозитория читают код остальных:

    • у brabo-infra есть action irmaos, который выгружает dev соседей для перекрёстных проверок;
    • brabo восстанавливает раскладку всех репозиториев через scripts/docs/montar-layout.sh для генерации документации. Здесь версия зафиксирована: irmaos.lock хранит SHA каждого соседа, а обновляет его бот regenera-gerados (ADR 0274). Человек этот файл не правит.

    Разработчики применяют тот же принцип на своей машине: clonar-tudo.sh из brabo-workspace клонирует всё рядом, а скрипты читают соседей через BRABO_IRMAOS.

    4. Образ по digest

    Каждый тег api, engine, web и broker публикует образ контейнера, подписанный cosign. Ворота main (brabo-qa) преобразуют тег в digest (image@sha256:...), проверяют, что у запущенного контейнера именно такой digest, и проверяют подпись. Тег - указатель, который можно переместить; digest - нельзя (ADR 0267).

    5. Подписанный бинарный файл

    brabo-runner не публикует образ: он работает на машине пользователя. К релизу он прикладывает бинарные файлы и подписанный checksums.txt. install.sh скачивает бинарный файл тега, который закрепляет componentes.json, и сверяет его с этой подписью.

    6. Пин продукта

    Файл componentes.json в корне brabo говорит, какой тег каждого компонента образует продукт:

    "imagens": { "api": { "repo": "viralabs-dev/brabo-api", "tag": "v2.1.0" } }

    Пин сам не движется, но его поднимает бот: каждые 6 часов он читает последний финальный релиз каждого компонента и открывает PR, меняющий только тег, а слияние делает человек. Проверка Pins dos componentes отклоняет продвижение продукта, если какой-то пин отстаёт (релиз продукта).

    Для вашего проекта: для каждого ребра карты запишите четыре вещи: кто публикует, кто потребляет, какой файл хранит версию и какая проверка срабатывает при расхождении. Если проверки нет, ребро ещё не готово.
