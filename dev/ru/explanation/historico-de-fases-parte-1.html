    История фаз, часть 1: фазы 1–15

    Запись от 8 августа 2026 г.: описывает Brabo на ту дату

    От фаз 1–12 через 13 (доказать и рассортировать), 14 (что потребовало реальное выполнение) и 15 (gate-ы как данные) до пост-фазы 15 (v2.5.0 и v2.5.1). Текст перенесён без переписывания из Истории фаз. То, что действует сегодня, находится в RN и ADR.

    Статус

    • ФАЗА 1 (MVP) — ЗАВЕРШЕНА: IAM/RBAC, сессии с неизменяемым event log, чат с маршрутизатором LLM (Ollama + API), metering/бюджет токенов, конвейер proposed_actions + permissions.json, движок Elixir/OTP с супервизией и событием завершения.
    • ФАЗА 2 — ЗАВЕРШЕНА: GitProvider (Local/GitHub/GitLab) с контрактным набором тестов и capabilities, зашифрованные учётные данные, идемпотентный и возобновляемый через конвейер bootstrap Gitflow, мастер с прогрессом в реальном времени.
    • ФАЗА 3 — ЗАВЕРШЕНА: Harness (PromptAssembler, ToolLoop, ContextManager, InstructionFiles, Hooks), явные handoffs, агенты Criativo, PO и Arquiteto с артефактами и проверками в домене.
    • ФАЗА 4 — ЗАВЕРШЕНА: агенты выполнения (динамические dev по модулю в изолированных worktrees, QA и SecOps как gate-ы PR, проактивная Infra), блокировка защищённого merge, живая панель команды; настоящий Psicólogo и Anamnese с замкнутым циклом. Gate-ы проверены реальным выполнением (ADR 0020).
    • ФАЗА 5 — ЗАВЕРШЕНА: образы production non-root и CI (ADR 0024), Kubernetes с Kustomize, HPA по очереди Oban, NetworkPolicies и ESO (ADR 0025), graceful shutdown + OpenTelemetry + dashboards (ADR 0026), бэкап с протестированным restore, runbooks и hardening (ADR 0027).
    • ФАЗА DOC — ЗАВЕРШЕНА: docs/ как единственный источник по Diátaxis, сайт Docusaurus в website/, читающий из docs/, генерируемые справочники, docs/.docmap.yml + проверка дрейфа (docs:check) в CI, слой сообщества, проверенная MIT, механизм задокументирован в docs/explanation/documentation-workflow.md.
    • ФАЗА 6 — ЗАВЕРШЕНА: механизированная политика веток (ADR 0030) — pr-police, approval-ladder с двумя режимами, promote/tag-release с вычисляемой версией и якорем по дереву, backmerge gate с автоматическим обратным распространением, версионируемые rulesets. Конвейер проверен от начала до конца (v0.1.0 → v0.2.0), а цепочка hotfix подтверждена реальным выполнением.
    • ФАЗА 7 — ЗАВЕРШЕНА: first-party auth вместо Keycloak — argon2id, access Ed25519, ротация refresh с отзывом семейства, прогрессивный lockout, токены учётной записи и MailSender только в лог (ADR 0031, RN-030..033); атомарный переход с собственным эмитентом, RBAC нетронут, /internal/* с service token, cookie httpOnly + CSRF, миграция пользователей и полное удаление Keycloak (ADR 0032, RN-034/035); OpenAPI в 23 контроллерах с DTO, закреплёнными по типу, табличный тест, требующий метаданных, сгенерированный docs/reference/api/ с манифестом хешей (ADR 0033).
    • ФАЗА 8 — ЗАВЕРШЕНА С ОТСЕЧЕНИЕМ: иерархия агентов — области с единственным lead как внешним контактом, приватные внутренние делегирования (таблица delegations, area как TEXT), консолидированный вердикт с прослеживаемостью, сбой с источником; QA как область (Lead + Автоматизация + Производительность/Безопасность, внешний контракт gate-ов не изменён — набор тестов Фазы 4 зелёный без изменений); Infra как область с субагентом Workflows, генерирующим CI по provider-у; панель команды по областям и Psicólogo/Anamnese, нацеленные на субагентов (ADR 0038). ОТСЕЧЕНИЕ ОБЪЁМА того времени, ОТМЕНЁННОЕ ФАЗОЙ 14d: agent_areas/agent_area_members существуют с тех пор, по проекту, с настраиваемым max_parallel — заставила это область dev, первая ДИНАМИЧЕСКАЯ. Список в apps/web/src/lib/agents.ts уцелел для цвета, иконки и ПРАВИЛА адресации; участники dev берутся из таблицы.

    ФАЗА 14 — ЗАВЕРШЕНА 2026-08-07 (что потребовало реальное выполнение)

    Выполнение hello world не прошло дальше первого хода и выявило дефекты, которые не ловил ни один набор тестов, потому что всё до этого работало с ЛОКАЛЬНОЙ моделью. Исправления уже внесены; остаётся функциональность, решённая пользователем во время выполнения.

    14a — Операбельность агентов (ЗАВЕРШЕНА)

    • Сбой хода стал ДОЛГОВЕЧНЫМ agent.error с источником, и агент ГОВОРИТ в нити; четыре разговорных агента перестали записывать пустой agent.response (RN-059). Путь ошибки, рассказанной в финальном frame-е, который не выдавал ни одного события, тоже закрыт.
    • Чат Criativo открывается приглашением, а не пустотой: он активируется и ждёт, пока пользователь заговорит первым, и экран теперь говорит об этом — в том числе что технология и код — НЕ его дело.
    • Ключ, который тратит агент, — ключ OWNER-а workspace (RN-058). Раньше ход искал учётные данные по SLUG агента в столбце UUID: ни один агент никогда не использовал provider с учётными данными, и работал только ollama.
    • Отчёт о расходах по ключам, только для владельца, с агентом, отделённым от человека (RN-060).
    • Bootstrap Gitflow в GitHub: только что созданный репозиторий отвечает 409 во всём Git Data API, и первый commit проходит через Contents API. Поддельный backend тестов лгал (404 там, где GitHub отвечает 409) — исправлено заодно, именно это держало набор тестов зелёным при сломанном продукте.

    14b — Древовидная временная шкала (ЗАВЕРШЕНА)

    Одна ветвь на агента, от первой вехи до того, что он делает СЕЙЧАС, выведенная на 100% из event log, который экран уже получает. Хронологическая лента остаётся в столбце активности: она отвечает «что произошло», дерево отвечает «кто что делает».

    Пересмотрено после ФАЗЫ 26 (без новой фазы, в том же духе точечного исправления, что 12d/ПОСЛЕ-ФАЗЫ 15): критерий открытия по умолчанию сменился с одного лишь «активен/стоит» на 5 агентов с самой СВЕЖЕЙ активностью — активный по-прежнему в приоритете (RN-118); каждая свёрнутая ветвь получила собственный счётчик НОВИЗНЫ, с «последним просмотренным» по агенту в read-state.ts (тот же механизм, что у колокольчика, теперь гранулярный); а tool.call/tool.result/agent.response стали раскрываться ПО ОТДЕЛЬНОСТИ (аргументы, результат, итерация), сгруппированные по границе итерации ToolLoop.

    14c — Автоматическая проверка UI (ЗАВЕРШЕНА)

    Контраст стал тестом над design/tokens.css, с известным долгом, измеренным и закреплённым; макет (обрезанный текст, меню вне viewport, dropdown, обрезанный предком, цель < 24px) стал браузерным проверяющим в scripts/dev/validacao-visual.js. Без новой зависимости.

    14d — ЗАВЕРШЕНА: параллелизм решает LEAD, разрешаете вы

    Сдана в четырёх PR (#181, #182, #183, #184). ADR 0053 стал ПРИНЯТЫМ, окончательно отменив три отсечения (Dev Lead, динамические области через module_map и общий аппарат областей).

    1. Области стали данными: agent_areas/agent_area_members по проекту, с max_parallel по умолчанию 2. Заставила это область dev — первая ДИНАМИЧЕСКАЯ, чьи участники — по одному на модуль module_map. То, что не перечислимо в коде, должно быть данными.
    2. Предел принадлежит СЕССИИ, а не модулю (RN-083). Счёт по модулю позволил бы N модулей × 2 без какого-либо разрешения — прежняя дыра под другим именем. Выше предела становится proposed_action.
    3. Настраивается по области в Настройках, требуя maintainer по той же причине, что и активация выполнения: изменить предел — значит решить, сколько продукт тратит, не спрашивая.
    4. Anamnese предлагает повысить, когда разрешение стало рутиной, — три одобрения и НИ ОДНОГО отказа (RN-086). Один отказ гасит сигнал: если вы хоть раз отказали, предел делает свою работу.
    5. Dev Lead существует (RN-087), разговорный, получающий handoff от Arquiteto в том же подтверждении, которое уже передаёт Infra, и предлагающий план: сколько агентов на модуль и почему. dev-<modulo> перестали быть адресуемыми через handoff — правило ADR 0038 стало действовать для dev так же, как уже действовало для QA и Infra.

    Находка X закрыта здесь (RN-085): TOOL_LOOP_MAX_ITERATIONS стал пределом ПО ТИПУ — 8 для разговорного, 60 для выполнения и gate. Критерий того, кто поднимается, — НЕ «кто много работает»: это тот, у кого под ним есть token_budget_micros, удерживающий расходы. infra-workflows использует тяжёлый инструмент и остаётся на 8, потому что работает без бюджета.

    Три пробела самой фазы, найденные мной при написании следующего среза, и все — один и тот же сбой: правило предела вошло с зелёными тестами, а продукт его не задействовал — ни один маршрут не вызывал вариант использования, одобрение действия ничего не выполняло, а тип мог быть автоматически одобрен через permissions.json (закрыто RN-086). Тестировать деталь — не значит тестировать путь к ней.

    Вне объёма, по объявленному решению (ADR 0053, пункт 5): смена владельца кнопки «Ativar execução». Делегирование Dev Lead → dev-<modulo> через таблицу delegations с area = "dev", которое этот же пункт тоже объявлял, ПЕРЕСТАЛО быть вне объёма — закрыто ADR 0094 (Аудит fluxo.yml × код, Волна 2, RN-405). Кнопка остаётся обратимой; выполнение остаётся на текущем пути, а исправление после gate по-прежнему идёт прямо к dev, открывшему PR.

    ФАЗА 15 — ЗАВЕРШЕНА 2026-08-07 (gate-ы как данные)

    Ни одного НОВОГО gate. Фаза выносит в docs/gates.yml gate-ы, которые УЖЕ неявно существуют в продукте, с проверкой скриптом и серьёзностью, в том же духе, что docs/.docmap.yml. Gate агента, которого не существует (dev-lead, platform), входит как status: planned со ссылкой на backlog — никогда как активный. Внешний контракт gate-ов НЕ меняется.

    15a — ЗАВЕРШЕНА: декларативный реестр

    1. docs/gates.yml с существующими gate-ами (см. ADR 0054, расширяющий ADR 0048 — решение в event log делает прохождение gate измеримым), схема проверена тестом.
    2. Загрузчик в api, читающий реестр; внутренний endpoint чтения.
    3. Скрипт pnpm --filter api validacao:gates, который извлекает из event log последнее прохождение каждого активного gate и завершается != 0, если у какого-либо gate block нет улик проверки скриптом.

    Не у каждого gate есть доказательство в event log, и реестр говорит, где оно живёт: merge-protegida гарантирован ТЕСТОМ (блокировка в decide.ts не выдаёт собственного события), а backmerge — это CI, с состоянием в .release/gate.json. Поэтому каждый gate объявляет evidencia: event_log | teste | ci с локатором — понизить их до warn значило бы солгать о самых жёстких блокировках продукта.

    15b — ЗАВЕРШЕНА: потребление

    1. Панель команды показывает gate, которого ждёт каждая story/PR, выведенный из реестра (не захардкоженный).
    2. docs/explanation/gates.md, объясняющий механизм, в docmap.

    ПОСЛЕ ФАЗЫ 15 — ЗАВЕРШЕНО 2026-08-08 (v2.5.0 и v2.5.1)

    Это не запланированная фаза: это то, что ИСПОЛЬЗОВАНИЕ нашло после 15, и оно здесь, потому что происхождение каждого пункта важно. Ничего из этого не пришло из сценария — пришло из навигации по приложению в Chrome и чтения панели безопасности.

    Дефекты UI, найденные при навигации (RN-088..091):

    • 429 превращался в БЕЛЫЙ ЭКРАН, а приложение отвечало ещё большим трафиком. Правило стало общим: каждый экран различает ТРИ состояния — загрузка, ошибка (с trace_id и кнопкой) и пусто. if (!dado) return null схлопывает все три.
    • Dashboard делал по запросу на проект: 3.824 → 12 req/min, с GET /workspaces/:id/projects-summary. Колокольчик был недостающей половиной: 289 → один запрос за цикл (RN-090/091).

    Ужесточение безопасности, с обеими панелями на НУЛЕ:

    • ADR 0058 — закрытый CSP в api (default-src 'none'), пересматривающий пункт 7 ADR 0027; и projectId, ограниченный корнем (RN-092), что затрагивало не только permissions.json, но и область, которая РАЗРЕШАЕТ терминал.
    • ADR 0059 — GIT_OAUTH_STATE_SECRET без значения по умолчанию в production (RN-093). Значение по умолчанию было ПУБЛИЧНЫМ (.env.example), и compose production подставлял его как fallback: требование «не пустая» ничего бы не поймало, потому что на реальном пути ошибки переменная была ЗАДАНА.
    • Алерт, который не выдерживал проверки, был ОТКЛОНЁН с письменным обоснованием, никогда не заглушён — и отклонение — решение пользователя, а не агента.

    Три операционных урока, стоившие цикла CI, и они действуют как правило:

    1. Зелёный CodeQL в PR не доказывает, что старый алерт закрыт — проверка PR сообщает о НОВОМ алерте. Алерт закрывается при сканировании ветки ПО УМОЛЧАНИЮ, то есть только после того, как исправление дойдёт до main.
    2. Gitleaks сканирует commit-ы, достижимые из refs/heads/*, а не дерево. Значение с высокой энтропией, закоммиченное однажды, навсегда проваливает CI на этой ветке; исправление поверх НЕ очищает. Выход — сделать commit недостижимым (пересобрать из dev и УДАЛИТЬ старую ветку ДО открытия нового PR) — никогда allowlist, который ослепляет сканер на этом пути для всех commit-ов. Refs PR в область не входят. Fixture, представляющий секрет, рождается БЕЗ энтропии.
    3. Барьер, живущий в другой функции, CodeQL не видит — отсюда три js/path-injection, пережившие исправление. Проверка осталась централизованной (RN-092), и цена была уплачена на панели: дублирование её в каждом вызывающем было бы проверкой, которая однажды разойдётся.
