    Релиз продукта

    Как Brabo, который живёт в нескольких репозиториях viralabs-dev/brabo*, публикует одну версию продукта (AT-704, EP-033). У каждого репозитория своя версия; у продукта своя — в brabo. Все начинают заново с 1.0.0. Эта страница — общий обзор; детали образов и подписи описаны в Цепочка поставок CI.

    Три этапа

    1. Каждый репозиторий ставит собственный тег. При каждом push в dev и main workflow tag-release.yml репозитория вызывает переиспользуемый tag-release.yml из brabo-ci, закреплённый по SHA. Переиспользуемый workflow вычисляет версию по функции ветки (breaking/ поднимает MAJOR, feature/ — MINOR, остальное — PATCH) и пушит тег токеном GitHub App бота (BRABO_APP_ID / BRABO_APP_PRIVATE_KEY, секреты организации). Это токен App, а не GITHUB_TOKEN, потому что только он заставляет тег запускать workflow публикации.
    2. Репозитории образов публикуют. По финальному тегу brabo-api, brabo-engine, brabo-web, brabo-broker и brabo-infra (образ бэкапа) собирают образ, сканируют его Trivy до подписи, подписывают по digest через cosign keyless и проверяют подпись в том же run. К своему Release они прикладывают imagem.json ({imagem, tag, digest}) — контракт с продуктом. brabo-runner не публикует образ: он прикладывает бинарники и checksums.txt, подписанный его build-runner-binaries.yml.
    3. brabo собирает релиз продукта. release.yml читает componentes.json (тег каждого компонента), скачивает imagem.json из каждого Release, собирает images.json (scripts/ci/montar-images.ts), сканирует образы по digest через Trivy, объединяет install.sh и ассеты brabo-install-* и подписывает один checksums.txt (cosign keyless, идентичность release.yml из brabo). Именно этот манифест проверяет install.sh. Бинарник runner проверяется отдельно, по подписанному checksums.txt из brabo-runner на теге, который componentes.json фиксирует в .runner.tag.

    Шлюз

    Переменная репозитория PRODUTO_RELEASE_LIGADA=true в brabo — единственный ключ, который ставит тег и публикует Release продукта. Когда она выключена, tag-release.yml и release.yml не запускаются (кроме репетиции ниже). Включает её владелец.

    Репетиция. workflow_dispatch для release.yml на ветке с пустым полем tag собирает и проверяет всё, что возможно, но не подписывает и не публикует, и запускается даже при выключенном шлюзе. Без Release каждого компонента образы не собираются, а Trivy и проверка образов остаются до первого тега.

    Что фиксирует componentes.json

    Поле Для чего
    infra репозиторий и ref, откуда берутся compose, .trivyignore.yaml и trivy-do-release.ts
    imagens.<alvo> репозиторий, тег и образ каждого компонента-образа; imagem.json должен совпадать
    runner репозиторий и тег brabo-runner; install.sh скачивает оттуда бинарник (RUNNER_TAG, проверяется scripts/dev/install-runner-release.spec.ts)

    Пин сам по себе в Git не двигается, но его двигает бот (AT-796, ADR 0282): каждые 6 ч regenera-gerados.yml читает releases/latest каждого компонента, проверяет ассет, который потребляет продукт (imagem.json; у runner — checksums.txt и подпись) и, если Release новее, меняет только тег в строке componentes.json. Пин никогда не понижается. infra и образ backup двигаются вместе, а RUNNER_TAG в install.sh меняется в том же коммите. Всё попадает в фиксированный PR chore/regenera-gerados, который пропускает лестницу; merge делает человек.

    Блокировка (scripts/ci/pins-dos-componentes.ts --conferir) падает, если пин отстаёт от Latest, у него нет финального Release, нет ассета, infra.ref отличается от imagens.backup.tag или RUNNER_TAG отличается от runner.tag. Она работает как проверка Pins dos componentes (PR в main) и в release.yml: на теге падает, в репетиции только предупреждает. Пять из пяти образов или ни одного: Release продукта с компонентом без imagem.json отклоняется.

    Хотфикс компонента

    Хотфикс — это PATCH по обычной лестнице (решение владельца, AT-728); hotfix/ напрямую в main не используется.

    1. Компонент исправляется через собственные dev → main и получает vX.Y.Z+1.
    2. Бот открывает или обновляет PR chore/regenera-gerados с новым пином (или владелец запускает regenera-gerados); смерджите его в dev. Пока пин отстаёт, блокировка не пропускает промоушен.
    3. Промоушен brabo выходит как patch продукта.

    Тег без Release из-за отставшего пина

    Если компонент выпустит Release между merge в main и штампом, блокировка release.yml падает на теге, и продукт остаётся с тегом без Release (так было с v2.1.0 и v2.1.1). Выход: смерджить PR бота в dev, выполнить промоушен и выпустить patch продукта. Пример: web v1.2.1 стал Latest, пока пин был v1.2.0; после merge PR бота следующий промоушен несёт web v1.2.1.
