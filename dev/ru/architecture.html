    Архитектура

    Этот документ — карта для тех, кто будет работать с кодом. Он говорит, с чего начинать чтение, что обещает каждая граница и что, как уже известно, кривое.

    Решения и их обоснования живут в ADR — их 282, и многие фиксируют реальный дефект, найденный при исполнении. Здесь мы не повторяем аргумент: мы указываем на него.

    Взгляд снаружи

    Brabo получает продуктовое намерение («хочу систему, которая делает X») и возвращает git-репозиторий с кодом, тестами и историей решений, произведённый командой ИИ-агентов. Между входом и выходом любое действие с эффектом во внешнем мире — запуск команды, коммит, открытие PR, трата токенов — проходит через запрос одобрения, который решает человек.

    Снаружи это веб-приложение. Отличает его то, что работу выполняют долгоживущие процессы, общающиеся с языковыми моделями, и что система построена так, чтобы ничего не происходило без следа и без разрешения.

    Две вещи на этой схеме не очевидны и многое объясняют:

    Engine никогда не говорит с LLM или с git напрямую. Он просит api. Именно это гарантирует, что у metering, бюджета и конвейера одобрения нет обходов — нет пути, который бы их миновал.

    Связь api→engine двойная. Асинхронное событие через transactional outbox в Postgres (потребляемое Oban) и внутренний HTTP для синхронной команды. Outbox существует, потому что запись состояния и публикация события должны быть одной транзакцией; HTTP существует, потому что некоторым операциям нужен немедленный ответ.

    Outbox опустошает три aggregate_type: session (с Фазы 5), task (Фаза 12b — task.gate_resolved/task.became_claimable, перепланирование dev agent после того, как gate разрешается или новая задача становится доступной) и container (ADR 0143 /RN-502 — container.running, присоединяемый в той же транзакции, что регистрирует достижение контейнером проекта состояния running, чтобы dev agents, которых его отсутствие поставило на стоянку в :idle, проснулись сами; собственный агрегат, а не позаимствованный task, потому что событие не касается никакой задачи). Причина, по которой это outbox, а не синхронный HTTP-вызов, как остальные: перезапуск engine между вердиктом gate и реакцией агента не может потерять сигнал — строка переживает процесс, который её прочитал бы, а HTTP не пережил бы смерть того, кто ждал ответа. Dev agent, который ПАДАЕТ (любой выход, кроме :normal/:shutdown), не считается завершённым: Engine.Dev.Monitor записывает долговременный agent.error (источник infra) и перезапускает его из собственной строки в dev_agent_states, до трёх раз; прерванная задача блокируется с диагнозом уже существовавшим восстановлением после перезапуска (RN-742). dev_agent_states получила consecutive_blocked/max_consecutive_blocked (предохранитель, RN-047); полное решение — в ADR 0045. Задача, заблокированная из-за временного сбоя сети/провайдера (DNS, сброшенное соединение, 5xx/429), снова разблокируется job Oban через 1, 3 и 10 мин (до трёх раз, тем же сценарием разблокировки, что и у человека), а dev agent делает паузу на минуту вместо того, чтобы брать следующую задачу (RN-864).

    Агенты gate (QaLeadServer/SecOpsAgentServer) не проходят через outbox на промежуточных переходах (correct/run_secops остаются прямым вызовом в памяти — механическое доказательство в комментарии record-gate-verdict.use-case.ts: только ТЕРМИНАЛЬНЫЕ исходы, done/blocked, путешествуют через outbox), поэтому они получили ТУ ЖЕ страховочную сетку, что уже была у dev agents: gate_states, плюс GateRescuer, который обходит застрявшие циклы и возобновляет их сам, — без новой таблицы для пути outbox, потому что проблема была не в отсутствии outbox, а в отсутствии долговременного состояния для того, что происходит МЕЖДУ двумя вызовами в одном процессе. См. RN-140, ADR 0067.

    У gate QA есть ТРЕТИЙ вердикт помимо approved/changes_requested: needs_user_decision — для требования, которое пользователь никогда не подтверждал (или которому противоречит действующее решение). Он не расходует исправление; QA Lead консолидирует его выше approved, а цикл СТАВИТСЯ НА СТОЯНКУ механизмом ADR 0207, пока пользователь не ответит на вопрос, что его возобновляет. Разговорная сторона того же правила — инструмент declare_open_question (Criativo, PO, Arquiteto, Dev Lead), записывающий artifact.open_question; ответы пользователя возвращаются к dev и QA как «решения пользователя» в dev-context (RN-862, ADR 0214).

    Тот, кто ЗАПРАШИВАЕТ gate, никогда не является самим gate: Engine.Gates.Dispatcher — behaviour с пятью callback (QA для PR и SecOps, два детерминированных gate инфраструктуры и AppSec проектирования — gate стратегии QA ушёл с ADR 0192, когда план тестирования стал первым шагом самого QA для PR), чья единственная работа — поднять GenServer на проект при необходимости и сделать в него cast. Косвенность существует ради тестов вызывающих: Engine.Agents.DevLeadTools проверяется ЛЁГКИМ тестом без sandbox Ecto, и подъём настоящего GenServer там лишь для доказательства того, что gate был ЗАПРОШЕН, привязал бы тест Dev Lead к базе. Самый новый из пяти, run_appsec_design/2, закрыл последний gate, который был вызываемым без вызывающего в production: assess_implementability теперь запрашивает модель угроз проектирования истории ПАРАЛЛЕЛЬНО — вердикт никогда её не ждёт, а запрос происходит один раз на историю (RN-539, ADR 0090).

    apps/web — React 19, 487 файлов в src/ (измерено 2026-09-25)

    src/lib/api-types.ts и src/lib/activity.ts — два файла, которые стоит прочитать первыми: первый — контракт с api, второй классифицирует 40 типов событий лога во что-то отображаемое — это лучший источник истины о том, что означает каждое событие.

    Три вывода из одного event log, отвечающие на разные вопросы:

    файл отвечает
    lib/activity.ts «что произошло» — хронологическая лента
    lib/agent-status.ts «кто существует и в каком состоянии» — карточки команды
    lib/timeline-tree.ts «что сделал каждый агент и что делает СЕЙЧАС» — дерево

    lib/aprovacoes.ts отвечает на четвёртый вопрос, и он идёт не из event log: «что произойдёт, если я одобрю». Глагол и фраза каждого типа proposed_action живут там, и их потребляют три экрана решений — очередь Aprovações, карточка внутри чата и вкладка Insights (RN-096).

    Объединение ActionType БЫЛО копией, и копия устарела — дважды, в production (три типа bootstrap Gitflow; затем parallelize/raise_max_parallel), оба раза незаметно для компилятора, потому что apps/api не является зависимостью apps/web. ADR 0116 закрыл класс: ActionType теперь генерируется openapi-typescript из docs/reference/openapi.json (lib/api-types.generated.ts, реэкспортируемый lib/api-types.ts), а не набирается вручную, и компилятор теперь требует, чтобы карты Record<ActionType, ...> в lib/aprovacoes.ts были исчерпывающими при каждой правке. Остальной api-types.ts — ~1600 строк — по-прежнему написан вручную; мигрировал только этот тип, с доказанной повторяющейся стоимостью. lib/aprovacoes.test.ts тоже остаётся, но для более узкой работы: ему больше не нужно ловить ОТСУТСТВУЮЩУЮ запись (это ловит компилятор), только плохую — слишком короткую фразу, без точки, сырой snake_case, просачивающийся в португальскую прозу. В сомнении UI всё равно деградирует, а не роняет дерево React.

    Дерево инвертирует ось ленты (сначала агент, потом время), потому что в сессии с Criativo, PO, Arquiteto и N dev хронологическая колонка не могла ответить, кто что делал. Ни у одного из трёх нет собственного состояния или маршрута — все выводятся из одних и тех же событий, и событие, которого нет в логе, не появляется ни в одном из них.

    Область чтения: экран проекта спрашивает по сессии, экран списка — по workspace. Внутри проекта запросы идут по сессии и по проекту, что является естественным срезом открытого. Но дашборд и боковая панель показывают ВСЕ проекты, и там срез по проекту превращается в N+1 — было семь запросов с опросом на карточку, 3.824 запр./мин при 23 проектах против лимита 300, и экран ронял сам себя ответами 429. Оба читают GET /workspaces/:id/projects-summary — read model, пересекающую агрегаты (git, бюджет, сессия, backlog, архитектура), число обращений к базе в которой не растёт с количеством проектов (RN-090).

    Ящик колокольчика следует тому же срезу, с одним отличием, которое стоит зафиксировать: ему нужна точка отсечки прочитанного для каждого проекта, а эта точка — seq, хранящийся в браузере смотрящего (lib/read-state.ts), — у сервера её нет и не будет «отметить как прочитанное». Поэтому клиент отправляет карту project → afterSeq в теле POST /workspaces/:id/unread-events, которое является чтением, несмотря на глагол, и возвращает 200 (RN-091). Глагол вытекает из тела, а не из мутации: это десятки пар, а строка запроса такого размера ломается на прокси, не говоря уже о том, что кладёт id проектов в логи доступа.

    Этот endpoint возвращает ФАКТЫ из event log, а не собранные компоненты: lib/agents.ts (кто lead, иконка, цвет) и rosterFromFacts (lib/agent-status.ts) остаются работой web, а правило присутствия — то же, что использует панель команды. Это та же граница, что у трёх выводов выше: api говорит, что произошло, а web решает, что из этого рисуется.

    Две проверки UI автоматические: контраст (lib/contraste.ts, тест по design/tokens.css) и раскладка (scripts/dev/validacao-visual.js, запускаемый в браузере). Объяснены в design/README.md.

    Установка решает, что предлагает мастер проекта. getProjectsBase (lib/api-client.ts) читает GET /workspaces/:workspaceId/projects-base — единую базу смонтированных проектов этой установки (ADR 0141), — и мастер Нового проекта — её единственный вызывающий (RN-513). projectsBase: null — нормальное состояние, а не сбой: у установки нет BRABO_PROJECTS_BASE, поэтому карточка смонтированной папки просто не предлагается, а container остаётся по умолчанию. То же верно, пока ответ в пути и когда запрос ПРОВАЛИВАЕТСЯ — неизвестное никогда не становится предложением, то же правило, что в RN-088/RN-468. С базой карточка приходит ПРЕДВЫБРАННОЙ, а поле пути открывается с <base>/<slug>, составленным caminhoSugeridoNaBase (lib/wizard.ts) — чистой функцией рядом с caminhoDentroDaBase, которая отвечает «находится ли этот путь под базой?» по СЕГМЕНТУ и отражает dentroDoEscopo из api. Ни предвыбор, ни подсказка не перезаписывают человеческий выбор.

    Выбор папки — единственное чтение web с ДВУМЯ ТРАНСПОРТАМИ, а интерфейс, делающий его одним, живёт в lib/fs-browser.ts (RN-504). У FsBrowser — listarDiretorio / diretorioInicial / fechar — две реализации, и они говорят не с одной и той же машиной: criarFsBrowserViaApi(workspaceId) вызывает GET /workspaces/:workspaceId/project-folders в api, жёстко ограниченный BRABO_PROJECTS_BASE (ADR 0141), тогда как connectFsBrowserChannel(projectId) (lib/fs-browser-channel.ts) говорит через Phoenix-канал terminal:<projectId> и читает диск ПОЛЬЗОВАТЕЛЯ через runner.

    Интерфейс был извлечён из модуля канала именно потому, что у него перестала быть единственная реализация. FolderBrowserModal выбирает между ними через размеченное объединение — origem: { tipo: 'api'; workspaceId } | { tipo: 'runner'; projectId }, а не два необязательных props, чтобы «ни одного» и «оба» не были представимыми состояниями, которые компоненту пришлось бы обрабатывать во время выполнения, — и его тело никогда не узнаёт, что получило. По origem ветвятся только три вещи: какая фабрика работает, какие ярлыки существуют (/ не предлагается транспортом api; он вне базы по построению, и кнопка могла бы закончиться лишь 400) и имеет ли смысл RunnerOnboardingPanel.

    ListagemResultado получил три НЕОБЯЗАТЕЛЬНЫХ поля — arquivos, simbolicos, truncado, — и они необязательны, потому что только транспорт api считает то, что исключил. Протокол runner (FsEntrada в apps/runner/src/channel.ts) возвращает папки и файлы вперемешку и ничего не считает; заполнить там нули означало бы утверждать «ничего не осталось за бортом», а это не то же, что не знать.

    RN-504 направила ОБА режима в api и объявила цену: для runner список перестал быть машиной пользователя и стал базой. Это было принято, потому что режим runner должен был уйти из мастера создания, — он не ушёл, и RN-533 (ADR 0151 пункт 7) это отменяет. Теперь транспорт выбирает РЕЖИМ, потому что они отвечают на разные вопросы: mounted спрашивает api (ваша папка живёт под базой, на СЕРВЕРЕ), runner спрашивает локального агента (ваша папка живёт на машине, которую сервер не видит). Ветвь runner опирается на проект, который мастер уже создал заранее (RN-437); когда это создание проваливается, никакое модальное окно не открывается, потому что откат на api показал бы базу СЕРВЕРА под подписью «ваша машина».

    Сбой несёт РАЗМЕЧЕННУЮ причину (MotivoDeFalhaDoAgente): sem-agente — это сервер, УТВЕРЖДАЮЩИЙ, что runner нет, sem-resposta — таймаут, упавший socket или отвергнутый ticket, — незнание, названное незнанием (RN-088/RN-468). Компонент решал по includes('Nenhum runner conectado'), сопоставляя фразу на pt-BR, живущую в .ex engine; сопоставление подстроки теперь живёт ровно в одном месте — модуле, владеющем протоколом канала, — и переписанное сообщение engine деградирует до sem-resposta, но никогда до «агент есть». Обе причины монтируют EsperaDoRunner — ожидание RN-474, ПЕРЕИСПОЛЬЗОВАННОЕ: те же три состояния, тот же потолок, тот же сигнал, — которое само повторяет упавший листинг, когда меняется штамп. Одно ожидание на экран: RunnerOnboardingPanel получает mostrarEspera, ложное лишь там, где его хозяин уже показывает ожидание. И выбор папки ГОВОРИТ, чей диск он перечисляет, в обоих источниках, — единственной подсказкой до этого была подпись ярлыка, которая называет место, а не машину.

    Панель также РАСПОЗНАЁТ уже сопряжённую машину (RN-548, ADR 0154). listRunnerDeviceKeys в lib/api-client.ts читает GET /projects/:projectId/runner-device-keys, который начиная с RN-543 помечает ВИД каждого ключа, — а весь вывод живёт вне компонента, в lib/agente-de-maquina.ts, потому что правило касается ДАННЫХ, а компонент — отрисовки. Семь состояний, ни одно не схлопывается в другое, и сбой выводится из isError, а не из статуса, поэтому сетевая ошибка говорит «не знаю», а не крутится в «verificando…» вечно. Зарегистрированный ключ — НЕ работающий агент — та же дисциплина, что уже навязывает workspaceVerifiedAt, — а список принадлежит УЧЁТНОЙ ЗАПИСИ, а не этому браузеру, поэтому самая сильная доступная фраза — «у вашей учётной записи есть сопряжённая машина». Оба ограничения произносятся на экране. Поток через браузер из ADR 0118 (сгенерировать ключ, скачать бинарник, записать папку) был выведен из употребления в ADR 0203 (RN-687): панель теперь показывает команду install.sh, которая уходит, когда распознан ключ, обслуживающий проект, а ручная команда с PAT остаётся в <details>, названном по случаю, на который она отвечает (другая машина). Минимум для чтения берётся из roleAtLeast против developer ENDPOINT, а настоящий 403 попадает в то же состояние — роль workspace — прокси, авторитет — api.

    Глобальная страница контейнеров (/containers, ADR 0136/RN-495) — чтение WORKSPACE, а не проекта, — getContainersOverview в lib/api-client.ts вызывает GET workspaces/:workspaceId/containers, а ContainerOverviewItem в lib/api-types.ts отражает ContainerOverviewItemResponseDto. То, что нельзя сделать пакетом, — спросить broker о наблюдаемом состоянии, — получает вместо этого явный бюджет на загрузку (ObterVisaoGeralDeContainersUseCase.TETO_DE_VERIFICACOES_POR_CARGA, спрашиваются только строки provisioning/running, с потолком 20): строка вне бюджета говорит naoVerificado, никогда молча не переиспользуя ответ другой строки и не наследуя зарегистрированное состояние. Действия (остановить/удалить/поднять) — proposed_action, как везде, — страница никогда не вызывает broker напрямую, — а ожидающее действие каждой строки (если есть) приходит в том же пакетном чтении и отрисовывается как встроенный ApprovalCard, тот же шаблон, что ProjectPrsTab.tsx уже использует для предложений merge.

    Начиная с RN-521 join — LEFT, и страница перечисляет ВСЕ проекты workspace, потому что она стала человеческим путём для подъёма ПЕРВОГО контейнера: подъём, проваливающийся до регистрации, не оставляет строки, а старый INNER JOIN скрывал ровно тот проект, которому страница была нужна. Поэтому ContainerOverviewItem.registrado допускает null — третье именованное в типе состояние, отличное от stopped и от «не удалось пронаблюдать», — а строки без контейнера никогда не попадают в бюджет broker, поэтому не могут вытеснить настоящий контейнер. Ветвление между container_start (broker) и container_start_via_runner (локальный агент) — чистая функция КЛИЕНТА, routes/containers-subida.ts: она же решает, когда НЕ предлагать кнопку (нет решённого образа, runner, папку которого ни один агент никогда не подтверждал, роль ниже maintainer по roleAtLeast), и у каждого отказа есть собственный текст — экран никогда не предлагает действие, о котором уже знает, что оно провалится, и никогда не скрывает почему.

    ДРУГОЙ предлагающий — агент Infra Lead — ветвится так же начиная с RN-566. Оба его инструмента проходят через единую recusa_local_de_subida/2 в infra_lead_server.ex, которая читает проект ОДИН раз (Project.get/1, тот же процесс BEAM, никогда HTTP: сетевой вызов внутри цикла агента — та цена, которую это исправление не могло платить) и возвращает nil или ИМЕНОВАННУЮ причину, по ветви на инструмент, — container/mounted предлагают container_start, runner отвергается с указанием на container_start_via_runner, а ветвь container_start — СПИСОК РАЗРЕШЁННЫХ, как у broker, поэтому новый режим в enum рождается отвергнутым. Отказ — текст РЕЗУЛЬТАТА инструмента, который читает модель (вход цикла, RN-163), а не agent.error, а tool.call по-прежнему порождается, чтобы локальный отказ никогда не исчезал из timeline. Чего агент НЕ проверяет, а экран проверяет, — решённый образ и подтверждённую папку.

    Границы и инварианты

    Это самая важная часть. Каждый пункт ниже проверяем, и у многих есть тест, проваливающийся при нарушении.

    1. Домен чист. apps/api/src/domain/ не импортирует infrastructure, application, @nestjs и никакой драйвер базы — проверено: ноль вхождений всех трёх. Направление всегда interfaces → application → domain, и 89 файлов application импортируют domain. Если вам нужен IO внутри domain/, схема неверна: создайте порт в application/ports/.

    2. Доменное событие неизменяемо. В таблице событий никогда не бывает UPDATE. У session_events есть unique(session_id, seq), а seq плотен по сессии — тест восстановления проверяет отсутствие дыр. Состояние, которому нужно меняться (жизненный цикл гипотезы, статус handoff), живёт в собственной изменяемой таблице рядом с событиями. Предложение handoff, переставшее быть действующим, становится superseded в этой таблице и получает собственное событие handoff.superseded — никогда не правку объявившего его handoff.offered (ADR 0182).

    3. Ни одного вызова LLM вне Harness. Это не соглашение: у engine нет клиента LLM. Он просит api, которая выполняет metering.

    4. Любое действие с внешним эффектом становится proposed_action. deny всегда побеждает allow в permissions.json, и два потолка применяются последними, поверх уже вычисленного вердикта: merge в защищённую ветку и патч инструкции никогда не автоодобряются. См. RN-006 и RN-007.

    5. Merge в защищённую ветку — ручной. Варианта его автоматизировать нет. Это потолок в домене (decide.ts), гарантированный тестом.

    6. Одна сессия — один владелец. SessionServer регистрируется под :global, а не в локальном Registry — без этого N реплик держали бы N копий одной сессии, и копии без heartbeat убили бы живую сессию (ADR 0026).

    7. Сбой агента записывает ИСТОЧНИК (infra | model | code | policy), никогда диагноз методом исключения. Дорогой урок ADR 0020: падение провайдера было записано как «модель остановилась, не подав сигнала», и система обвинила модель в инфраструктурной проблеме.

    8. Контейнер проекта решается, а не подразумевается. Вкладка Код разблокируется только после того, как Arquiteto выпустит artifact.project_image, — пока состояние sem_decisao, чтение кода возвращает 409 (RN-105). А git push, открытие PR и deploy не проходят через терминал даже в рамках проекта: decide() распознаёт их по префиксу команды и возвращает deny ДО любого разрешающего шага — не require_approval, потому что «всегда разрешать» записало бы шаблон в allow и снова открыло бы дверь (RN-106, ADR 0065). Жизненный цикл контейнера (подготовить, перезапустить, очистить) существует как таблица project_containers и конечный автомат provisioning → running ⇄ stopped (RN-243 — RN-248, ADR 0081): сценарии использования лишь записывают переход, и ни один из них не обращается к Docker. Сокет Docker сервера держит brabo-broker. Поэтому этот инвариант сосуществует с политикой области путей ADR 0055.

    А начиная с ADR 0143 /RN-502 решённый образ больше не единственное предусловие: dev agent не берёт ни одной задачи, пока контейнер проекта не ЗАРЕГИСТРИРОВАН как running. Страж живёт в Engine.Dev.AgentIo.try_claim/2 — единственной точке claim, — а не только в activate-execution api, потому что реидратация доходит до try_claim/2, не проходя ни через какой маршрут (DevAgentServer.init/1 -> finish_restart_recovery/1). Без контейнера агент переходит в :idle (единственное состояние, которое ещё спасает wake) и говорит об этом через dev.blocked_by_container. Другая половина того же правила в том, что Engine.Actions.TerminalExecutor перестал падать в System.cmd внутри процесса engine, когда контейнера нет: он отказывает, с названием причины, как уже делал режим runner.

    9. Агент, который ПИШЕТ, должен уметь ЧИТАТЬ и должен уметь СПРАШИВАТЬ. Обе половины — один и тот же урок, и пришли они от агента, у которого были только инструменты записи: PO собирал контекст один раз, при kickoff, и с тех пор действовал по устаревшему снимку — перед пробелом он выбирал между выдумыванием и остановкой (RN-164, RN-165). Чтение не становится proposed_action (инвариант 4 касается ВНЕШНЕГО эффекта, а чтение им не является), но оно ограничено в смысле ADR 0060: область закрыта путём маршрута, стоимость постоянна на вызов, и есть потолок строк в тексте, передаваемом модели. И цикл агента не заканчивается молча — потолок итераций порождает toolloop.limit_reached, невыполненное обязательство порождает долговременный исход с источником (RN-166).

    Сквозные вопросы

    Кросс-origin. Web отдаётся с собственного origin и говорит с двумя другими, поэтому CORS — архитектурная граница, а не деталь конфигурации (ADR 0037). Четыре пути, и только три проходят через CORS:

    путь механизм
    web → api, HTTP CORS Nest, точный origin из WEB_ORIGIN + credentials
    web → engine, HTTP (/health) EngineWeb.Plugs.Cors, только маршруты health
    web → engine, WebSocket check_origin endpoint Phoenix — WebSocket не проходит через CORS
    api ↔ engine, HTTP CORS неприменим: серверный клиент, а не браузер

    Одна переменная — WEB_ORIGIN — питает первые три, в обоих сервисах. Независимое двукратное чтение её — вот как CORS engine остался вообще без origin, тогда как в check_origin уже был правильный список; в engine она теперь разрешается один раз, в runtime.exs.

    И порт — часть origin: web на :5174 — другая система в глазах браузера. Поэтому vite.config.ts использует strictPort.

    Аутентификация. First-party, в домене api — внешнего IdP нет. Пароли с argon2id, access token EdDSA на 15 минут и непрозрачный refresh token с обязательной ротацией; сессия web живёт в cookie httpOnly с CSRF через double-submit. JwtAuthGuard глобален и читает пользователя по sub токена (это users.id); открытый маршрут требует явного @Public().

    Ни одно решение RBAC не читает claim токена: роль берётся из request.user.id и строк в базе. Поэтому матрица прав пережила смену эмитента без изменений. Решения — в ADR 0031 и в ADR 0032.

    Вызовы engine не проходят через JWT: маршруты /internal/* — @ServiceRoute(), а EngineServiceGuard сравнивает общий секрет (BRABO_SERVICE_TOKEN) за постоянное время. Вся поверхность классифицирована в security-surface.md, и табличный тест проваливает новый маршрут без классификации.
